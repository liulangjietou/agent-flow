# PostgreSQL 容量基线

后续修复及同参数复测见 [参与者检索性能验证](participant-search-performance.md)。本文保留修复前的阶段 56 原始基线，便于对比。

`scripts/capacity_baseline.py` 为现有审批链路提供可重复的本机负载测量。它创建独立的 PostgreSQL 17 与后端容器，经真实 HTTP API 发布流程、创建申请、提交和批准，再测量待办、申请检索、流程目录、运营和通知查询。数据库中同时保留未完成任务和批准历史。

`PASS` 表示本次请求与业务核对通过，不表示满足生产容量或可用性目标。日提交量、峰值并发、部署资源、通知延迟和 RTO/RPO 仍需要确定，不能由一次本机测试推导。

## 运行方式

使用本机 Docker 28+ 的 Unix socket context、Python 3.10+、已在本地构建的服务镜像和 `postgres:17` 镜像。工具不下载镜像，不接受现有服务 URL、数据库连接或凭证。可以先按演示部署文档构建镜像：

```bash
docker build -f deploy/Dockerfile.server -t agentflow-capacity-server .
docker pull postgres:17
python3 scripts/capacity_baseline.py \
  --server-image agentflow-capacity-server \
  --output /fyoung/tmp/agentflow-capacity-run-001 \
  --applications 1000 --definitions 40 \
  --seed-concurrency 4 --concurrency 1,4,8 --requests 100 --warmup 5
```

输出目录必须尚不存在且位于 `/fyoung/tmp` 下。目录权限 0700、JSON 文件 0600。失败后换一个目录重跑；不要覆盖或删除原失败证据。默认本机端口 8192，可指定 8190–8290 中的未占用端口。

| 参数 | 范围与含义 |
|---|---|
| applications | 100–10000 份真实申请，申请人交替为 alice/bob |
| definitions | 1–100 个流程版本，且不超过申请数 |
| seed-concurrency | 1–8 个并发生成/办理客户端，默认 4 |
| concurrency | 1–5 档不同并发度，每档 1–16，默认 1,4,8 |
| requests | 每个读端点、每档并发度的请求数，1–500，默认 100 |
| warmup | 每个读端点的预热次数，1–20，默认 5 |

流程为“开始 → 指定 manager 审批 → 结束”，一份申请一个轮次。每四份申请批准一份，其余保持待办。表单含精确金额与合成文本；没有真实员工、财务、模型或附件数据。此负载不代表会签、复杂分支、不同租户或不同业务正文尺寸的容量。

## 隔离与资源

- 本次运行生成随机网络、卷和容器名，只连接本次新建数据库，不复制主库。数据库不发布宿主机端口。
- 后端仅映射到 `127.0.0.1`，启动后核对实际端口映射；HTTP 客户端不继承系统代理、不跟随重定向。
- 使用独立 NAT 桥接网络，不加入已有业务网络。它不是禁止全部出站访问的网络策略；本工具不配置外部通知、模型或其他集成目的地。
- 后端限制 2 CPU、1536 MiB 内存、最大 Java 堆 1024 MiB、Hikari 最大连接数 10；数据库限制 1 CPU、768 MiB。限制不等于独占资源，Docker Desktop 和宿主机上的其他负载仍会影响测量。
- 正常完成、失败或键盘中断均核对本次容器完整 ID 与运行标签，然后停止后端、数据库。不会删除容器、网络、卷或样本；身份不符时报告清理错误并保留资源。
- 首个失败阻止排队中的业务操作继续发出，已在途的请求等待原结果；写请求不自动重试。若进程被强制终止，按报告或 Docker 的 `io.agentflow.capacity.run` 标签识别资源，核对后再停止。

只绑定 localhost 的行为及 Docker 28 版本边界依据 [Docker 端口发布文档](https://docs.docker.com/engine/network/port-publishing/)。首轮工程试跑发现 internal 网络未提供宿主机端口映射，按保护条件终止；之后使用上述独立 NAT 网络，失败产物保留。

## 测量口径与报告

报告保存服务/数据库镜像不可变 ID、PostgreSQL/Java/Python 版本、Docker 可用资源、容器资源限制、负载参数、每个请求的延迟与状态。令牌、密码、请求正文、响应正文和 Docker 完整环境变量不进入报告。

- `seed`：真实定义创建/发布及申请创建/提交；`actions`：实时任务读取和逐单批准。记录各端点分布及阶段总时间，其中可能包含冷启动/JIT 影响。
- `seedWallSeconds` 仅计申请创建加提交的生成阶段，不含之前的定义创建/发布；`actionsWallSeconds` 同时包含任务读取与批准。端点延迟和业务循环耗时不能混用。
- `warmup`：预热，单独记录，不混入 `read_c1` 等正式查询阶段。
- `read_cN`：N 个有界客户端循环请求。每个请求新建 HTTP 连接；延迟从发送前到完整响应读取和 JSON 解码后，包含客户端、连接、服务和数据库时间。
- p50/p95/p99 使用最近秩；失败和超时仍进入请求计数及延迟分布。报告列出样本数，小样本尾延迟不能当作稳定分布。
- 吞吐为该阶段全部完成请求数除以阶段实际秒数，属于闭环观测值；不是独立到达流量下的最大 RPS。各端点请求数量相同，不代表生产流量比例。

产物：`progress.jsonl` 为阶段进度，`samples.json` 为原始请求样本，`report.json` 为配置、统计、业务核对、容器标识和停止结果。`INCOMPLETE` 不能作为通过证据，也不会因 HTTP 全为 200 就忽略业务不一致。

最终核对全部分页申请的精确 ID 与状态、剩余任务集合、申请人的可见结果、无关账号空结果、提交/批准轮次、缺失历史计数、流程版本总数及 manager 的通知总数。测试不直接写业务表或 Flowable 表。

## 职责与门禁

CLI → 隔离部署 → 认证/定义/申请/任务 API → 原应用服务、领域聚合与引擎适配器。负载生成与测量属于部署验收脚本层；没有生产 Java、UI、SQL、索引或审批语义变更。

CI 执行工具保护测试，覆盖输出防覆盖、远端 Docker 拒绝、容器身份、保留资源、HTTP 失败与脱敏、重定向、分位数、重复游标和失败后停止排队操作。CI 不自动进行写入型压测。正式数据规模测量独立执行，避免与编译测试同时争用资源。

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s scripts/tests -p 'test_*.py' -v
```

当前报告未覆盖生产 SLO、持续压测、开放式到达流量、跨节点扩容、网络/TLS/反向代理、故障注入或灾备时限。发现延迟问题后应依据对应 SQL/调用链进一步定位，不能只增加索引或线程数掩盖原因。

## 本机实测（2026-09-23）

两个独立数据集均使用上述固定容器限制，Docker Desktop 分配 5 CPU、约 15.4 GiB 内存；架构 arm64，PostgreSQL 17.11、Java 17.0.20。每个数据集含 40 个发布流程，每端点预热 5 次，每档每端点测量 100 次，共 7 个读端点。测量期间没有并行运行项目编译或测试；宿主机资源不是独占。

| 申请数 | 批准 / 待办 | 1 并发混合请求/秒 | 4 并发 | 8 并发 |
|---|---|---:|---:|---:|
| 1000 | 250 / 750 | 68.423 | 86.675 | 71.487 |
| 5000 | 1250 / 3750 | 16.242 | 13.744 | 11.549 |

| 查询端点 | 1000 申请，8 并发 p95（ms） | 5000 申请，8 并发 p95（ms） |
|---|---:|---:|
| 管理员申请检索 | 83.181 | 90.883 |
| 参与者申请检索 | 201.415 | 1296.869 |
| 待办首页 | 201.402 | 1306.733 |
| 待办第二页 | 200.197 | 1314.564 |
| 审批运营 | 398.950 | 2703.654 |
| 流程目录 | 83.833 | 88.568 |
| 站内通知 | 84.135 | 91.566 |

正式读测量共 4200 请求，零失败；两个数据集的所有业务核对通过，保留共 6000 份申请。另有 100 份申请的功能试跑通过。全部测量容器已停止，主业务服务与数据未被该工具修改。

数据量增加后的延迟增长集中在涉及引擎事实的参与者、待办和运营查询，不能仅凭增加客户端并发提升吞吐。测量期间一次资源采样显示数据库约占 99% 的单 CPU 上限，后端约 2.6%；这是一次采样，不是全程资源曲线。

测量结束后单独重开 5000 样本库，对运营使用的 `SELECT COUNT(*) + FlowableActiveTaskSql.fromCurrentApplications()` 做三次 `EXPLAIN ANALYZE`：执行时间 43.727、73.847、36.616 ms。计划返回 3750 个活跃任务，存在各 3750 次的任务、申请与两次引擎变量索引读取，另扫描变量表按名称筛选。该结果定位了一条需继续分析的热点查询，不等于完整运营接口耗时，也未证明增加某个索引即可解决。

可移植摘要与原始文件摘要见 [本次基线证据](evidence/capacity-baseline-20260923.json)。原始报告及每次请求样本分别保存在 `/fyoung/tmp/agentflow-capacity-1000-20260923/`、`/fyoung/tmp/agentflow-capacity-5000-20260923/`；查询计划在 `/fyoung/tmp/agentflow-capacity-5000-query-plan.json`。报告不把上述数字换算成可承诺的用户数或日业务量。
