## 旧版本升级与实际办理

先用旧包在独立文件 H2 中建立组织、原 v1 复制草稿、已发布定义和一张在审报销。升级新包后，旧草稿、旧发布定义及原申请的公开详情逐项一致；原流程继续由业务主管、纸件签收和财务审核完成，未补造上溯记录。新版目录接受 v2 复制，携带过期 v1 来源的新复制请求返回 `TEMPLATE_VERSION_CONFLICT`。

新报销采用 6,000 元示例，主管后进入部门负责人。部门负责人为申请人，因此按发起时的任职上溯原主管 manager。提交后把任职主管改为 bob，并在后续部门节点激活前强制终止应用。重启后当前任务和将要激活的部门任务仍由 manager 办理；部门节点的上溯审计保留申请人、替代人、原流程版本和规则版本。之后正常完成签收与财务审核，原审计编号不变。

另一张报销先按 bob 提交，撤回后将主管改回 manager 并重新预检提交。只有第 2 轮采用新关系，未把第 1 轮候选当作当前责任。独立的缺少上级场景在正式提交返回 `APPROVER_NOT_FOUND`，草稿及财务版本不变，没有上溯审计或成功提交。

## 纸件职责、重启与恢复

并行场景保留共同必经签收和财务审核。财务人员先实际签收纸件，尚未点击任务同意时，尝试审批其原本有候选权的业务任务返回 403；旧候选历史没有被改写，当前待办和总数排除冲突任务。第二次强制终止后，原签收事实及职责限制仍有效。

停止应用后导出数据库，并在另一目录恢复。253 张表、662 条记录的逐表内容摘要一致；在独立副本上比较完整 SQL 语句，1,980 条结构、约束及序列声明一致。原合成预算受理文件配套保存。恢复后的公开详情与原快照一致，冲突财务人员仍没有业务待办；原在审单由 bob 继续推进到部门节点，使用原冻结候选并产生对应上溯审计。恢复未改写原数据库和原合成预算受理记录。

共 6 次应用启动，包括原版本、两次强退后的重启和独立恢复。本轮自建应用进程已全部停止，原运行实例 87821 保持。本样例没有附件，不作为票据原件恢复证据。6 个不同预算命令各发送一次，没有因升级、重启或恢复增加发送。
