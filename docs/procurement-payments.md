# 采购付款实施

采购付款采用独立结构化申请。领域、独立业务持久化、财务只读预检、本地应付占用、正式提交与审批接口已实现。模板和页面已完成本地验收，原验收库随后已升至 V67。跨业务票据防重已接入 V67，详见[票据归属](cross-business-invoices.md)。独立供应商支付及外部原应付结算仍在接续。

## 调用链与职责

采购申请页填写法人、供应商、原应付号及本次金额。应用服务按当前员工和固定财务目标读取 `procurement-payable`，取得原合同、订单、验收、查验发票、应付挂账、预算确认及供应商账户；申请聚合冻结本轮完整依据。审批状态仍由审批聚合管理，采购付款批准不等于银行付款或原应付核销。

`ProcurementPayablePort` 的快照验证三单来源和金额、数量守恒；`ProcurementPaymentRequest` 拥有自身内容、版本、提交历史与批准约定。组织读取、当前身份、外部端口、跨申请应付占用以及后续独立财务授权和出纳执行归应用编排。网络不得在数据库事务中执行。

受影响场景为供应商已有应付的部分或全额付款、退回后修改与重提、原未付额变化、账户或匹配依据变化、重复发票行和多发票共用同一订单行。员工借款与费用报销保持各自业务语义；供应商不映射为员工账户。

## 已采用的采购范围

首条链路办理已有合同、采购订单、验收和查验发票的原应付。必须有应付挂账与原采购预算确认引用；本系统不会再次按员工费用记账或重复消费同一采购预算。预付款、无订单付款、超验收容差和外币付款需要各自明确依据，不通过本条已匹配应付路径隐式放行。

请求只包含法人、申请员工、供应商引用和应付引用。外部目录按该员工限定范围；返回精确匹配请求，并保留版本、观察时刻与有效期。未来、到期及超过五分钟的依据不得用于新提交，旧轮次在恢复时仍按当时提交时刻验证。财务目的地摘要随提交快照固定，配置后来变化不得改查另一套系统。

每行记录原订单行、验收引用、规范发票键、发票行、原件摘要、查验引用、单位及订购/验收/开票数量和金额。数量不隐式截断，最多六位小数；金额复用非负两位 `Money`。开票不得超过验收，验收不得超过订单。同订单行被多张发票使用时必须共用相同验收依据，累计数量和金额分别不能超过实际验收；同发票行不能重复。同发票的摘要和查验依据保持一致，税额不能超过该行含税额，全部开票行合计必须等于原应付总额。

原未付额等于原应付减已结算金额。已付完可以是有效只读事实，但不能支持新的正额申请；本次申请不得超过实际未付额。该读取不产生外部预留。已有本地占用约束还不能阻止财务系统的其他支付，后续资金执行必须在原外部目标复核并取得原应付的明确结算依据。

供应商账户保存法人、供应商、稳定账户引用、掩码、摘要与源版本，拒绝完整卡号或换供应商。申请内容不能注入账户、已付额、匹配或批准状态。公开投影接入时只按字段权限展示所需材料，内部完整快照不直接返回给普通列表。

## 只读财务协议

沿用现有 `contractVersion=1`、租户及请求关联号的严格 JSON 信封，固定路径 `procurement-payable`。它是读取操作，没有资金写入的幂等头，返回成功快照或封闭拒绝原因：法人、员工、供应商、账户、应付不可用，或尚未满足采购匹配。其他接口的拒绝码不能冒充采购结果。

未配置、目的地改变、网络失败和格式错误均保持不可用。适配器复用有界响应、无重定向、严格未知字段和金额解析。跨租户、错原件、过期、超余额以及非掩码账户结果在信任边界拒绝。

## 当前验收与接续

12 项采购领域测试通过，覆盖多发票共享验收上限、原未付额、只读已结清状态、来源绑定、旧轮次保留与失败原子性。43 项服务端范围通过，其中采购 HTTP 5 项，其余覆盖财务传输、配置、既有付款账户和公开契约。回环 HTTP 使用本地夹具，不代表企业采购或资金系统验收。

V66 增加采购业务绑定、申请修订、持久预检及修订、本地应付占用及修订。预检输入包括原内容、双版本、任职、轮次和财务目标；运行只能领取一次，完成不能改变原租约。数据列与状态 JSON 交叉核验，错误归属和不存在的财务版本由外键拒绝。普通表单接口不能使用采购保留字段创建无业务绑定的申请。

同一租户、法人、供应商和原应付同时只允许一张本地活动申请。即使只申请部分金额，也先完整保护该应付的本地付款入口。退回、撤回、批准均保留占用；重提原子替换原轮次占用；拒绝、作废才按实际审批状态释放。新占用冲突时旧释放与新财务修订一起回滚。实际支付后的释放尚未接入，不能凭未付额的数值变化推断本次付款已核销。

本阶段采购领域 17 项、H2 持久化/迁移 9 项通过；PostgreSQL 33 项通过，包括采购持久化 8 项、V65→V66 升级 1 项、旧借款流程与采购表单绕过保护 19 项、公开契约 5 项。并发使用两个真实事务竞争同一应付，只有一个成功；升级保留旧表单和报销行。详情见 [持久化证据](evidence/procurement-persistence-20260929.json)。

## 正式提交与审批接口

`/api/v1/procurement-payments` 提供本人列表和创建；`/{id}` 按权限读取草稿或原轮次；写动作分别为 `revise`、`submit`、`withdraw`、`cancel`。`/{id}/prechecks`、`prechecks/options`、`prechecks/{jobId}` 提供明确排队、当前目标、历史和候选依据。全部写接口使用既有幂等边界，最小回执不缓存敏感明细。

排队固定原内容、双版本、下一轮次、本人任职和财务目标。后台短事务领取，事务外查询目录和原应付，完成时再次检查上下文。过期、目的地变化、任职变化、新一轮预检和网络期间修改都会使旧候选不可用。领取后崩溃只记录超时；不会自动重发旧任务。

提交重新检查候选，并在同一事务写采购轮次、替换应付占用、更新派生路由和启动审批。只有所有结束路径都经过可完整读取敏感明细的人工节点才可提交。最终人工批准确认实际轮次、原路由和现存占用后保存采购批准依据；中间审批不产生此依据。拒绝和作废同步释放，退回与撤回保留占用。数据库故障回滚业务修订、审批状态、轮次及引擎任务。

预检和详情统一返回受控投影，供应商账户仅显示掩码，不含账户引用、摘要、发票摘要或内部查验凭据。旧审批人看原冻结轮次，不能读取后续补正草稿；管理员也受敏感明细权限限制。三单数量返回精确十进制字符串，金额沿用 `Money` 字符串契约。

本阶段新增 18 项采购联动测试。H2 相关范围 38 项通过（采购联动 18、采购 HTTP 6、财务传输 14）；PostgreSQL 联动范围 42 项通过（采购 18、借款 19、契约 5）。实际 HTTP 财务夹具参与，覆盖并发领取/提交、原占用回滚、字段隔离、最终批准和故障原子性。OpenAPI 校验 201 个操作、387 个模型、74 个请求示例通过，见 [审批编排证据](evidence/procurement-workflow-20260929.json)。

大数量回归发现财务网关中间 JSON 树默认浮点化会丢失六位小数，原小整数测试没有覆盖。最小回环测试先稳定失败，再仅在财务网关隔离解析器启用精确十进制树；验证原值完整保留，七位小数不能被舍入后放行。平台通用 JSON 行为未改变。

采购与报销票据去重随后已接入 V67；接续独立付款授权、外部应付预留与结算。审批通过仍不产生银行付款、原应付核销或重复采购预算消费。

## 模板与页面本地验收

财务申请新增“我的采购付款”。申请人填写法人、供应商、原应付编号、用途与本次付款额；修改法人会清除原供应商、应付号和金额。预检显示原应付总额、已结及未结余额、供应商掩码账户、原挂账和预算确认引用，并分别展示订单、验收及开票数量与金额。页面不重算资金事实，数量保留服务端十进制字符串。

模板为“本次任职直属主管 → 财务复核”。财务占位角色在复制后绑定实际人员或岗位，未绑定不能发布；两个节点必须完整只读采购明细。采购明细已接入待办、申请详情和历史轮次，管理员仍受敏感组权限约束。草稿按身份暂存，最小保存回执只确认原操作，重新读取成功后才能预检和提交；版本、任职、内容与时效变化使原候选不可提交。

模板与后端相关范围 71 项、PostgreSQL 相关范围 43 项、前端范围 56 项通过，各范围有重叠；前端构建、201 个 OpenAPI 操作及 387 个模型检查通过。真实 HTTP 90 次（66 份业务 JSON 响应及 24 次登录）通过，其中 66 份业务响应逐份符合公开契约。

浏览器完成 70 元草稿、预检、正式提交、撤回、改为 65 元、第二轮预检提交、直属主管批准和财务批准。第一轮原 70 元及完整匹配材料保持；页面显示“已批准”，并明确实际付款仍需独立财务授权和结算。实测 376 CSS 像素窗口内，采购明细宽 285、滚动宽 285，无横向溢出；大数量 `999999999999999.123456` 完整保留。

V65→V66 以实际 jar 升级旧验收库，升级前备份 745705 字节，109 张业务表、5 份附件和 5 份财务命令文件保持。办理后原 107 张表的既有行保持，组织仅按验收需要新增主管任职、绑定申请人主管并增加目录修订；原付款、凭证、核销、退回及档案不变，采购批准未生成员工财务凭证。证据见[模板与页面验收](evidence/procurement-ui-20260929.json)。
