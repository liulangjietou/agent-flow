# 费用预算操作通知

F17 的费用预算冻结、调整冻结、释放和消费已接通原操作通知、受控详情与消息页面。通知描述一笔原命令的结果；当前预算占用、付款和业务结算仍须分别核对。独立预算冲回、预算调整业务及其他财务恢复来源仍需继续核对，F17 保持 OPEN。

## 调用链和职责

- 调用方：`ExpenseSubmissionService` 和 `ExpenseReductionService` 登记冻结或调整；`ExpenseReleaseService`、`ExpenseBudgetRetentionService` 和 `ExpenseSettlementService` 登记释放或消费。
- 下游：`BudgetOperationService` 保存操作与预算台账；`BudgetOperationCompleted` 继续只驱动终态的业务退回、释放、留存或结算处理。
- 受影响场景：提交、核减、退回重提、申请终止后迟到冻结、保留期释放、结算消费、未知结果查询和领取超时恢复。

新增 `BudgetOperationChanged` 独立描述持久状态变化。`claim` 中的领取超时、`finish` 和 `fail` 均经过同一保存入口；原 `BudgetOperationCompleted` 的终态语义保持不变。不会把未知或待处理事件交给结算完成分支。

`BudgetNotificationService` 负责最小提示、接收关系和事实去重。站内消息及外发意向与预算状态加入同一事务；通知写入失败时预算确认一并回滚，后续仍按原命令恢复。业务事务内不调用通知渠道。

## 原事实与去重

事件键为 `budget:<原命令 UUID>:<事实>`，每个接收人的同类事实只保存一次。后续登记的新命令使用新的编号，不覆盖原命令的消息。

| 原状态或回执 | 通知含义 |
| --- | --- |
| 首次排队、执行中、查询中 | 不制造结果或异常提醒 |
| `PENDING` | 预算系统正在处理，不能写成异常或成功 |
| 技术失败或领取超时 | 结果暂不明确，继续按原编号查询 |
| 权威查询 `NOT_FOUND` | 原操作查无，保留同一命令和编号重试 |
| `REJECTED` | 预算系统明确拒绝原操作 |
| `APPLIED` | 这笔原操作收到确认回执 |

预算的权威查无后原命令重试是既有预算协议；不套用凭证或付款场景的重发规则。历史冻结确认也不代表此刻仍有冻结：后续可能已经释放或消费，页面明确提示回到申请核对当前占用。

## 接收关系和读取边界

接收人从原命令对应的 `expense_report_revision` 确定。该版本完整快照重新派生的预算位置必须与原命令一致，包括单据、轮次、财务版本、员工、法人、币种、日期与分摊。

原申请人是固定参与人。若该精确财务版本由核减产生，其核减证据中的实际经办人必须同时匹配版本审计的操作者，才加入接收人；代理核减沿用实际操作者。后来的核减经办人、其他财务角色及当前最新财务版本不会反向改写旧命令的接收关系。自动释放和消费沿原确认位置追溯参与人，不将后台进程冒充为人工发起人。

生成和外发时，接收人须仍是可信目录中的有效人员。外发领取与重试还会重新检查原消息、原操作、申请和轮次关系，以及既有偏好、同意和收件绑定。最小提示不复制金额、账户、成本分摊、用途或远端错误正文。

`GET /api/v1/notifications/{id}/budget-target` 只处理当前用户自己的预算消息；拒绝查询参数，响应 `Cache-Control: no-store`。读取原命令摘要前调用 `ExpenseDraftService.read`，执行原轮次的申请可见性和财务字段权限。仅保有管理员角色也不能绕过字段约束。

返回原编号、轮次、财务版本、动作、操作状态及已验证回执摘要，不公开命令、金额、分摊、账户、内部连接目标或写入许可。旧拒绝消息在新命令成功后仍定位旧拒绝记录；旧冻结消息在后续核减后仍保留其原财务版本。

## 消息页面

消息中心在点击“查看原预算”后读取原记录。详情区分正常处理中、结果未知、权威查无、明确拒绝和已确认，并显示受控的中文原因。页面提供重新读取和原申请轮次导航，原业务页面继续执行当前权限校验。

重新读取先清空旧事实；身份切换、消息切换、失权、超时和卸载都会使旧请求失效。即使底层请求忽略取消，迟到成功响应也不能恢复旧回执。
