# 报销结算修订通知

F17 的报销核销完成、持久阻塞、预算核销拒绝和资金或凭证复核状态已接通站内消息、外发意向及原结算详情。原银行到账、预算操作、付款凭证和归档仍各自保留原有含义。供应商结算和其他独立财务恢复来源、固定安装包及环境验收尚未完成，F17 保持 OPEN。

## 调用链与职责

四处业务服务拥有实际状态转换：

| 调用方 | 实际业务变化 |
| --- | --- |
| `ExpenseSettlementService` | 核销资源、登记预算消费、记录阻塞、明确重试和预算终态 |
| `ExpenseSettlementRegistration` | 资金或挂账事实登记结算；冲突、退票或冲销冻结原账本 |
| `ExpenseFinancialDisputeRecovery` | 原资金或凭证裁决、独立冲销安全结束及无退回确认后的接续 |
| `ExpensePaymentReturnService` | 新退回或不一致查询冻结结算；明确登记实际退回事实 |

这四处更新共同使用 `ExpenseSettlementChanges`，先由现有仓储保存状态及修订，再发布 `ExpenseSettlementChanged`。它只编排持久化和事件；领域转换仍由 `ExpenseSettlement` 判断，各原业务服务继续持有事务及锁。消息与外发意向失败会回滚原更新。结算创建仍只登记排队意图，不提前发送完成通知。

下游通知服务读取原修订和原财务来源，生成最小消息。后台网络调用、资源核销、资金与预算命令均不进入通知读取路径。

## 事实与原参与关系

键为 `expense-settlement:<报销 UUID>:<结算修订>:<事实>`。同修订重复事件去重；重试或裁决后再次发生同类事实拥有不同修订，不被旧通知吞掉。

| 事实 | 含义 |
| --- | --- |
| `BLOCKED` | 原核销条件不满足，银行成功事实保持 |
| `BUDGET_REJECTED` | 预算实际占用未通过，已经消费的资源不能重复扣减 |
| `REVIEW_REQUIRED` | 原资金或凭证依据需要独立复核，迟到预算成功不能自动解除 |
| `SETTLED` | 本地资源与预算实际占用完成；付款凭证、归档和后续调整仍须分别核对 |

`QUEUED` 和 `BUDGET_PENDING` 保持安静。恢复至等待状态不伪称已经完成；恢复至 `SETTLED` 才产生对应结果事实。

原申请人、原挂账准备参与人和原付款授权人由固定输入及持久原命令确定。零核定没有付款或挂账命令，仅额外纳入原财务修订能够确证的实际核减人。不会枚举当前财务角色猜测接收人，也不把出纳执行关系当作业务结算权限。

生成及投递重新检查人员有效性；原财务参与人还须在原法人具有有效任职。消息详情另行执行原轮次的当前字段权限。管理员不能凭自己持有的消息绕过字段约束。

## 原修订读取与页面

`GET /api/v1/notifications/{id}/expense-settlement-target` 拒绝查询参数并返回 `Cache-Control: no-store`。消息接收人、原申请、原财务版本、修订事实和不可变结算输入逐项核对；历史修订读取不能回退到最新修订充数。

响应分别返回 `notice` 和 `current`：前者为消息发生时的原修订，后者为同一结算输入的当前状态。旧预算拒绝消息在明确重试成功后仍保留原拒绝和原预算编号，同时显示当前结算完成与新的预算编号。金额、账户、回单明细、外部地址及办理许可不出现在摘要中。

消息中心点击“查看原结算”才读取。页面区分“消息发生时”和“当前结算状态”，原登记依据分别标明银行付款、借款全额冲销或零核定。重新读取、身份或消息切换先清空旧事实；超时、失权和卸载使迟到响应失效。只提供重新读取和原申请轮次导航。
