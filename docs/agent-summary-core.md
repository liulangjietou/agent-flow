# Agent 审批摘要核心（开发中）

审批摘要的 DDD 聚合、证据引用和持久化已实现，后续阶段已接入有申请授权的只读 API 与详情 UI，见 [运行记录](agent-summary-records.md)。当前没有模型适配器、后台执行器或生成/复核写入口。测试中的 `test-model-v1` 和摘要文本都是合成夹具，不是模型调用证据。

模型供应商或协议、实际模型名称、部署位置及允许发送的申请字段尚待确认。本阶段不发送申请数据到模型，也不读取或保存模型密钥。

## 调用链与职责

后续应用服务应先经现有 `ApprovalApplicationFacade.get` 复核实时申请可见权限，再经已确认的字段策略取得输入；已授权的引用与摘要组成 `AssistInput`。`AssistRun` 负责自身状态和人工复核不变量；`AssistRunRepository` 保存运行与追加记录，JDBC 适配器复核租户、申请版本及原输入上下文。外部模型调用必须发生在数据库事务之外。

读取运行的授权编排已接线；创建/执行的身份复核、字段解析、脱敏及外部调用尚未接线，不能把值对象校验当作完整业务鉴权或数据发送策略。

## 已实现规则

状态依次为 `QUEUED → RUNNING → COMPLETED → ADOPTED / DISMISSED`，执行失败进入 `FAILED`。每次推进只增加一次运行版本，乐观版本阻止重复推进和迟到结果覆盖已失败运行。一次运行终止后不复用原身份重试；后续重试用例需建立新的可追踪运行。

- 输入绑定申请 ID、内容/审批上下文版本、轮次和不可变证据清单；不存储多余的原字段正文。
- 当前只支持审批摘要需要的 `application:...` 和 `form:...` 源键；这些是清单内的不透明标识，不能执行为 URL、文件路径或工具调用。附件抽取不属于当前实现。
- 每条模型陈述必须带证据，源键与 SHA-256 摘要须同时匹配授权输入。证据匹配只证明来源绑定，不证明自然语言陈述真实，仍须人工核对。
- 记录实际提供方、模型版本、提示版本与模型报告的置信度。置信度不是经过校准的概率，也不触发批准；所有完成结果都停在等待人工复核的状态。
- 人工修订文本与模型原文分开保存。采纳时要求申请版本仍一致；已变化的申请仍可拒绝旧建议，不可采纳旧建议。
- 聚合没有审批、发布、付款或修改申请的方法，也没有工具执行或网络依赖。文本按不可信内容原样保留，未来 UI 必须按纯文本展示。

输入最多 64 个来源，摘要最多 20 条，每条最多 1000 字符。技术限额以代码常量为准，不能据此认定业务容量和模型上下文能力已验收。

## 持久化与事务

V19 只增加 `agent_assist_run`、`agent_assist_transition` 两张表，不补造旧数据。运行创建通过 `INSERT ... SELECT` 绑定同租户、同申请版本和轮次；查找始终限定租户。

状态更新不能改写原输入上下文。当前运行和追加记录在同一事务中保存；追加记录失败时，运行状态一起回滚。人工采纳在事务中锁定源申请并重新校验版本，防止查看之后申请被并发修改。锁内没有模型或其他外部调用。

时间与模型/复核结果在 JSON 中保留完整精度，SQL 时间列方便数据库侧核对创建时间。仓储读取通过领域行为重建聚合并校对状态与版本，不能把不一致的存储结果当作有效运行。

仓储不提供删除、替换旧追加记录或跨租户检索的方法；这不等于已经具备独立审计留存、防篡改或生产数据库权限治理。
