# 逾期借款提醒与新借款控制

F08 对应原费用领域设计 §6.2。逾期只由法人当地日期与实际未还余额决定；是否阻止新借款由服务端按租户明确配置。本项不改变费用报销审批，也不将预留额度当成已还款。

## 规则与配置

```yaml
agentflow:
  advances:
    overdue:
      reminders-enabled: true
      reminder-delay-ms: 60000
      tenants:
        your-tenant:
          block-new-requests: true
```

- `true`：本人在本次借款法人下存在逾期且未还清的借款时，预检和正式提交均阻断。检查覆盖该法人的所有币种，不合并其他法人、人员或租户。
- `false`：明确允许存在逾期余额时提交新借款；提醒独立执行。
- 不配置租户：返回 `UNCONFIGURED`，页面明确说明尚未配置且当前不自动阻断。配置了租户却漏填布尔值时，启动失败。

这是部署配置，不是由借款人提交的字段。现有本人接口 `GET /api/v1/advance-requests/{id}/prechecks/options` 新增 `overduePolicy`，值为 `UNCONFIGURED / ALLOW / BLOCK`。配置修改后重启生效，旧的 READY 预检不会绕过当前规则。

## 业务链路与职责

1. 借款页面调用原预检接口；财务目录给出本次法人的时区，应用服务分页读取本人本法人到期借款，交给 `EmployeeAdvance.overdue` 判断。
2. 正式提交通过 `AdvanceRequestCheckService.readyFailure` 重新读取当前配置和余额。出现逾期返回 HTTP 409 / `ADVANCE_OVERDUE`，借款、申请版本及审批轮次不变。还清后重新预检才可提交。
3. 调度器每次最多取 100 笔候选，按归还日、租户及借款 ID 继续扫描，到末尾后回到首页。候选日期使用合法时区偏移上界，单笔最终判定使用原借款轮次冻结的法人时区。
4. 提醒服务按原申请、借款、余额的顺序加锁，重新计算实际未还余额。站内消息与提醒依据在同一事务中保存；失败全部回滚。

实体负责未还余额和逾期含义；配置、跨聚合读取及消息事务由应用服务负责。日期索引只负责缩小候选范围，不能代替余额判断。预留、资金冻结、凭证冻结及还款复核不会凭空消除欠款。

## 一次性提醒与权限

同一笔借款的归还约定不可变，提醒按租户与借款 ID 唯一。已读、重复扫描、多实例竞争和进程重启均不重发。首次生成前已还清则不生成；生成后保留历史消息及当时依据，后续还款不会把历史通知抹掉。已入队的外部投递仍表示原先已经发生的提醒事实，不代表发送时的实时余额。

`advance_overdue_reminder` 保存借款版本、法人时区、当地日期、当时未还金额、币种及消息编号。站内文案不复制金额或账户，入口指向原借款申请，查看申请仍走现有实时授权。管理员及其他人员不能通过本人消息或预检入口读取申请人的数据。

提醒针对具有可验证原借款申请入口的实际放款。孤立导入余额不会被挂到虚构申请上；启用阻断时，该类余额仍参与本人本法人的逾期检查。现有异步外部通知按用户偏好处理，未配置企业渠道不声称已完成企业投递。

## 数据升级

V102 从 `finance_resource.context_json` 的原约定读取归还日，补到 V101 的 `employee_advance_order`，增加本人到期查询及全局到期扫描索引，并建立提醒证据表。损坏或缺失日期阻断迁移。迁移不修改原余额、资金版本、申请和历史记录；重复启动不会重复迁移。

## 验证范围

最小失败用例先证明：预检通过后新增逾期余额时，原提交仍成功返回 200；原页面仅显示通用错误。修复后验证预检和提交双重检查、部分还款仍阻断、全部还清后允许、配置三态、租户/本人/法人隔离、跨法人当地零点、不同币种、冻结余额及跨 100 笔分页。

提醒验证覆盖原轮次时区、当前未还余额、生成前还清、生成后保留、只通知本人、写入回滚及并发唯一。范围 Java、前端、PostgreSQL、已有数据迁移和实际页面/重启记录见 [F08 验收证据](evidence/advance-overdue-controls-20261003.json)。本地运行使用受控财务服务及独立数据库副本；逾期历史日期夹具的准备与迁移验证分别记录，原数据库不变。

本项不代替全项目发布门禁、原需求逐条盘点或真实企业环境验收。
