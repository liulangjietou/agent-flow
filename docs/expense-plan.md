# 事前申请与批准额度

更新：2026-09-28。本阶段实现后端完整申请链路和本地合成财务 HTTP 验收；专用填报及审批明细页面接续实施，尚未作为浏览器业务链路验收。

事前申请使用独立 `EXPENSE_PLAN` 业务绑定。`ExpensePlan` 保存原币计划和每轮冻结依据，`Application` 拥有审批状态，`ExpenseRequest` 保存实际批准后的可核销行余额。提交和预检均不创建额度；只有最后一个实际人工任务完成且申请变为 APPROVED 后，才在同一事务按冻结本位币行金额创建额度。默认严格控制、容差为零，额度标识与计划标识相同，批准依据保留申请和轮次。

## 调用链与职责

1. 本人调用 `/api/v1/expense-plans` 创建或修订草稿。已发布流程必须符合独立表单契约，普通申请创建/修改/提交入口不能绕过业务绑定。
2. 本人选择当前有效任职和明确财务目标，调用 `/{id}/prechecks` 排队。V41 保存双版本、轮次、尝试序号、租约和不可变任务历史；同一计划只允许一个活动任务。
3. 执行器在数据库事务外通过现有财务 HTTP 端口读取本人目录和法人汇率。计划只查询目录及汇率，不调用账户、发票或预算端口。金额和分摊在领域对象内校验；候选不写回当前计划。
4. `/{id}/submit` 在短事务内重验最新有效检查、任职、双版本和发布版本，冻结本轮计划并启动审批。每条结束路径都必须经过人工审核，所有人工节点必须原样可读计划明细。汇率按法人当地提交日冻结，预检时效不超过五分钟、目录有效期或当地次日零点。
5. `FlowableTaskFacade` 调用计划应用服务，在申请、计划的固定锁顺序下办理任务。最终批准先保存实际申请状态，再生成批准额度。额度或审计写入失败会同时回滚引擎任务、申请状态及轮次结果。

跨聚合授权、版本协调和外部事实查询属于应用服务。计划内容、逐行汇兑、精确分摊和历史约束属于计划领域；批准行余额仍使用已有财务资源模型。没有用 Flowable 变量或客户端标记代替批准事实。

## 权限与恢复

本人仅在草稿、退回、撤回时编辑。退回或撤回后重新查询目录和汇率，提交产生新轮次，原金额与依据不改写。管理员不因此取得敏感明细权限；旧审批人不能读取补正草稿，按明确历史轮次读取时仍校验该轮权限。

未提交草稿作废后本人仍能查看。退回补正后作废，本人看到最后保存的补正内容，旧审批人只能显式选择原提交轮次；不会把旧金额冒充最后草稿。已批准申请不能通过申请人的作废入口撤销额度，额度关闭和后续结算不在本阶段增加新的管理入口。

所有写入使用平台原请求幂等恢复。新预检使旧 READY 结果失效；版本、任职、目标或汇率日期变化同样阻止提交。排队任务可恢复领取；已领取后崩溃只在原租约到期后记超时，不自动重复外发。迟到成功不能覆盖终态。接口只向本人返回候选计划，不返回完整外部目录或错误正文。

V41 扩展业务类型约束并新增计划、计划修订、预检和预检修订表。旧普通申请和报销保持原样，复合外键限制租户、业务类型、归属与预检引用的实际计划版本。不存在自动把旧表单转换为计划的迁移。

## 验证

- 领域模型与契约 17 项通过，覆盖精确金额、汇兑和成本分摊、时间区、历史隔离、人工审核旁路、敏感明细和迟到预检。
- 初轮 H2 范围回归 94 项通过，覆盖计划、原有报销、委派、会签和 OpenAPI；补充作废补正负例后，最终计划/升级/OpenAPI 21 项通过。两批有重叠，不相加。
- PostgreSQL 17.11 同范围计划 15 项、升级 1 项通过，覆盖并发领取、网络等待中修改、两级实际审批、批准额度原子回滚、权限及跨轮次读取。
- OpenAPI 136 个操作、231 个结构、46 个示例校验通过；Java 531 个文件、914 个命名类型的作者与解析检查通过。

最初金额模型测试未经过实际 `FormSchema`，集成测试发现字符串字段类型映射与枚举映射比较导致正常定义被拒绝；改为比较字段键及实际枚举类型，并补充契约测试。作废读取的初始实现假定终态必有可用提交快照，未覆盖未提交作废和补正后作废；两个真实接口回归分别失败后修复当前内容与历史读取分支。

实际 HTTP 使用本机合成目录和汇率，人工审批由真实 Flowable 执行。未声明已接入企业标准、已付款或已完成浏览器验收。机器记录见 [事前申请后端证据](evidence/expense-plan-20260928.json)。接续专用页面、借款发起与实际放款、凭证、结算及归档。
