# 事前申请与批准额度

更新：2026-09-28。后端与专用页面均已完成本地验收，使用实际应用、PostgreSQL、Flowable 和本机合成财务目录。企业接口仍需实际联调。

事前申请使用独立 `EXPENSE_PLAN` 业务绑定。`ExpensePlan` 保存原币计划和每轮冻结依据，`Application` 拥有审批状态，`ExpenseRequest` 保存实际批准后的可核销行余额。提交和预检均不创建额度；只有最后一个实际人工任务完成且申请变为 APPROVED 后，才在同一事务按冻结本位币行金额创建额度。默认严格控制、容差为零，额度标识与计划标识相同，批准依据保留申请和轮次。

## 调用链与职责

1. 本人调用 `/api/v1/expense-plans` 创建或修订草稿。已发布流程必须符合独立表单契约，普通申请创建/修改/提交入口不能绕过业务绑定。
2. 本人选择当前有效任职和明确财务目标，调用 `/{id}/prechecks` 排队。V41 保存双版本、轮次、尝试序号、租约和不可变任务历史；同一计划只允许一个活动任务。
3. 执行器在数据库事务外通过现有财务 HTTP 端口读取本人目录和法人汇率。计划只查询目录及汇率，不调用账户、发票或预算端口。金额和分摊在领域对象内校验；候选不写回当前计划。
4. `/{id}/submit` 在短事务内重验最新有效检查、任职、双版本和发布版本，冻结本轮计划并启动审批。每条结束路径都必须经过人工审核，所有人工节点必须原样可读计划明细。汇率按法人当地提交日冻结，预检时效不超过五分钟、目录有效期或当地次日零点。
5. `FlowableTaskFacade` 调用计划应用服务，在申请、计划的固定锁顺序下办理任务。最终批准先保存实际申请状态，再生成批准额度。额度或审计写入失败会同时回滚引擎任务、申请状态及轮次结果。

跨聚合授权、版本协调和外部事实查询属于应用服务。计划内容、逐行汇兑、精确分摊和历史约束属于计划领域；批准行余额仍使用已有财务资源模型。没有用 Flowable 变量或客户端标记代替批准事实。

## 权限与恢复

本人仅在草稿、退回、撤回时编辑。退回或撤回后重新查询目录和汇率，提交产生新轮次，原金额与依据不改写。管理员不因此取得敏感明细权限；旧审批人不能读取补正草稿，按明确历史轮次读取时仍校验该轮权限。

未提交草稿作废后本人仍能查看。退回补正后作废，本人看到最后保存的补正内容，旧审批人只能显式选择原提交轮次；不会把旧金额冒充最后草稿。已批准申请不能通过申请人的作废入口撤销额度。2026-10-02 已补齐本人手工关闭额度的独立入口：停止新增和增额，保留原批准及已有预留，详见[额度关闭](expense-request-closure.md)。

所有写入使用平台原请求幂等恢复。新预检使旧 READY 结果失效；版本、任职、目标或汇率日期变化同样阻止提交。排队任务可恢复领取；已领取后崩溃只在原租约到期后记超时，不自动重复外发。迟到成功不能覆盖终态。接口只向本人返回候选计划，不返回完整外部目录或错误正文。

V41 扩展业务类型约束并新增计划、计划修订、预检和预检修订表。旧普通申请和报销保持原样，复合外键限制租户、业务类型、归属与预检引用的实际计划版本。不存在自动把旧表单转换为计划的迁移。

## 平台费用类别修订

启用平台费用制度后，计划采用平台启用类别与企业授权目录的交集。预检在查询外部目录前记录类别修订，完成时与读取 READY 时复核；首次启用管理或修改生效类别后，旧检查不可提交，返回 `EXPENSE_CATEGORY_CONFIGURATION_CHANGED`。页面提示刷新目录并重新检查。

正式提交与类别修改共用租户配置头锁，并持有至计划轮次和审批事务完成。类别修改先完成时，提交返回 409，计划、审批和额度均不产生半成品。已经提交的轮次仍按原类别依据审批，不随后续停用而改写。

`ExpensePlanRound.managedCategoryRevision` 保存实际采用的类别修订，预检候选和历史明细展示该值。未启用管理及旧快照中缺少字段时保持为空，不给旧数据补造版本，也不新增表迁移。计划没有执行报销金额制度判定，因此只编辑制度草稿或仅发布金额制度、类别修订未变时，计划检查仍可用；报销继续按自己的完整制度选择复核。

## 页面与实际业务验收

费用工作区新增「我的事前申请」。本人从已发布流程选版，填写原币计划、成本分摊后保存，再显式选择任职、查询财务依据及确认正式提交。申请记录中支持双版本补正、说明确认后撤回或作废；通用申请编辑入口不处理业务绑定表单。审批待办、申请详情和明确选择的历史轮次均读取计划专用授权接口，403 时只展示原字段投影。

页面暂存仅留在按身份隔离的内存中。读取有超时与代际隔离，换账号、换轮次或修改保存版本时清空旧结果。金额以十进制字符串保存和整数分校验，浏览器只合计服务端冻结金额。未知写入响应沿用平台原请求和原幂等键恢复，不自动换版本重发。

实际浏览器在隔离库完成：创建 UI-PLAN-001，100.00 元第一轮提交后撤回，补正为 120.00 元后提交第二轮；历史页仍显示第一轮 100.00 元。主管从实际待办查看明细并批准，只有此时生成 120.00 元额度。申请人随后通过报销资源选择器引用该计划行，提交 100.00 元实际报销后，台账显示预留 100.00 元、可用 20.00 元、已使用 0.00 元。后续付款与核销尚未发生。

实际 HTTP 在批准前后核对额度，并确认无关人员返回 404、无敏感明细授权的管理员返回 403。计划预检阶段的合成财务调用只有目录和汇率。后续报销查询账户、制度和预算，属于独立报销链路。

页面专项 21 项测试及报销、附件和原请求恢复范围共 95 项通过；两者为包含关系。类型检查和生产构建通过，保留现有大包提醒。桌面和窄屏详情检查通过，首次请求沿用了较早测试会话，重新登录后正常。页面证据见 [本地页面验收记录](evidence/expense-plan-ui-20260928.json)。
