# 报销核销与零应付结算

更新：2026-09-28。V48 独立结算账本已接通真实审批、挂账、付款、发票和余额资源、预算消费，以及财务状态和重试页面。`SETTLED` 仅表示本地资源和预算实际占用完成；付款凭证、归档、人工争议裁决仍继续实施。

## 来源与职责

`PaymentOperationService` 保存真实成功回执时，同步登记原报销的结算意图。登记读取原付款授权、命令、挂账、冻结轮次和双版本，不接受客户端金额或成功声明。银行已经到账而当前审批后来撤销时，仍保留原到账依据，当前来源守卫会阻止后续资源消费。

全额借款冲销不制造零额付款：真实挂账确认后直接登记核销。核定总额为零时，凭准备服务在实际批准、纸件和预算守卫后保存的 `NOT_REQUIRED/ZERO_AMOUNT` 进入相同核销流程，不生成零额凭证。普通正额挂账不会提前启动结算。

`ExpenseSettlement` 拥有生命周期、资金依据、原业务绑定和不可回退的资源消费标记；`ExpenseSettlementResources` 在副本上生成精确资源计划；应用服务负责跨聚合读取、锁、事务及预算命令登记。Flowable 仍只推进审批流程。

## 本地事务与预算确认

独立后台先锁申请和报销，再按资源类型及标识稳定排序加锁，锁后重读原发票、事前额度和借款预留。只核销本轮仍有正额的核定行，已经核减释放的引用不会被再次消费。每个预留须与原报销、轮次、行和核定金额完全相符。

发票占用自身会增加版本，结算可沿用占用前的成功验票；其后任何新查验若未成功，则不能用更旧成功记录绕过。消费时还检查验票有效期。争议借款不能继续核销，申请人仍可重新查验本人发票，处理后由有权限的财务明确重试。

发票、额度、借款消费，预算 `CONSUME` 命令及结算修订在同一短事务提交。最后一笔版本冲突、审计修订失败或预算登记失败，整批回滚。银行回执与消费属于独立事务，因此本地资源失败不会将已确认银行付款改成未知。

预算排队显示 `BUDGET_PENDING`，实际成功后才成为 `SETTLED`。明确拒绝显示 `BUDGET_REJECTED`；财务重试只重新登记预算消费，永久保留 `resourcesConsumed=true`。未知结果继续由原预算操作查询恢复，界面没有换号重试入口。银行退回、资金冲突、挂账冲回或冲突将原结算标记为 `REVIEW_REQUIRED`，不恢复已用资源，迟到预算成功不解除争议。

恢复扫描以有界游标轮转读取未登账的成功付款、已过账凭证及零额准备；某些正额凭证尚未付款，不会长期挡住后面的零应付记录。恢复只使用持久来源，不请求银行、不重新付款。

## 入口和操作边界

- `GET /api/v1/expense-reports/{id}/settlement?roundNo=1`：原轮次完整财务字段权限，显式返回尚未登记的 null，响应禁止缓存。
- `POST /api/v1/expense-reports/{id}/settlement/retry`：FINANCE、非申请人、当前法人有效任职，原轮次字段可读；审批、财务和结算三个版本一致；必填人工说明。客户端不能传金额、账户或消费结果。
- 人工重试与审计、幂等回执同事务，回放前仍复核当前权限。管理员和出纳不会由角色取得报销敏感字段旁路。
- 页面独立显示结算依据、资源核销和预算实际占用，切换身份或轮次立即清空旧状态。未知写入恢复原幂等请求，恢复后须重新读取才能继续操作。

后台由 `agentflow.expenses.settlement-worker-enabled` 控制，默认开启，`agentflow.expenses.settlement-poll-delay-ms` 默认 1000。它只进行本地事务，预算外发由原预算执行器处理，停止调度不会删除队列。

旧回归只确认银行成功，遗漏核销登记。新增实际审批到付款用例先得到“期望一条、实际零条”的失败，再接入登记消费者。最终 H2 范围 59 项（领域 17、服务端 42）、PostgreSQL 80 项、前端 54 项通过；范围重叠，不相加为独立总数。数据库故障注入的错误日志属于预期回滚验证。前端生产构建、OpenAPI 158 操作 / 274 schema / 52 示例、645 Java 文件 / 1151 命名类型检查通过。

隔离 PostgreSQL 从 V47 升级到 V48。浏览器办理 `UI-SETTLEMENT-237293c4`：100 元费用由已到账借款全额冲销，预算第一次因期间关闭被明确拒绝；财务填理由重试后实际占用成功。结算账本一份、修订六条，预算冻结一笔、消费两笔，发票消费和借款消费各一条，付款授权零份，重试审计一条。重试前后发票和借款版本完全相同，借款已冲销 100 元、可用 200 元。准备阶段保留 29 次 HTTP 检查，完成后另有 13 次；桌面和实际 480 CSS 像素窄屏验证通过，无横向溢出。
