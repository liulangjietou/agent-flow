# 票据抽取与本人确认

2026-10-02：领域、图片／XML 模型适配、已识别 XML 的本地优先路径、PDF 原件输入、V100 持久后台和本人五个 API 已完成各阶段范围测试。票夹页面现已接通来源预览、逐字段复核、原请求恢复和私有会话草稿；83 项前端范围、105 份实际响应契约、独立 V99→V100 升级及一次实际进程重启通过，见[页面与运行证据](evidence/invoice-extraction-ui-20261002.json)。报销确认结果辅助填报现也完成本地验收，见[填报证据](evidence/expense-invoice-fill-20261002.json)。真实页面使用合成 XML；模型外发与识别质量、OFD 完整渲染及其余完整生命周期仍待验收或开发，票据抽取继续属于剩余工作。

验收基线包含原产品目标，以及费用报销领域设计 `doc/05-费用报销领域设计.md` §4.1、§16：XML 结构化解析优先，识别结果带置信度和证据位置，必须由申请人确认。当前本地路径支持经原件示例核对的 EInvoice 0.31 无命名空间结构，未知结构保留单独授权模型处理的能力，不宣称支持所有电子发票 XML。

## 职责与调用链

个人票夹的 `InvoiceWallet → InvoiceDetail → InvoiceExtraction` 页面经 `api.ts` 调用五个本人接口。接口先核对同租户、同本人及原件 READY 状态，再调用 Agent 协作域的独立抽取用例。内容适配器经 `InvoiceOriginalFiles` 读取并校验完整原件；`InvoiceExtractionEngine` 统一复核本人原件及创建时固定的执行方式，已识别结构直接返回本地候选，否则才允许与固定模型目的地相符的执行。`InvoiceExtractionRun` 保存原件身份、摘要、实际页数、执行方式、结果契约、生产者版本、可选模型目的地及本人的人工修订。

这段状态逻辑放在 Agent 协作域，因为它描述建议的生产和复核；原件归属、上传完整性与正式税务查验继续分别属于票夹和发票领域。`CONFIRMED` 仅表示本人确认了选中的候选值。应用服务独立持久化该记录，不调用 `Invoice.verified`，也不授予批准、核销或付款权限。

## 已实现的领域约束

- 固定发票 ID、原件 ID、SHA-256、格式、字节数和实际页数；最多 10 页，原始字节沿用票夹 20 MiB 上限。页数必须由内容适配器读取，不能采用客户端或模型自报页数。
- 11 个封闭字段：票号、代码、开票日期、买卖方名称和税号、币种、不含税金额、税额与价税合计。缺少依据的字段省略，空结果如实表示未识别。
- 票号保留前导零，金额使用字符串保留精度与红字负号；不会为使算术相符而修改票面候选值。金额、日期和币种的格式检查不证明票据真实。
- 每项建议绑定原件及真实页码，最多 4 份摘录、每份 512 字符。结构化 XML 还保存唯一元素的完整路径，模型不能提供或冒充该位置；模型摘录仍属于其声称的依据。两者都须本人对照原件。
- 每项候选保留 LOW／MEDIUM／HIGH 置信度。MODEL 使用模型自评；STRUCTURED_XML 的 HIGH 仅表示直接读取已识别的明确字段。均不能展示成实测准确率或真实性保证；缺失或超出枚举的值拒绝。
- 本人明确选择并可编辑部分建议；提取原值与人工值分别保存。其他人、管理员、重复目标、额外目标或已变更来源不能确认。
- 运行创建时固定 STRUCTURED_XML 或 MODEL；本地方式必须没有模型目的地，模型方式必须绑定目的地指纹，结果不能更换方式。本地失败或未知 XML 不自动外发。
- 排队、运行、完成、失败、确认、放弃按版本单次推进；超时或终态后的晚到结果不能重新启动。重建持久状态必须通过合法动作校验。

## 已确认票面辅助填报

费用编辑器的 `ExpenseEditor → ExpenseInvoiceAssist → invoiceFillChoices/fillExpenseLineFromInvoice` 通过已有本人票夹、提取历史和详情接口读取确认结果。这里只更新前端未保存输入，因此映射逻辑放在费用填报模块；实际保存仍经过原 `expenseContent → createExpense/reviseExpense → ExpenseDraftService`。没有增加后台写入入口或数据库迁移，确认运行仍独立保存，费用单不新增提取来源关联。

本人先选择目标费用行、原件和已确认记录，再逐项勾选含税金额或币种。未确认、已放弃和已变更原件不能使用，带入前重新读取并核对本人权限、完整原件身份、运行版本及人工确认值。等待期间禁止保存、预检和离开；账号、单据或法人切换清除来源，费用行变化、读取超时和迟到结果均不能覆盖新输入。读取被拒绝会清除私有票面与列表。

只映射两个语义相同的字段。开票日期不能推导费用发生日期，票面税额不能推导可抵扣税额；这些信息供人工对照。金额按字符串保留精度，红字、零值和超出费用金额上限的值不可直接带入。未确认币种时须本人确认原币单位；改变币种时也须确认整行税额和分摊的单位，金额数字不换算。带入不修改分摊金额，保存仍校验分摊合计、税额等原有约束。此操作不查验或引用发票、不保存或提交费用，也不重新请求模型。

57 项前端范围测试和构建通过，其中 15 项覆盖辅助填报，费用编辑器新增一项覆盖复核互斥与普通保存。真实页面从已确认的 105.50 带入费用行，保留原始提取值 106.00、费用日期和 0.00 可抵扣税额；分摊仍为 100.00 时保存被阻止，人工改为 105.50 后仅产生一次草稿创建。38 份实际响应通过契约，浏览器 31 份且捕获缺口为零；500 CSS 像素下来源栏纵向排列且无横向溢出。独立 V100 副本一次重启保持 232 张表、4,064 行与六份文件，票据仍待查验且可用，85 张票据及财务相关表未改，原 V100 服务与数据保持。仅使用本地合成目录，未连接真实企业财务或模型；[完整验收证据](evidence/expense-invoice-fill-20261002.json)保留这些边界。

## 持久后台与执行边界

V100 新增抽取运行和追加状态轨迹。原件归属采用租户、发票、本人、原件 ID 与 SHA-256 复合外键；同一发票最多一个排队或运行任务，结束后释放活动名额，历史建议和人工修订仍保留。状态版本、租约及活动键在同一语句更新，状态轨迹与更新同事务提交；轨迹失败时整笔回滚。数据库索引时间截断至微秒，冻结上下文保留原时间，避免 PostgreSQL 与 H2 的时间精度差异导致记录无法恢复。

`InvoiceExtractionService.prepare` 在数据库事务外读取并核验实际原件，返回不能由请求构造的服务端准备对象。排队时按组织目录、原件、运行的顺序加锁，复核本人有效资格、原件信息和明确选择的方式。模型方式必须匹配当前目的地指纹，本地 XML 不能携带模型目的地。已初始化租户采用本地人员启停，演示租户采用实际账号目录；普通员工和出纳无需拥有审批资格，管理员也不能代看或确认他人的票据建议。

工作器每批最多十项。领取形成固定租约，来源检查和模型等待均在数据库事务外执行；发送前再次检查本人资格和原件。锁等待后重新读取时间，过期运行只结算失败，迟到结果不能覆盖。未知执行异常保留原租约，下一次轮询不会重新执行该运行；过期后记为失败，需要本人明确创建另一项运行。失败分类为模型不可用、执行超时、结果无效和输入不可用；本地 XML 的失败不会被标成曾经调用模型。

抽取采用独立单线程调度，可通过 `AGENTFLOW_INVOICE_EXTRACTION_WORKER_ENABLED=false` 关闭，默认启用。模型关闭不影响本地 XML，也不阻止已有模型任务结算为不可用。本人确认只保存所选候选及人工修改；票面、税务查验、发票占用和申请数据均不由该服务写入。

公开 API、幂等回执与恢复、最小审计和票夹页面已接通。本地 XML 的存量验收库升级与终态进程重启已实际验证；模型执行中重启及 OFD 不在票夹页面验收结论内；后续填报的独立验收见上节。

## 本人接口与原请求恢复

| 接口 | 行为 |
| --- | --- |
| `GET /api/v1/invoices/{id}/extraction-runs/input` | 在事务外读取原件，返回实际方式、页数、模型目的地及外发范围，不创建任务或发送文件 |
| `POST /api/v1/invoices/{id}/extraction-runs` | 明确选择本地或模型方式后排队，返回 202 和最小回执 |
| `GET /api/v1/invoices/{id}/extraction-runs` | 本人历史分页，默认 20 条、最多 50 条；索引不含票面、摘录或人工值 |
| `GET /api/v1/invoices/{id}/extraction-runs/{runId}` | 本人查看原始候选、依据与人工确认，管理员不能代读 |
| `POST /api/v1/invoices/{id}/extraction-runs/{runId}/review` | 按运行版本确认选中值或放弃，不修改原件、发票查验、占用或申请 |

创建请求携带 `expectedOriginalId`、`expectedOriginalDigest`、`method`、可空的 `targetDigest` 和必填的 `externalSendConfirmed`。方式必须与本地解析相符，不能强制把已识别 XML 改成模型方式。`MODEL` 必须明确确认外发并匹配刚展示的目的地指纹；`STRUCTURED_XML` 必须关闭外发且没有目的地。接口不接受租户、归属人、模型地址、凭据或客户端页数。

来源预览中的 `transmission` 分三种：`NONE` 不外发；`XML_TEXT` 发送完整 XML 正文、元素名和属性；`ORIGINAL_BYTES` 发送完整图片或 PDF 原始字节，包含内部元数据和内嵌内容。页面据此显示发送范围，默认不勾选模型外发。所有成功响应为 `no-store`。除历史分页的 `page/pageSize` 外，不接受查询参数；重复查询参数、额外请求字段、数字类型票面值会被拒绝。外发确认只接受 JSON 字面布尔值；运行版本只接受整数，文本或小数不能自动转换成授权或当前版本。

两种写操作都要求 `Idempotency-Key`，绑定原账号、角色、方法、路径、查询及原始正文。成功回执只含运行编号、当时状态和版本。恢复成功回执不重新读取原件，不重新排队；需要查看当前内容时仍经过本人的当前权限核对。准备发生在数据库事务外，准备完成后在原幂等写事务内再次争用同一键；并发准备只有一方产生业务效果。准备期间原件不可用，但另一相同请求已经成功时，恢复该成功回执。没有成功记录的准备失败不会留下已成功回执。

排队、确认和放弃与 `InvoiceExtractionRun` 最小操作审计同事务保存，动作分别为 `INVOICE_EXTRACTION_QUEUE`、`INVOICE_EXTRACTION_CONFIRM`、`INVOICE_EXTRACTION_DISMISS`。审计仅记录运行及发票标识、方式和状态，票面、证据摘录及人工意见留在本人受限入口；自动执行阶段仅追加自身轨迹，不冒充本人操作。管理员审计检索和导出可按该来源及三种动作筛选。没有新增迁移，也不补造旧运行的历史排队审计。

## 票夹页面与私有复核

页面先读取真实原件、处理方式、页数与目的地。已识别 XML 直接开放本地提取；模型方式要求本次明确勾选，重新读取来源、提取请求失败或切换账号都会取消勾选。未启用的模型只展示说明，不发送原件。前端校验来源与回执身份；它只控制展示和交互，所有归属、版本和财务约束仍由服务端执行。

原始候选与本人值分列展示，窄屏上下排列。首次读取不自动选择任何字段，票号和金额始终按字符串编辑；仅提交明确勾选的字段。摘录和 XML 元素路径以普通文本显示。模型自评与结构化映射的把握说明分别展示，不当作准确率。确认、放弃都不会触发发票查验或财务写入。

未发送修订按账号和票据隔离，仅留在内存，离开业务页面再返回可接续；刷新或关闭浏览器会丢失，会触发离页提醒。存在未保存修订时禁止切换记录和查验，明确清除后才恢复。刷新发现服务端版本变化时保留本地修订并禁止旧版本提交；恢复成功回执只清除仍匹配原版本与原正文的草稿。

读取分别有 12 秒超时和序号，身份失效清除显示，迟到响应不能回填。两种写入有 25 秒等待期限；超时或回执损坏保留原请求，继续由全局恢复入口重放相同账号、键和正文，不能据此另建任务。恢复后打开原运行并清除旧写入提示，新读取错误独立显示。

本阶段先复现入口缺失、全局 `header` 样式导致标题重叠，以及恢复成功后仍显示旧错误。前两处分别以入口测试、实际截图和元素位置验证；第三处新增失败用例后修复。前端 83 项通过，包含新面板 23 项及票夹、草稿助手、共享请求回归；构建仍有既有大包提示。真实页面保存两项人工修订并保留原候选，发起和放弃均模拟成功回执丢失后原键恢复。并发同键只产生一次效果，管理员和其他本人均不能代读。

独立 V99 副本升级保留 230 张原表的 4,019 行和三份文件，V100 增加两张表。合成用例完成后，一次重启保持 232 张表的 4,059 行及六份文件完全一致；重新登录后页面仍可读取原值、人工值及放弃记录。演示认证令牌本就在进程内，旧会话重启后收到 401，页面清除正文后由原账号重新登录。累计 105 份实际响应符合契约，其中 63 份来自浏览器，捕获缺口为零；不计故意丢弃的响应为已送达。初次夹具对可省略空字段的判断错误已记录并按原票据编号接续，没有重复上传。原 V99 数据与服务保持，未调用外部模型。

## 当前内容适配范围

| 原件 | 当前实现 | 边界 |
| --- | --- | --- |
| PNG、JPEG | 原始图片字节通过内联 data URL 发送；解码前检查尺寸，随后检查可读性 | 单边最多 12,000 像素、总计最多 2,000 万像素；没有外部图片 URL |
| EInvoice 0.31 XML | 本地按根、版本、无命名空间和完整唯一元素路径提取；不调用模型 | 9 种已核对字段；未知／缺失币种、代码不推测，原件和数字签名原文保持；结构识别不等于验签或税务查验 |
| 其他 XML 的模型兜底 | 遵循原声明编码读取正文、元素名和属性，再作为纯文本准备 | 只有单独冻结为 MODEL 的任务可以外发；文本最多 64 KiB UTF-8，超限失败；模型摘录必须存在于发送文本 |
| PDF | 独立 JVM 检查实际页树后，以内联 `file_data` 发送完整原始 PDF | 1–10 页；加密、畸形页树、伪造页数或解析超限时失败；不截取部分页发送 |
| OFD | 预检、基础页面、基本描边／颜色、复合裁剪和模板合成已实现；完整渲染和隔离进程仍待接续 | 仍不在当前适配器能力清单中，不能当作文本、图片或原生 PDF 文件静默发送 |

本地 XML 映射依据为 [TooMaker 公开原件示例](https://toomaker.com/guide/fms/invoice/)，只覆盖该示例明确的 0.31 结构；它不是完整税局 schema 的证明。票号与日期读取 `TaxSupervisionInfo/InvoiceNumber` 和 `IssueTime`，不采用 `Header/EIid` 或申请时间。购销双方读取各自 Information 分组；金额读取 `BasicInformation` 的三项合计，不汇总明细或修改算术差异。财政部[电子凭证会计数据标准公开包](https://kjs.mof.gov.cn/zt/kuaijixinxihuajianshe/dzpzkjsjbzshsd/sjbz/202505/t20250519_3964020.htm)中的入账 XBRL 与发票原始 XML 是不同结构，本次未将该 XBRL 声称为受支持的原件格式。

XML 共用一次有界 SAX 读取：深度最多 64、元素最多 100,000、单元素属性最多 64。DTD、外部实体、schema 和 XInclude 外部访问均禁用，不执行数字签名引用。重复标量、重复关键分组、关键路径上的外来命名空间、标量中的子元素和无法表达的候选值直接失败，不能静默挑选一个值。本地路径不受模型文本 64 KiB 限制，仍受原件 20 MiB 与结构限制；模型文本按完整 UTF-8 字节数计量，不截断后发送。

PDF 采用 PDFBox 3.0.8 严格解析，并自行遍历唯一页树叶子，核对父子关系、类型及每层实际页数，不只相信文件自报的 `Count`。页树深度最多 16、节点最多 128；每页继承的 MediaBox 必须是四个有限数值，宽高大于零且不超过 3,000 点。这是页树和 MediaBox 检查，不代表所有页面内容已经渲染成功、文档符合完整 PDF 标准或数字签名有效。

PDF 检查由专用子进程执行，父服务不加载不可信 PDF 对象。单进程槽限制并发，子进程堆上限 256 MiB、直接内存上限 64 MiB、元空间上限 128 MiB、线程栈 512 KiB，执行最多 15 秒。超时或中断后终止本次子进程并清理私有目录；进程不能停止时保留占位，防止继续累积。子进程不继承模型或数据库环境变量，只返回固定八字节页数结果；不渲染、不执行文档动作或读取外部附件。上述措施是 JVM 资源与生命周期限制，不是操作系统权限沙箱，也不声称约束全部本机内存。处理不可信文件的资源限制依据见 [PDFBox 安全说明](https://pdfbox.apache.org/security.html)。

OFD 预检分为两个职责：`InvoiceOfdArchive` 完整读取 ZIP 中央目录定义的文件、核对实际解压长度与 CRC，并生成只包含普通文件的新目录；`InvoiceOfdDocument` 检查 XML、包内文档与有序页清单。原始包仍保留，生成目录不恢复 ZIP 的文件类型和权限，也不合并已有目录。包最多 1,024 项，每个文件最多 8 MiB，累计解压最多 64 MiB；原始包仍受 20 MiB 限制。路径长度最多 512、层级最多 32；拒绝目录逃逸、重复项、文件与目录冲突，以及在常见文件系统上可能冲突的大小写／Unicode 别名。

预检读取全部 `.xml` 文件和已识别为 XML 引用的其他文件：单份最多 2 MiB、总计最多 8 MiB，累计元素最多 100,000、深度最多 64、单元素属性最多 64。DTD、外部实体、schema 与 XInclude 外部访问均禁用；定位依据使用包内路径，不读取宿主路径或下载资源。入口支持当前核对的 OFD 1.0／1.1、`http://www.ofdspec.org/2016` 命名空间；按全部 DocBody 与 Pages 的原始顺序检查 1–10 页，保存文档路径、页面路径和实际 PhysicalBox。宽高必须大于零且不超过 1,000 毫米。引用区分大小写，规则依据见上游 [ST_Loc 定义](https://github.com/ofdrw/ofdrw/blob/2.4.0/ofdrw-core/src/main/java/org/ofdrw/core/basicType/ST_Loc.java)。资源基目录可以没有实体目录项，但被引用的文件必须实际存在；引用按父节点与元素名识别，不能把 `Signatures` 等同名文档根节点当作路径。

此预检尚未接入公开请求；OFD 请求仍在内容适配入口明确拒绝。后续还须实现独立处理进程、字体／图像解码、模板和图元完整性、嵌套印章内容、全页渲染与模型输入。当前候选库 OFDRW 2.4.0 的 [转换模块依赖](https://github.com/ofdrw/ofdrw/blob/2.4.0/ofdrw-converter/pom.xml)、[字体初始化](https://github.com/ofdrw/ofdrw/blob/2.4.0/ofdrw-converter/src/main/java/org/ofdrw/converter/FontLoader.java)及[局部渲染错误处理](https://github.com/ofdrw/ofdrw/blob/2.4.0/ofdrw-converter/src/main/java/org/ofdrw/converter/AWTMaker.java)仍需解决，尚未添加该依赖。预检不证明页面已完整渲染、数字签名有效或发票真实。

2026-10-02 的独立渲染实验将依赖疑点落实为可复现结果：原 converter 二进制搭配 PDFBox／FontBox 3.0.8 时，两个公开样本均因缺少 `SeparableBlendMode` 退出。只排除 iText 也不足以接入，字体初始化和 `CommonUtil` 的 PDF 颜色方法签名仍会触发类加载。实验在临时目录、独立命名空间中改编三份上游源文件，保留现有 PDFBox 版本，移除图片路径不需要的 PDF 字体导出及工具类调用；这不是应用依赖或生产实现的变更。

初次实验能输出五页图片，但视觉检查发现中文缺失。默认字体实际为 `Trattatello`，对“中文金额税0123456789”的字形检查有五字缺失；仅改用支持 TTC 的加载方式仍失败。显式指定本机 `STHeiti Light.ttc` 后，该检查通过，实际选中的是 `STHeitiTC-Light`；五页重新输出，检查的前两页恢复了中文票面和明细文字。字体文件没有复制进项目，也没有外发或分发；最终部署仍须明确字体及具体字体面，不能依赖本机扫描结果。

### OFD 基本样式与复合裁剪接续

`InvoiceOfdStyle` 按属性合并图层 `DrawParam`、`Relative` 引用链和图元显式值，保留文字黑色填充／透明描边、路径透明填充／黑色描边的默认区别。支持三种线帽和连接方式、虚线及正负偏移；OFD `MiterLimit` 是物理长度，传给 [Java BasicStroke](https://docs.oracle.com/en/java/javase/17/docs/api/java.desktop/java/awt/BasicStroke.html) 前转换为线宽比。等比变换下零线宽为一个设备像素，正线宽至少两个设备像素；非等比变换中无需补足设备最小值的描边已支持，需要逐段补足的情况仍明确拒绝。

`InvoiceOfdColors` 处理默认颜色空间、GRAY／RGB／CMYK、1／2／4／8／16 位通道、十进制／十六进制值、调色板、透明度以及包内 ICC 配置；显式 `Value` 优先于 `Index`。沿用现有 PDFBox 的 CMYK 转换，没有添加新的运行依赖。配置文件仍按所属资源表的包内路径读取；单份最多 1 MiB、每页最多实际加载 32 份且累计不超过 8 MiB，同一文件经不同颜色空间重复加载也计入预算。

`InvoiceOfdClips` 复用页面的路径与文字解析：同一 `Clip` 内的 `Area` 求并集，不同 `Clip` 求交集，保留各自的绘制参数、Boundary、CTM 和嵌套顺序。`TransFlag` 采用已核对的[上游扩展含义](https://github.com/ofdrw/ofdrw/blob/2.4.0/ofdrw-core/src/main/java/org/ofdrw/core/pageDescription/clips/Clips.java)：缺省为 false，true 时裁剪随图元自身 CTM 变换；这不代表已经支持 OFD 1.2 文档入口。裁剪在整次调用中最多 256 个 Area、嵌套 8 层、单几何 20,000 段；布尔操作前累计核算输入规模，预算为 4,000,000。虚线展开同样在调用 Java 绘制前限制为 25,000 次转换。

### OFD 模板页接续

`InvoiceOfdDocument` 在原有 XML 预检内解析每个文档的模板目录与每页引用，保留重复引用和引用顺序。页面显式 `ZOrder` 覆盖模板声明的默认类型，省略时沿用声明值，最终缺省为 Background。模板文件仍从所属文档的包内目录定位；重复定义、缺件、未知引用和非法类型使整份失败。模板内部的 `Template` 节点按 GB/T 33190—2016 §7.7 表 12 不再展开。

绘制顺序按同节图 16：背景模板 → 背景图层 → 正文模板 → 正文图层 → 前景模板 → 前景图层。同一类型内保持引用或图层原顺序；模板内部仍保留自身图层次序。页面物理区域采用正文页 → 模板页 → CommonData 的来源顺序；在已核对条款未明确给出多模板冲突尺寸优先级的情况下，当前要求正文页显式给出区域，否则拒绝，避免任意选择尺寸裁掉内容。这是当前输入边界，不作为完整兼容性结论。

`InvoiceOfdResources.Scopes` 为同一输出页缓存正文与各模板的资源作用域：共用文档资源，分别读取各自 `PageRes`，字体和图片路径仍相对资源文件定位，不混用正文或其他模板的私有资源。所有作用域共用原来的 ICC 加载预算，输出页结束统一释放字体。每个文档最多 64 个模板定义、每页最多 64 次模板引用；整次渲染最多展开 20,000 个图层，空图层也计入，原图元、几何、像素和文件包预算保持。

模板新增 16 项测试；另将图层可省略 ID 的规范情形单独复现后修正。原用例始终提供 ID，因而未覆盖该场景。当前共 88 项 OFD 范围测试通过，包含前一阶段 71 项，不累计为独立测试数量。两页合成输出已实际查看，尺寸分别为 227×114、171×86；四份原始公开样本仍全部通过预检，五页样本解析出 5 次模板引用，但完整渲染通过数仍为 0。未接通公开入口、模型或隔离进程，详见[模板页证据](evidence/invoice-ofd-templates-20261002.json)。

图片请求采用 Chat Completions 的 `image_url` 内联图片格式，协议依据为 [OpenAI 图片输入文档](https://developers.openai.com/api/docs/guides/images-vision)。PDF 使用 [OpenAI 文件输入文档](https://developers.openai.com/api/docs/guides/file-inputs)中的内联文件格式；XML 内容以文本块处理，不能据此认为模型文件接口原生支持 XML 或 OFD。最终配置的模型仍需实际图片／PDF 能力与质量验收。

模型只接收原件引用和白名单字段，不发送归属人、租户、原文件名或文件系统路径作为请求元数据；PDF 请求使用固定名 `invoice.pdf`。图片与 PDF 的全部原始字节会外发，包括原件内部元数据及 PDF 内嵌内容。固定文件名不能消除原件内部的个人信息，公开接口和页面已提供实际发送范围并要求明确确认，默认不勾选。模型只能返回封闭候选结构，额外动作、未知字段、数值类型票号、伪造原件、不存在页码和 XML 虚假摘录均拒绝。

1. 接续 OFD 独立进程和完整渲染，解决实际依赖、字体、嵌套印章及局部错误被忽略的边界，再将有序全部页面接入模型。现有文件包和页清单预检作为该进程的输入检查。XML 新结构只有取得对应接口或原件依据后才增加明确映射，未知格式继续按现有显式授权边界处理。
