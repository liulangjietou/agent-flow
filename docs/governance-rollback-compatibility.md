# V25 治理版本回退兼容性验证

2026-09-26，在合成 PostgreSQL 数据库的独立恢复副本上完成候选版本 → 旧版本 → 候选版本验证。结论：**数据结构能够被演示模式的旧程序读取，但旧程序不执行流程停用守卫，不能以健康检查通过作为安全回退依据。** 生产使用的严格结构校验会拒绝旧发布包连接 V25；本次没有启动生产身份链路。

本记录补充未发布治理分支的部署边界，不代表该分支已提交、合并或部署。旧申请重提策略、实际 SLA 和完整浏览器模板导入仍未完成。

## 版本与隔离范围

- 旧发布包：主线业务版本 `d65b625`，包含业务迁移至 V24。
- 候选发布包：基于 `60bafa0` 的未提交治理与期限配置整合，包含未发布 V25。
- 两个 jar 的完整 SHA-256 和备份 SHA-256 记录在 [结构化证据](./evidence/governance-rollback-20260926.json)。
- 仅使用原合成验收库的备份恢复副本，HTTP / PostgreSQL 分别绑定本机 18197 / 18657；没有向主演示 8180 写入。
- HTTP 业务探针使用 default profile 和 demo auth；严格结构检查独立执行 `--schema=validate`。

| 停用前草稿首次提交 | 409 / DEFINITION_DISABLED | 200 / IN_APPROVAL | 尚未提交的原草稿仍返回 409 |

旧程序已经启动的流程在恢复候选后仍为 `IN_APPROVAL`。重新启用守卫不会撤销这次启动，不能将重新升级当作业务补偿。

## 根因与测试边界

候选版本在 `ApprovalApplicationFacade.create` 锁定定义并检查 `requireStartEnabled`，首次提交在 `FlowableProcessRuntimeAdapter.start` 检查实际绑定版本。旧程序没有这些逻辑，演示模式的自动迁移允许读取未来 V25，因此能够启动并接受原本应拒绝的请求。

现有 `DefinitionAvailabilityIntegrationTest` 覆盖候选程序的新建和首次提交守卫，未切换到旧发布包执行同一业务请求；此前结构升级验证也不能证明旧程序仍执行新增业务约束。本次通过独立副本和真实 HTTP 请求补齐这一验证边界，没有将待确认的退回/撤回重提规则当作缺陷。

严格命令的实测结果不同：旧发布包返回 `FlywayValidateException`，候选通过。源码 `ProductionSchemaConfiguration` 复用 `DatabaseSchemaLifecycle` 的严格校验，拒绝未知未来迁移。因此，本记录不声称 prod 可以绕过检查启动，也不将演示模式结果称为生产认证或授权漏洞。

## 数据保持与后续部署约束

备份恢复 → 候选启动、候选停机 → 旧版启动、旧版停机 → 候选启动，三个边界各比较 68 张表，行数与整表内容哈希完全一致，完整 Flyway 历史保持。停用标记与治理记录保持。旧程序主动业务探针造成的 16 张表变化单独记录，不计为启动丢失数据。严格校验前后 68 张表也保持一致。

后续发布不得将“在 V25 原库上换回旧 jar 并恢复业务入口”列为安全回退方式。生产继续遵循 [停机升级与隔离恢复规则](./production-database-lifecycle.md)：维护窗口中保留当前库，恢复与目标发布包匹配的备份到隔离库，完成严格校验和业务核对后再决定切换；不得关闭严格校验或改迁移历史。备份之后的业务写入不能假定自动迁回，切换前需要明确处理。
