# 费用提交预检

预检已接入真实财务端口、个人票夹、当前任职和资源版本。它只持久保存检查输入及结果，不改变申请状态、不冻结报销轮次、不占用发票、不预留额度、不冻结预算。`READY` 是有时效的提交候选，正式提交仍须在本地事务内复核；完整提交与预算冻结是后续独立步骤。

## 调用链和职责

申请人 → 预检 API → 短事务登记任务 → 独立后台线程 → 主数据/账户/汇率/制度/验票凭据/预算只读检查 → 短事务复核并保存结果。

申请聚合决定下一次提交轮次：草稿预编号为第一轮，退回或撤回后才递增。报销聚合负责金额、税额、分摊与轮次候选冻结；`ExpenseSubmissionResources` 在副本上计算资源预留与重提迁移。应用服务负责真实任职、本人权限、跨聚合版本和外部调用，不在数据库事务中等待文件或 HTTP。

同一报销单只能有一个活动任务。每次明确的新请求分配递增检查序号，不能用随机 UUID 或时间戳猜测最近结果。新任务一经登记，旧 READY 结果立即只供历史查看；新任务失败时也不回退复用旧结论。

## API

所有路径前缀为 `/api/v1/expense-reports/{id}`，均仅供申请人本人使用，管理员没有财务明细豁免。响应设置 `Cache-Control: no-store`。

| 方法与路径 | 行为 |
| --- | --- |
| `GET /precheck-options` | 当前申请/财务版本、真实财务目标及可排队状态 |
| `POST /precheck` | 幂等保存任务，返回 `202` 和任务 ID |
| `GET /prechecks/{jobId}` | 状态、逐行问题、候选金额与当前可用性 |
| `GET /prechecks?limit=25&beforeId=...` | 有界轻量历史，最大 100 条，不批量复制费用明细 |

排队请求只接受 `applicationVersion`、`financialVersion`、`initiatorAppointmentId`、`accountingDate` 和 `targetDigest`。员工和租户从当前身份取得；核定金额、外部地址或“通过”标记等额外属性直接拒绝。

记账日期是显式输入，由预算端口核对期间是否开放；平台不自动把已结账日期顺延。汇率日期独立采用检查时法人当地提交日，不能用费用发生日或宿主机时区替代。目录的法人必须提供合法 `timeZone`（如 `Asia/Shanghai`），其 UUID 与所选本地任职法人一致；企业代码转换属于接入适配器。

## 检查事实与失效

- 校验本人目录内的法人、类别、计量单位、城市、成本中心和项目，账户须属于同一员工和法人。
- 每张所选发票必须具有当前版本的成功验票任务，目标指纹匹配，原件 READY 且物理字节摘要正确。之后有任何新验票尝试，即使超时未改动发票版本，也不能继续沿用旧成功结论。
- 原币金额按法人提交日的真实汇率折算，制度核算额和可抵扣税额使用本位币。制度明确要求事前申请而未引用时阻断，不使用模拟标准或税率。
- 同时检查本次和上一轮引用的发票、批准额度及借款，以同一资源计划计算释放、迁移和新预留。资源按集合批量读取，避免逐张查询数据库。
- 除聚合版本外，还检查当前规范票号占用键。另一份同票号文件被占用可能完全不改变本单资源版本，仍必须使候选结果失效。
- 预算按核定含税成本分摊检查，不按扣除税额或借款冲销后的付款额计算。请求及回执绑定单据、轮次、财务版本、员工、法人、记账日期和完整分摊。

有效期取目录、账户、制度、验票、预算事实、5 分钟本地上限和法人次日零点中的最早时刻。结果入库前重查双版本、任职、目标和资源。读取 READY 结果时另给出 `usable`；输入过期、资源变化或被新检查取代时，历史状态仍是 READY，但当前不可提交。

预览只显示账户掩码，内部账户引用、绑定摘要、原件摘要和目标凭据不返回页面。`preview.submittedAt` 是候选构建时间，不代表实际提交；正式提交必须重新创建真实轮次记录。

## 任务状态与恢复

`QUEUED → RUNNING → READY / BLOCKED / UNAVAILABLE`。每次状态转换追加历史，三种终态分别表示完整候选、业务不满足、没有可信结论。逐行问题包含阶段、行号、分类和受控错误码，不透传外部响应正文。

排队任务在重启后可继续领取。进程在领取后退出，其他进程保留原租约，租约到期只记 `TIMEOUT`，不会自动重发。员工可以明确新建检查；原幂等请求始终回放原任务 ID。事务内任职查询使用可缺失结果，避免在捕获事务代理异常后误以为仍可保存失败结论。

财务网关默认关闭。启用后预检使用独立调度线程；`AGENTFLOW_EXPENSE_PRECHECK_WORKER_ENABLED=false` 只暂停领取，不删除数据库任务。`AGENTFLOW_EXPENSE_PRECHECK_TIMEOUT_SECONDS` 默认 300，支持 15–900 秒，限制整项预检而非单个 HTTP 请求。每次外部请求仍受网关 1–60 秒超时限制，晚到结果不能覆盖终态。

V37 新增任务与版本表，复合外键约束报销单、本人、原申请和真实财务版本；活动键和检查序号分别唯一。升级不重写旧申请、财务快照、发票或验票任务。

## 验证边界

自动测试使用真实 HTTP 适配器连接本机合成财务服务，并验证 H2/PostgreSQL 状态与事务。另以打包服务验证进程恢复。合成政策、查验和放款引用不能替代真实企业联调；完整财务页面、正式提交、预算冻结与结算仍继续开发。当前证据见 `evidence/expense-precheck-20260928.json`。

验证记录（2026-09-28）：预检领域 3 项、申请领域回归 22 项；服务端范围回归 70 项（含当时 13 项预检）；最终预检/升级 15 项、调度 1 项、OpenAPI 5 项；PostgreSQL 同场景 15 项；最终打包阶段端口/调度/契约 20 项。范围有交叉，不累加为独立功能数。

打包服务在独立 PostgreSQL 上完成 141 次实际 HTTP 请求（含轮询）：排队重启后得到 READY；执行预算请求时终止本次 JVM，重启后保留租约，到期仅记 TIMEOUT；明确新建任务后成功，旧幂等请求仍返回旧超时任务。最终 2 个 READY、1 个 UNAVAILABLE 和 9 条任务历史，全部报销仍为草稿财务版本 1，发票占用与金额预留均为 0。临时后端及合成网关已停止，数据保留。
