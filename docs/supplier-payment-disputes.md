# 供应商原付款争议裁决

供应商付款目前已有原号查询和持续争议冻结，本阶段补充独立财务裁决的领域规则及 V78 持久凭据。公开办理、页面及原验收库升级继续实施；当前本地演示仍为 V77，不能将数据库单元验证视为完整办理验收。

## 调用链和职责

调用方是原采购轮次中具备完整财务字段读取权限、当前法人有效任职的独立财务人员。原申请人和原付款出纳不能裁决。后台原号查询先保存银行回执，财务再针对展示版本作出明确决定；客户端不提供金额、账户或自行编造银行回单。

付款实体判断近期终态是否保留原交易及历史资金。应用服务负责当前权限、原申请锁、展示版本与审计，仓储在一个事务内保存裁决后的付款修订及独立凭据。下游 ERP 核销仍读取当前银行状态；裁决本身不产生银行发送、ERP 核销或预留释放。

受影响场景包括到账后出现矛盾回执、修订倒退、短期证据过期、已经确认退回后再次返回到账、并发裁决和处理进程重启。原银行指令、出纳选择、ERP 预留、既有核销及旧修订保持。

## 裁决规则

- 只采用原指令最新保存的最高外部修订，状态为成功、明确失败或退回；观察时间的五分钟窗口为左闭右开，到期必须重新查询。
- 首次确认到账后，成功裁决必须保留同一银行交易号、原金额、账户、到账时刻及回单。退回必须仍属于原交易，且不能早于原到账。
- 历史中曾出现到账或退回证据，即使当时属于争议候选，也不能随后裁决成从未付款。仓储逐条读取连续修订，不能只检查当前两份回执。
- 已确认的真实退回不能被新成功回执抹掉，也不能换成另一份退回回单。原退回的更高版本可在独立核对后确认，仍不解除资金退回对应的其他处理要求。
- 普通查询保留争议。普通仓储更新也不能清除冲突；必须经专用裁决入口保存具名人员、外部对账引用、原因及裁决前后两个相邻版本。

V78 新增 `supplier_payment_dispute_resolution`，两个外键分别约束原付款的冲突修订和结果修订，每个冲突及结果版本只能裁决一次。操作状态、结果修订或裁决凭据任一失败全部回滚。最后裁决读取时再次核对两份原修订和裁决当时的历史，后续新查询不修改旧决定。

## 验证与接续

新增七项领域测试覆盖原回单、不同交易、过期、修订倒退、历史资金和真实退回保护；相关领域范围共 29 项通过。新增六项数据库测试覆盖无证明解冻、并发唯一裁决、保存失败回滚、历史缺失、损坏凭据和 V77→V78 保留旧数据；H2 与 PostgreSQL 相关服务端范围各 45 项通过，见[持久裁决证据](evidence/supplier-payment-dispute-persistence-20260930.json)。范围包含既有银行与 ERP 核销回归，不能相加为全项目独立用例数。

无证明更新缺口先由最小测试产生失败，再增加持久边界。原测试只验证正常应用服务路径，缺少对清除冲突本身的仓储约束验证。公开财务权限、幂等接口、实际页面、V78 演示库升级及真实外部系统仍须继续验收。
