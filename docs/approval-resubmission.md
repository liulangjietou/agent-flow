# 申请撤回、补正与重新提交

本用例适用于通用表单申请。申请人可撤回审批中的申请，再修改并重新提交；草稿和已退回申请也可修改。结构化费用报销单仍需后续实现。轨迹与审计见[审批历史](approval-history.md)，写请求重试见[幂等协议](request-idempotency.md)。

## 使用路径

1. 审批人在待办中选择“退回”，填写原因并确认。当前流程实例终止，申请进入“已退回”。
2. 申请人在“申请记录”点击“查看并修改”，查看退回原因，修改标题、金额或说明。
3. “保存修改”只保存当前内容，不增加审批轮次；“重新提交审批”先保存修改，再以最新申请版本提交。
4. 提交后开始新轮次和新流程实例，沿用原流程版本。各轮提交内容及最终处理意见可在“提交轮次”中展开查看。

当前固定表单只编辑标题、金额和说明，其他 payload 字段保留。业务单号、流程 key、定义版本和申请人不能通过补正接口更换。

申请人也可在审批中申请的详情页选择“撤回审批”，填写可选说明并确认。撤回会终止当前实例的待办，保留既有审批意见和提交内容；之后可修改并重提。其他用户没有撤回入口，已退回和终态申请也不能再次撤回。

## API

`PUT /api/v1/applications/{id}`：只允许当前租户的申请人修改。

```json
{
  "expectedVersion": 3,
  "title": "补充材料后的申请",
  "payload": {"amount": 4800, "description": "已补齐说明"}
}
```

成功返回更新后的申请；`version` 增加，`roundNo` 保持不变。请求的 payload 是当前内容的完整替换，API 调用方需保留仍有效的业务字段。

`POST /api/v1/applications/{id}/submit`：沿用已有提交接口，携带保存后返回的 `expectedVersion`。第一次提交使用第 1 轮，退回或撤回后的提交增加轮次。

`POST /api/v1/applications/{id}/withdraw`：仅当前租户的申请人可撤回 `IN_APPROVAL` 申请。

```json
{
  "expectedVersion": 1,
  "comment": "补充材料后重新提交"
}
```

`comment` 选填，最多 2000 字符。成功返回状态为 `WITHDRAWN` 的申请，申请版本递增、轮次不变。撤回说明保存在本轮结论及申请审计中；随后重提才增加轮次、启动新实例。

`GET /api/v1/applications/{id}/rounds`：与申请详情使用相同读取权限，返回轮次数组。每条包含 `roundNo`、`processInstanceId`、`definitionVersion`、`title`、`payload`、`submittedBy`、`submittedAt`、`status`、`reason`、`completedBy`、`completedAt`。未终结的轮次没有完成时间、处理人和原因。

- 申请版本过期：`409 CONCURRENCY_CONFLICT`，重新加载并核对后再操作。
- 非申请人修改：`403 FORBIDDEN`。
- 当前租户下不存在或无权读取的申请、轮次：`404 NOT_FOUND`。
- 状态不允许修改或提交：`422 DOMAIN_RULE_VIOLATION`。
- 撤回时没有唯一当前实例、轮次与实例关联不符，或引擎并发写入冲突：`409 CONCURRENCY_CONFLICT`，不能把缺失实例当作撤回成功。

乐观锁用于拒绝过期写入；业务写接口同时要求 `Idempotency-Key`，相同请求重试回放原结果。二者分别负责版本竞争和请求恢复，详见[幂等协议](request-idempotency.md)。

## DDD 职责及事务

`Application` 聚合维护可编辑状态、版本和轮次规则。应用服务执行发起人授权，并编排聚合、仓储、流程运行端口和轮次仓储。JDBC 适配器保存轮次记录，Flowable 适配器返回实际实例标识，控制器只承接请求与响应。

提交快照包含提交时的标题、payload、定义版本和实际流程实例。流程启动、申请状态更新和快照追加位于同一本地事务；任一步失败不得留下新实例或新轮次。审批结论更新只允许补充轮次状态、原因、处理人和时间，不修改提交内容。

撤回状态由 `Application.withdraw` 维护；应用服务编排当前轮次绑定、运行时终止、申请更新、轮次结论和 `ApplicationAuditPort` 审计，全部参加同一本地事务。引擎适配器以系统写入的租户、申请 ID、轮次定位唯一运行实例，已有快照时还必须匹配实际实例 ID。用户 payload 放在独立的 `formData` 变量中，不覆盖这些关联变量。

V3 迁移新增轮次表，不覆盖 V1/V2。升级前未生成轮次快照的旧申请不补写虚构历史；界面提示暂无快照，旧申请的正常办理保持兼容。完整历史恢复需以实际保存的引擎历史和审计证据为准，不能用当前内容代替。

V4 仅扩展轮次结论约束，允许 `WITHDRAWN`，不改写 V3。内置全局流程的旧实例可能没有引擎租户字段：此时仍要求上述系统变量精确匹配；引擎租户字段非空时必须与当前租户一致。没有提交快照的旧轮次保留原状，撤回仍写入申请审计，界面不将缺失记录解释为“未填写说明”。

## 验证入口

根目录执行作者检查和 `mvn verify`，前端执行 `npm run build`。后端 `ApplicationResubmissionIntegrationTest` 覆盖真实 HTTP、数据库和流程引擎链路；具体通过数量以本次 Surefire 报告为准。

2026-09-22 补正阶段验收：后端 `verify` 共 67 项通过（domain 19、server 48），前端构建通过，54 个 Java 文件的 92 个命名类型作者检查通过。回归包含过期版本、顺序重复提交、跨租户和非发起人边界、引擎启动失败与快照写入失败回滚；该阶段未执行同时竞争测试。

真实浏览器已验证退回申请 6000 → 修改为 900 → 保存仍为第 1 轮 → 重提第 2 轮 → 部门审批批准；第一轮的 6000 与退回原因保留，新增轮次绑定不同实例且沿用原 v2。该场景的初次创建与退回由 HTTP 准备，补正、重提和第二轮批准由浏览器操作完成。另验证加载错误后关闭、编辑后服务不可用时本地放弃、带空格账号登录后的编辑权限及初始反向 Tab 焦点。

显式 JSON `null` 可用于清空可选字段，并保留到数据库、轮次快照和 Flowable 变量；测试实际经过条件网关，避免保存成功却在后续审批中失败。

2026-09-22 撤回阶段验收：后端完整 `verify` 共 88 项通过（domain 20、server 68），其中撤回集成回归 20 项；前端构建通过，57 个 Java 文件的 97 个命名类型作者检查通过（包含检查脚本自身）。在保留原申请的本地 H2 文件库上实际完成 V3 → V4 升级。

撤回测试覆盖状态、越权、过期版本、无实例/多实例/关联不符、存量空引擎租户、payload 系统变量隔离、审计写入失败回滚，以及撤回与最终批准同时进入真实引擎的竞争。实际观察到 Flowable 乐观锁冲突与 H2 死锁回滚，分别按明确异常类型返回 409；确定性回归还证明包装后的事务回滚异常可识别，无关 SQL 错误不被误报为冲突。这些场景不代替压力测试或 PostgreSQL 实库验收。

浏览器另验证审批中金额 800 → 申请人填写说明撤回 → 金额改为 650 并重提 → 部门审批批准。两轮分别为 `WITHDRAWN/APPROVED`，原说明保留，实例不同且均绑定 v2；初次创建与提交通过 HTTP 准备，撤回、补正、重提和第二轮批准均在浏览器完成。空说明撤回、审批人无撤回入口、失败保留说明、操作完成后的焦点和反向 Tab 也通过浏览器验证。
