# 凭证处理通知

F17 的借款挂账、报销挂账和员工付款凭证已接通准备异常、ERP 结果、原记录详情和消息页面。凭证已过账不表示资金已到账，也不表示业务核销、资源恢复或归档已经完成。F17 继续保持 OPEN。

## 调用链与事务

`VoucherPreparationService / VoucherOperationService / 既有凭证对账与冲销服务 → 已保存状态事件 → VoucherNotificationService → JdbcInboxRepository`。

准备服务新增 `VoucherPreparationChanged`；过账服务补齐领取时发现租约过期、依据变化及发送期限过期的事件。准备及过账聚合继续决定状态，通知层决定最小内容、原接收人和去重。站内消息、外发意向与原状态同事务提交；数据库事务内没有通知渠道网络调用。保存通知失败时，本地确认回滚，过账恢复仍查询原操作。

事件键为 `voucher:<原准备或操作 UUID>:<事实>`。每次重新准备都有新的 UUID；由准备登记的实际命令沿用该准备编号。同一编号的相同事实对每个接收人只记录一次。不同结果分别保留，重复查询和事件重放不增加重复提醒。

- 准备被阻断、暂不可用、来源失效分别给出最小提示，没有登记命令时不会写成过账失败。
- 正常排队、准备完成、无需金额凭证、ERP 受理中和主动复查不制造异常。
- 查询失败、租约丢失、权威查无、回执冲突、发送过期与来源变化分别表达；未知不推断未过账，不自动重发。
- 已过账、过账未通过、已冲销作为 ERP 结果提示，资金和业务资源仍由各自链路确认。

## 接收人与当前权限

接收人是原申请人和该次准备记录中的实际发起人：批准触发时为原批准操作人，付款成功触发时为原执行出纳，财务重新准备时为该次财务操作者。不向当前所有财务角色广播，也不从角色列表猜测升级前命令的发起人。没有准备历史的原命令只采用可确证的申请人。

接收人须仍是可信组织目录中的有效人员。普通挂账沿用审批参与关系，不额外要求出纳场景的法人任职；付款凭证中的非申请人还须保留原法人有效任职。外发领取和重试重新核验上述边界、本人偏好、同意代次及固定收件绑定。消息不复制金额、账户、科目、完整命令、用途或回单正文。

`GET /api/v1/notifications/{id}/voucher-target` 只读取本人持久消息对应的原编号、原申请和轮次。拒绝查询参数，响应为 `Cache-Control: no-store`。详情调用既有 `VoucherAccess.read`，继续执行该轮申请可见性和完整财务字段权限；收到最小提示不等于获得凭证明细权限，管理员也没有旁路。

失败准备的消息即使后来同轮已成功过账，仍显示那次失败准备，实际操作保持为空，不改为最新准备。详情仅复用凭证工作区的准备与过账摘要，不公开会计命令、账户、内部目标或办理动作。

原凭证绑定独立冲销时，`reversalBound` 明确标记当前停用。此前已接受的过账事实仍保留，不能因为它显示已过账就作为新的付款或资源依据。

## 消息页面

消息中心只在点击“查看原凭证”后读取受控详情；读取不标记已读、不重新准备，也不发送过账。准备与过账分栏展示，冲突保留此前已接受的凭证号；ERP 正常处理中单独显示。导航明确定位原申请轮次，业务入口再次核验当前权限和办理条件。

重新读取先清空旧财务事实。切换账号、切换消息、读取失败、失权、超时和卸载都会丢弃旧请求，忽略取消的迟到响应也不能恢复旧内容。
