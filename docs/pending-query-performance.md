# 待办分页查询性能验证

2026-09-24，合并待办页面与完整总数的重复查询。`GET /api/v1/workspace/tasks` 的响应、筛选、授权和游标格式保持不变，不增加数据库迁移、任务缓存或状态副本。

## 根因与职责

调用链为 `PendingTaskQueue → PendingTaskController → PendingTaskReadPort → FlowablePendingTaskReadAdapter`，列表与看板共用这一接口。原入口先读取页面，再独立计数，两次执行相同的申请、当前轮次、租户、活跃任务以及指派/候选人联查。前轮 5,000 份申请的容量报告已经观察到待办并发延迟增长。

读端口现在一次返回分页候选项和完整匹配总数。SQL 内层执行原授权与筛选，并用 `COUNT(*) OVER ()` 计算总数；外层才应用时间/任务 ID 游标、排序和 `limit + 1`。因此第二页的总数不会只统计游标之后的任务，预读行也不会被当作完整总数。

首页为空时总数为零。后续页为空时，之前仍可能有未完成任务，因此在同一只读、可重复读事务中补查总数；不能直接返回零。正常非空页仅联查一次，空后续页最多两次。页面之间仍会反映新提交、转交和完成，不提供跨请求冻结快照。

查询组合及行映射属于基础设施读适配器；领域端口只定义摘要与总数，不引入 SQL 或 Flowable 类型。审批聚合、写入应用服务、乐观锁、幂等和引擎事实条件保持原样。

## 先复现与回归

原有测试覆盖筛选、权限、游标、异常引擎绑定和金额精度，没有检查重复数据库读取。新增最小测试在真实 JDBC 连接上记录准备的 SQL，先稳定失败：非空页与总数预期一次当前任务联查，实际两次。没有使用容易受宿主机波动影响的毫秒阈值。

回归同时覆盖：

- 5 条匹配、每页 2 条，第一页和第二页都返回完整总数 5，末页无后续游标。
- 末页任务完成后，旧游标返回空页、无后续游标，但总数仍为前方待办的 4。
- 无匹配、无 APPROVER 角色、其他租户均返回正确的空页及总数。
- 全员会签只统计当前用户自己的任务；finance 完成后自己的总数为零，admin 的剩余任务仍为 1。
- 原领取、转交、委派、回交、同时间游标、筛选绑定、暂停、错误租户/轮次及精确金额用例继续通过。

## 独立 SQL 实验

使用阶段 58 保留的隔离 PostgreSQL 样本库，5,000 份申请、3,750 个待办、40 个流程，数据库限制 1 CPU / 768 MiB。按生产联查及 manager 实际角色组装查询，首页读取 31 条；分别执行三次 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`。

| 查询 | 三次执行时间 ms |
|---|---|
| 原独立计数 | 52.192 / 40.075 / 41.036 |
| 原独立页面 | 42.550 / 43.336 / 43.301 |
| 合并页面与总数 | 47.749 / 44.196 / 43.003 |

新旧页面全部字段逐项一致，新页面各行总数均为 3,750。合并查询省去独立计数的主要开销，但这组数据只证明 SQL 实验结果，完整 HTTP 指标另行记录。总数仍需遍历完整匹配集合，不意味着待办在任意规模下具有固定查询成本。

原始失败、完整门禁与双库日志位于 `/fyoung/tmp/agentflow-pending61-{red,verify,pg-final}.log`；SQL 与计划见 [SQL 证据](evidence/pending-query-plan-20260924.json)。
