# 费用类别与制度版本管理

F01 正在开发。管理 API、版本存储、预检绑定和管理页面已完成阶段验证；填报提示、事前申请类别版本绑定以及管理制度的完整提交验收仍待完成，因此 F01 仍在未完成台账内。

## 权限与职责

管理 API 前缀为 `/api/v1/admin`，统一要求 `FINANCE_CONFIG_ADMIN`。普通 `FINANCE` 和 `ADMIN` 不隐含这项权限。开发演示的 `admin` 明确具有该角色；企业环境必须在 OIDC 中显式映射，不能把示例配置当成企业授权。

领域模型负责类别身份、规则定义和发布版本不变量。应用服务编排跨聚合校验，仓储保存不可变历史及当前指针。企业财务服务继续提供职级、城市等级、票据等级、税务等事实并执行指定制度，平台不会生成企业标准或用申请人的输入替代这些权威事实。

## 管理入口

| 路径 | 方法 | 作用 |
| --- | --- | --- |
| `/expense-categories` | GET / PUT | 当前目录、携带 `expectedVersion` 保存完整修订 |
| `/expense-categories/versions` | GET | 类别历史摘要 |
| `/expense-categories/versions/{version}` | GET | 某版完整目录及操作者、时间和原因 |
| `/expense-policies` | GET | 草稿目录摘要 |
| `/expense-policies/current` | GET | 最新类别及当前生效制度 |
| `/expense-policies/activations` | GET | 制度发布生效历史 |
| `/expense-policies/{key}/draft` | GET / PUT | 当前草稿、携带 `expectedRevision` 创建或编辑 |
| `/expense-policies/{key}/draft/versions/{version}` | GET | 历史草稿正文 |
| `/expense-policies/{key}/publish` | POST | 发布并切换当前完整制度集 |
| `/expense-policies/{key}/versions` | GET | 发布版本摘要 |
| `/expense-policies/{key}/versions/{version}` | GET | 不可变发布正文 |

读请求禁止缓存。目录使用 `afterKey`，各历史列表使用 `beforeVersion`，`limit` 默认 25、最大 100。拒绝未知及重复查询参数。写请求必须携带幂等键及非空原因；成功响应、内容历史和版本指针在同一事务中保存。HTTP 输入拒绝未知字段、重复 JSON 键、尾随文档以及版本和布尔值的隐式类型转换。

类别版本 0 仅表示尚未配置。已有代码不能从目录删除；停用、更名、修改允许单位和重新启用均产生新修订。未发布制度前，配置处于准备阶段，既有费用用例继续使用原企业目录和制度源。首次发布后，员工可选类别和单位取平台启用目录与企业授权目录的交集；配置不会扩大员工权限。

草稿修订 0 表示明确创建，首版为 1。草稿可以暂时没有规则，但发布必须具备启用类别及完整规则。发布请求同时提交 `expectedDraftRevision`、`expectedCategoryRevision`、`expectedActiveRevision`。当前租户只有一个完整生效制度集：需要多个法人、类别等差异时放在同一制度集的规则中；发布其他制度键也会显式切换该指针，不做隐含的多制度合并。

保存草稿不影响当前制度。发布相同草稿两次会拒绝；有内容变更时保存新草稿修订，再发布新的制度版本。发布版本不提供覆盖或删除接口。V103 新增配置头、类别修订、草稿、草稿修订、发布物及生效记录六张表，不回写旧审批或财务轮次。

## 规则语义

规则按显式顺序首次全维度匹配。法人、类别、城市等级、职级集合为空表示任意值；日期上下限均包含当天，币种为空表示不限。未命中不能解释为默认允许，事实源应返回 `POLICY_NOT_FOUND`。完全相同的匹配条件和重复规则键不能保存。

每条规则可配置单价限额及单位、票据最长时限及处理方式、允许的舱位或等级、事前申请要求；禁止报销的规则不能再附带允许性约束。金额限额必须明确同一原币条件。固定行程补贴属于 F03，事前额度控制模式属于 F05，不在本实现中冒充已完成。

舱位或票据时限例外通过 `SERVICE_LEVEL`、`INVOICE_AGE` 标记，金额超标通过 `AMOUNT` 标记。非金额例外不能靠伪造较低上限来表示。需要例外审批时，申请人仍必须提供说明，`hasOverStandard` 仍驱动原有流程条件。

## 制度执行与提交绑定

启用平台制度的 `expense-policy` 请求增加 `managedPolicy`，包含固定的 `selection`、完整 `definition` 和本行的启用 `category`。选择信息为：

```json
{
  "policyId": "00000000-0000-0000-0000-000000000001",
  "policyVersion": 1,
  "categoryRevision": 1,
  "activeRevision": 1,
  "definitionDigest": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
}
```

以上仅为协议示例。摘要由平台对本次发送的规则正文计算，不是企业额度或签名凭证。企业响应的 `policy.managedPolicy` 必须包含相同 `selection`、本定义内命中的 `ruleKey` 及匹配事实的 `factSourceReference`。平台同时检查政策身份及版本、本地已知匹配维度、事前申请要求、例外种类、折算金额及税额边界。职级和城市等级的真实性仍属于 E03 企业接入验收，回环夹具不能证明企业制度已经接通。

事实源缺少回执、采用其他版本或返回未声明规则时，结果为 `UNAVAILABLE / INVALID_RESPONSE`；不会沿用旧制度结论。尚未启用平台制度的租户保持原协议，历史快照仍可读取。

一次预检固定一个选择，所有行的回执都必须一致。后台落库前和读取 READY 结果时复核当前选择；发布或修改生效类别后，旧结果显示 `POLICY_CONFIGURATION_CHANGED`。最终提交持有配置头锁直至财务轮次和审批事务结束，与管理员发布串行化，避免检查后换版。已经提交的轮次保留原始回执和版本，不随当前草稿变化。

## 管理页面阶段验证

具有 `FINANCE_CONFIG_ADMIN` 角色的账号可从“管理与集成 → 费用制度”进入。页面包含费用类别、制度草稿与生效记录；编辑规则时可调整匹配顺序，发布前重新读取草稿和当前配置，展示三版本、将替换的制度、已保存类别及完整规则，管理员填写理由并勾选确认后才发出发布请求。

本地编辑仅保存在按身份隔离的内存中。请求结果未知时，公共恢复入口只发送原幂等键和原正文；确认新建成功后页面重新读取保存修订。版本冲突保留本地旧基线，需要明确核对或放弃修改；失败、账号切换和失权时不继续展示可操作的旧配置。历史页面仅提供只读查询。
