# 业务操作追踪

O01 请求入口及持久队列的来源关联已完成；审批、Agent、核心财务、集成、Webhook、财务复核、供应商及报销恢复业务标识已通过本地验收。继续六类直接调度业务标识及原 02 §10 最终范围核对。

## 请求及日志

服务器在 CORS 和认证之前生成 UUID 格式的 `X-Trace-Id` 响应头。客户端传入的同名头不参与生成，也不代表身份。已有认证、CSRF、参数绑定和领域错误中的 `traceId` 与响应头一致；成功请求也返回该头。允许的前端来源可以通过 CORS 读取它。

同一请求的同步 Flowable 调用沿用当前线程 MDC；`tenantId` 只来自完成认证的主体。请求日志包含 traceId、可信租户、路由模板、结果状态及耗时，未知路由使用 UNMAPPED，不写入原 URI、查询参数、请求体、令牌或异常正文。指标标签没有增加租户或追踪标识。已有日志保留各自的稳定错误码。

作用域支持嵌套并在异常时恢复，只管理自身 MDC 键。请求错误再分派保持原追踪标识。归档 ZIP 下载会换线程，控制器在授权读取之后显式捕获诊断上下文，写文件完成后清理；认证主体不会随它传到下载线程。

## 审批与投递

新的申请/任务审计 payload 保存来源 traceId。当前审批事务产生的 Webhook 事件体使用相同 traceId，审计事件 ID 与追踪 ID 分工明确；业务幂等重放不改写原审计或投递记录。每个 HTTP 重试有自己的请求追踪标识，原业务事件继续保留首次执行来源。

worker 在事务外发 HTTP，从已存事件体恢复 traceId，租户只读投递索引，不采用事件体中的身份值。外部请求额外带 `X-Trace-Id`，签名、正文、eventId、租约、重试次数及人工重试规则保持原语义。响应头用于诊断，授权与验签仍使用原协议。

旧版本已存事件若具有有效 traceId（当时通常等于 eventId），保持它原样；缺失、非 JSON 或无效字段使用“事件类型范围/租户/eventId”派生的稳定诊断 UUID，不重写历史正文，也不声称它是原始 HTTP 来源。一次失败在该投递的诊断作用域内记分类和投递 ID，后续租户不继承它。

## Agent 持久任务

审批摘要、申请草稿、票据抽取、报销填报、预检解释和风险解释在原队列创建事务中保存来源 `trace_id`。V122 仅为六张原表新增可空列，不改领域 JSON、租约、版本、发送同意和目标摘要；幂等重放也不替换首次来源。

每个工作器在领取前恢复该任务的 traceId 和索引租户，模型执行、结果结算及失败分类日志均在这个作用域内；离开后恢复外层上下文。六类模型共用传输客户端，只增加 `X-Trace-Id` 头，提示词不增加租户或诊断数据。身份仍由原服务在发送前复核，诊断上下文不传递 Actor 或登录凭据。

历史空值或无效值按任务类别、索引租户和运行 ID 生成稳定的独立诊断 UUID，数据库保持原值，不声称找回了原 HTTP 来源。失败、跳过、相邻租户以及线程复用有独立测试。固定包使用六类真实 HTTP 入队和回环模型验证旧库升级、新任务排队后强退、原键恢复及独立备份恢复；模型共收到 12 个请求，原审批状态保持。见[Agent 阶段证据](evidence/operation-tracing-agent-20261007.json)。

## 财务持久任务

费用预检、发票查验、预算、凭证准备及执行、出纳执行申请、付款执行和账户复核在原事务内保存来源 trace_id。V123 只给八张队列表增加可空诊断列，不改原输入、命令摘要、业务状态、版本或租约。

八个工作器在领取前恢复上下文；补建借款余额与付款凭证的两个入口也恢复原付款来源。准备生成的凭证、出纳申请生成的付款以及付款生成的后续凭证继续沿用同一来源。旧记录没有请求来源时采用按类别、租户和任务编号派生的稳定 UUID，原空列不回填。

共用财务网关只增加 X-Trace-Id 请求头。财务协议的 requestId、写命令 Idempotency-Key 和原正文继续承担各自职责，不能用追踪号替换业务幂等编号。

9 项缺失断言先失败，修复后新增范围 19 项通过；相关回归 636 项通过。固定包 8 次启动、291 次业务 HTTP、116 次回环网关请求、14 次原键重放通过；280 表非空升级与独立恢复保留原列，16 份授权详情保持。22 条不同财务命令各发送一次。见[财务阶段证据](evidence/operation-tracing-finance-20261007.json)。这些结果不覆盖其余后台链路，也不替代 PostgreSQL 或真实财务系统联调。

## 核心集成持久任务

服务任务、电子签、组织同步、通知投递、事件收件和付款回调在原入队事务保存来源 trace_id。V124 只增加六个可空诊断列，工作器在领取前恢复索引租户与来源，领取失败、结果保存、电子签原件发送和结果文件收取处于同一作用域。离开后恢复线程原上下文。

服务、电子签和组织来源的 HTTP，邮件 MIME 及企业微信令牌/消息请求增加独立 X-Trace-Id。原命令号、签名原文、Message-ID、幂等键和首次授权保持；付款回调不会覆盖原付款命令来源。历史空列使用稳定派生标识，不回填或伪称原请求来源。

11 项缺失断言先失败；594 个唯一相关用例经范围执行及 35 项旧夹具修正复测全部通过。固定包按认证边界拆成共享 OIDC 与演示通知两组，共 14 次启动，分别验证 280 表原列保持、排队后强退、原键重放和独立恢复。电子签保持原 OIDC 授权；演示邮件/企业微信每次启动重新登录。14 份授权详情恢复一致且不重发。见[核心集成阶段证据](evidence/operation-tracing-integration-20261007.json)。结果不替代浏览器、PostgreSQL 或真实企业系统验收。

## 供应商持久任务

## 报销恢复与结算归档

六个报销恢复工作器的十五条执行路径已保存或恢复来源，V127 新增十个可空字段。部分调整根记录、预算授权和会计授权分别保留来源；扫描候选携带原命令编号，在原报销锁内核对后领取，重新授权后的命令由新候选处理。预算复核同样在原申请锁内核对预算编号，避免旧扫描推进新授权。结算补登读取原付款、凭证或零应付准备的来源，归档沿用原结算来源。异常日志仅保留错误码和业务标识。

## 直接定时入口

代理生效、任务超期、审批升级、定时等待、借款逾期和预算保留到期共六个入口，在进入业务事务前恢复各自不可变来源。V128 给代理授权、借款归还约定及原停止轮次的预算保留各增加一个可空字段；人工任务和定时任务的创建来源由独立 Flowable 适配器写入应用表，与引擎创建一起提交或回滚。来源租户取自原生对象，转交、暂停、恢复和失败队列迁移不改写原来源。调度异常只记录错误码和定位键。

12 个行为与日志失败复现、7 个持久化缺失检查经实现后通过；25 组相关测试共 249 个唯一用例通过。固定包覆盖代理、超期、升级及定时等待四个入口，共 7 次启动、231 次业务 HTTP、263 个响应头和 6 次原键重放；8 条通知来源一致，2 次定时推进各执行一次，280 张旧表原列保持、281 张表独立恢复后无重复通知。借款逾期和预算保留由范围内持久化与业务集成测试验证，不冒称固定包覆盖了两者的到期运行。见[直接定时阶段证据](evidence/operation-tracing-direct-scheduler-20261007.json)。

## 审批业务标识

诊断作用域现在管理 traceId、tenantId、businessNo、processInstanceId 和 taskId。新入口清理外层业务键，显式异步捕获携带当前事实，关闭时恢复原作用域；日志对控制字符、方向字符、空白和等号作替换并限长，不改数据库中的单号或审计原值。

申请及任务读取只在资源授权成功后记录业务关联。引擎创建事件从本对象的实际实例读取受控变量，子流程不借用父申请；任务动作、流程启动及完成各有明确作用域。申请与任务审计端口由调用方提供当时单号，任务审计同时写入原 taskId，旧审计不补写。HTTP 完成日志保留请求级 traceId 和认证租户，各条业务日志通过相同 traceId 关联，避免把一个父子流程请求误当成只有一张申请。

7 个失败复现修复后，21 组范围测试累计 260 个唯一用例通过；最后的日志分隔符修改通过 56 项匹配回归。最终固定包完成 6 次启动、38 次业务 HTTP、64 个追踪响应头、两张申请四个轮次、6 条新审计关联及 4 次原键重放；281 张表升级前后保持，独立恢复无重复审计，两份授权详情一致。见[审批业务标识阶段证据](evidence/operation-tracing-approval-business-20261007.json)。后台队列的业务号及原实例/任务恢复仍需逐项接通，O01 继续保持 OPEN。

## 供应商业务标识

九类队列和两个本地补齐入口按同租户原授权及原复核轮次关联，不借当前轮次。原回款阻断、核销和退役条件保持，缺少来源时不借其他租户资料。

43 个新增用例中 22 项先失败，修复后 341 项范围回归通过。固定包初次运行发现验收脚本将发送中状态误作终态，三个运行状态先复现后修正，原失败证据保留。相同 Java 包二次验收完成 8 次启动、380 次业务 HTTP、424 个追踪头、140 次回环网关请求和 18 组业务上下文；22 条命令各接收一次，12 次原键重放通过。281 表升级和独立恢复一致，12 份详情保持、恢复无重发。两个本地补齐入口的日志隔离由范围测试核验。见[供应商业务标识证据](evidence/operation-tracing-supplier-business-20261007.json)。报销恢复与直接调度继续开发。

## 报销恢复业务标识

六个工作器的十五个入口按原结算、调整、命令和凭证关联业务号及原实例；重新授权指令、版本、当前轮次资格和原核销规则保留。56 个新增用例中 30 项先失败，修复后 468 项范围回归通过。

固定包实际执行凭证冲销准备、冲销执行、报销结算及归档四类入口，旧新两轮共八组上下文。该合成流程没有预算审批节点，两笔预算复核在回执事务同步确认，不计作后台恢复覆盖；首轮校验对此作了错误预期，原始失败证据保留。其余十一条后台路径由范围测试覆盖。

相同 Java 包二次验收通过：八次启动、332 次业务 HTTP、435 个追踪头、154 次回环网关请求、八次原键重放；281 表升级和独立恢复一致，十份详情保持、恢复无重发。独立网关命令审计核对 16 条预算、12 条凭证、6 条付款及 2 条冲销，各仅接收一次。见[报销恢复业务标识证据](evidence/operation-tracing-expense-recovery-business-20261007.json)。直接调度及最终范围核对继续。
