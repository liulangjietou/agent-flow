# F14 项目分摊负责人会签

状态：本地实现与固定包升级、强退恢复、配套还原已验证，最终独立审查发现的长节点名读取限制已修复并验证；浏览器与 PostgreSQL 保持未验收。依据费用领域设计 §9 和用户已授权的推荐规则连续实现。固定原轮次的项目责任，复用既有全员会签，不建立另一套审批引擎。

## 业务规则

实际分摊中的每个项目必须由已配置的可信财务目录提供负责人主体，项目代码、法人和目录版本同时保留。客户端只选择费用分摊，不能指定负责人。负责人为空、项目缺失、主体没有本租户有效审批资格或来源过期时阻断预检/提交，不用流程管理员或任意主管兜底。目录的新增负责人字段可空，保证历史协议可读取；缺字段不能被解释为已完成项目审批。

正式提交冻结本轮全部项目到原负责人的映射。同一人负责多个项目时只创建一份会签责任，同时保留他承担的全部项目。申请人兼任项目负责人时复用本轮已选任职的直接主管上溯规则，并保留原负责人及上溯依据。提交后外部项目负责人变动不替换本轮名单；当前审批资格失效仍阻断办理，撤回/退回重提重新预检和冻结。

流程使用明确的 `PROJECT_REVIEW` 节点和 `expense:projectOwners` 规则，审批模式固定为 `ALL`。节点位于每条财务审批路径之前，费用敏感明细须为只读。服务端从冻结分摊派生 `hasProjectAllocation`：有项目必经项目节点，无项目必须绕过该节点。两个方向都在定义发布时静态校验，不能在无项目时凭空创建一个审批人，也不能借其他金额条件跳过真实项目责任。

项目会签不受普通相邻同人自动通过策略影响。项目名单固定，通用加减签和转交不得删除、替换该责任；已有委派协助与有效审批代理继续按原责任办理并保留实际操作者。不因同人负责多个项目或代理同一人而减少其他项目负责人的责任。当前申请人、自审批上溯、业务/财务职责分离及暂停/终止继续使用现有约束。

旧发布定义和旧在审轮次不补造项目会签事实。新提交含项目分摊而绑定定义不满足项目会签契约时明确拒绝，需采用合适的已发布版本发起；不能静默把旧在审改到新模板。无项目的旧定义保持原载荷和提交行为。财务核减不能改变本轮项目映射或清掉派生路由字段，已结束轮次的来源保持可追溯。

## 调用链和职责

1. `ExpensePrecheckEvaluator` 在原事务外财务主数据调用中取得实际项目负责人，领域值核对项目全集和同一法人，预检证据保存来源与有效期。`FinanceCatalog.Project` 只承载可信来源，不解析组织关系。
2. `ExpenseSubmissionService` 在现有申请/财务/组织锁顺序中复核预检，将项目依据与原财务修订、本轮、定义和预检号一起保存。缺必经节点或资格失败回滚所有财务占用与审批启动。
3. 费用项目绑定服务负责分摊到组织主体的编排。`ExpenseSelfApprovalBindings` 使用已冻结的原项目名单和原上溯规则，`FlowableCountersignMembers.resolveExpense` 使用既有 ALL 执行器。成员审批、并发版本及审计仍归原生任务链路。
4. 只读 Query 复用 `ExpenseDraftService.read` 的原轮次和敏感字段授权，组合项目来源与原审批责任证据。管理员同样不能读取被隐藏或脱敏的费用依据；查询不授予新的任务身份。

费用层保存项目到负责人的业务依据，组织层核验账号及任职，引擎层执行冻结后的会签责任。外部网络不进入提交事务；不会在节点激活时重新查询外部目录。

## 页面与兼容

费用预检对缺失项目负责人给出明确补正原因。原轮次详情展示项目代码/名称、原负责人及适用的上溯责任，区分旧未记录、无项目和已记录。身份、单据和轮次切换清理迟到读取，不缓存敏感数据。

设计器同时明确专用项目选人、全员会签和固定责任限制。费用模板升级为新版本，加入受控项目分支和派生字段；现有已发布复制件不改写。OpenAPI、真实页面解析、模板示例和模拟使用同一字段契约。

## 验收

先验证旧目录/旧预检 JSON 兼容、负责人缺失/重复/跨法人、项目全集与原轮次绑定，再验证真实多项目 ALL 会签、同人多项目、申请人上溯、负责人变化/失效、减签和转交阻断、代理/委派、并发/回滚及核减。无项目、旧在审、三轮重提及敏感权限必须有独立用例。

固定 V119 包建立旧在审、原预算与原件，升级后核对全部旧列；新包经实际 HTTP 验证项目流程、原键丢失恢复、原生多实例处理中强退和独立数据库/附件/预算接收方配套还原。原各版本契约分别校验，实际页面解析单独核对。浏览器/PG 和真实企业主数据接入继续保留原验收边界。
