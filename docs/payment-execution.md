# 原付款后台执行

更新：2026-09-28。此阶段在 [付款持久状态](payment-persistence.md) 上接入实际批准来源、当前组织范围、事务外账户复查及资金 HTTP 执行器；后续已完成 [出纳选择的持久复查](payment-execution-requests.md)。财务／出纳业务入口、页面、到账生成借款、费用核销及付款凭证仍在接续开发。集成测试直接准备合成业务与人工授权，不代表用户已经能够在页面付款。

## 调用链

调用方为后续经过认证角色及业务范围校验的付款办理服务，先保存出纳执行登记，再在相同事务调用 `PaymentOperationService.register` 建立唯一原命令队列。后台调度读取到期标识，服务按既有申请／财务聚合顺序加锁、检查来源并领取；释放事务后，`PaymentOperationWorker` 经 `GatewayPaymentAccounts` 读取原出纳的目录与原申请人的当前收款账户。

`ApprovedPaymentSources` 复用凭证来源服务，重新读取实际批准的借款或费用聚合及版本，并校验纸件、预算、金额和分摊，再从真实财务轮次取得原收款账户。原账户不接受调用方用另一个同名员工账户替换。`PaymentPersonnel` 只检查当前法人内人员、部门、岗位和任职有效性，不授予系统角色；认证入口仍须分别验证 FINANCE 和 CASHIER。未初始化组织不回退到演示账号。

账户复查结束后，短事务再次核验实际批准、原凭证和原授权人／出纳的组织状态，才保存 SENDING。随后释放锁，经 `GatewayPaymentSystem` 发送持久原命令；已有不确定结果只调用原交易查询。财务端点始终绑定原目标摘要，配置变化不会向另一个系统发送。

## 故障与对账

- 账户 HTTP 等待不占用申请锁；另一执行器看到现有租约时不能重复领取或发送。
- 批准在查询账户期间被撤销，发送登记前的第二次来源核对会阻止发送。
- 当前账户明确变化、不可用或出纳目录拒绝，停止新发送；网络和目标配置不可用只重新检查，不能伪造银行拒付。
- 原授权在账户读取期间到期，保存未发送的 EXPIRED；不误归为可能已经付款。
- 发送租约丢失后只查询原授权。此时即使原批准已撤销、人员停用或授权过期，仍可查询资金事实。
- 资金成功后的本地消费者在同一事务内处理；消费者失败会回滚本地确认，然后查询原交易恢复，不能再次首次发送。
- 权威查无需要明确恢复动作；仍使用原编号、原金额、原出纳和原期限，并重新检查两端账户。查询不会自行创建新授权。

账户目录和当前业务检查不能消除提交到外部系统期间的变化窗口。资金系统仍须在受理命令时原子验证自己的账户、职责分离、批准与凭证规则。当前后台仅能复核本地人员／任职状态，不能声称已在线查询企业 IdP 的实时角色撤销；角色校验将在认证办理入口进行，企业联调仍需验证身份源和资金系统的策略。

## 配置与验证

财务网关启用时可消费已登记任务。`agentflow.payments.worker-enabled=false` 停止消费但保留持久事实；`agentflow.payments.poll-delay-ms` 默认 1000，`agentflow.payments.lease-seconds` 默认 90，限定 15–300 秒。每批最多十笔，账户和资金网络请求均在数据库事务外。调度器只消费已授权记录，不创建新的人工授权。

新增实际聚合、组织、数据库及回环 HTTP 集成测试 11 项通过；包含付款、凭证、账户及支付端口的 H2 范围回归 87 项通过；其中后台、仓储和迁移共 17 项在本地 PostgreSQL 通过。范围重叠，不相加。611 个 Java 文件、1082 个类型作者及语法检查通过。

账户读取跨过授权到期的新测试先失败，再修复：原测试只覆盖领取前到期，未覆盖读取期间到期。现在模型在进入 SENDING 前明确保存 EXPIRED，发送次数保持零。记录见 [执行器证据](evidence/payment-execution-20260928.json)。尚未对企业资金服务、银行、认证付款 API 或实际到账结算做完成声明。
