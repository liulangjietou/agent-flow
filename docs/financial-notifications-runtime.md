# 财务通知固定后端验收与来源核对

F17 仍为 OPEN，已确认未完成总数保持 **34 项**。本轮验证固定后端包的真实 HTTP、持久化、重启与独立恢复，同时复现供应商应付来源的三个漏通知场景；没有把已实现的通知类数量当作完整覆盖证明。

## 已验证范围

产品源码为 `6bc1d184009fee36b0d99cbee6a74a195fca250d`，固定后端 jar 的 SHA-256 为 `814aad25835bf05b001849adb4929bcc74b922769bb46cce22c8feb94bfc3c4b`。现有 17 类通知、55 处发布点完成组合核对，32 个测试类中的 **408 个不同 Java 用例通过**。原核减通知仍由 `ExpenseReductionService → ApprovalNotificationService.expenseAdjusted` 生成，已有成功与回滚证据保留。

实际公开接口创建组织、任职、制度、科目映射和借款模板，由申请人提交、主管及财务批准。受控财务服务先保存付款受理，再丢失响应，应用记录未知结果。强制终止独立进程后，同一数据库保留原消息和外发意向；恢复只查询原授权，银行命令受理次数保持 1，原未知消息仍指向同一付款。

财务原法人任职停用后，4 条付款外发意向被抑制，原付款详情返回 404。普通借款挂账凭证沿用历史审批参与及字段权限，不能误套出纳法人任职条件。SMTP 和 IM 只收到登录消息中心的通用提示，不含金额、账户或原财务正文。

SMTP 接收正文后丢失确认，原投递变为 UNKNOWN；重启不自动重发。未确认可能重复的重试返回 `400 NOTIFICATION_DUPLICATE_ACK_REQUIRED`；明确确认后沿用同一投递编号及 Message-ID，尝试次数从 1 变为 2。最后 22 条意向被渠道受理、4 条被抑制；审批版本、付款原请求及结果不变。这里的受理仅指本地合成渠道回执。

独立导出和恢复保留 **253 张表、427 条记录**，结构、序列和行摘要一致。恢复后的公开接口可读原申请、付款、消息和投递记录，权限限制仍生效，5 张通知表在只读核对后保持一致，原运行目录没有被恢复操作改写。本样例没有附件，不扩大为原件恢复证据。

230 份实际响应与 43 份成功请求通过当前 OpenAPI；付款和凭证消息详情、1,040 条重复采样的投递元数据及重试回执通过当前页面解析器。1,040 是采样次数，不是独立投递数。前一阶段的 190 项前端用例沿用原证据；本次没有冒充重新运行或实际浏览器验收。后端 jar 与 Web 分开构建部署。

## 仍缺的原业务来源

从 `FinanceGatewayClient.Operation` 及原领域服务反向核对，发现已实现的 17 个通知家族之外，还存在供应商应付复核、ERP 预留和安全结束三个入口。

调用方为 `SupplierFinanceActions`、复核 Worker 和预留 Worker；下游为原复核/预留聚合、授权仓储及 ERP 端口。受影响的是财务复核失败、已授权预留结果未知，以及原授权已安全结束的申请人和实际财务参与人。现有测试检查了状态和资金安全，没有断言这些入口产生消息。

三个最小用例先断言业务记录确已成为 UNAVAILABLE、UNKNOWN 或已有安全结束记录，再断言对应消息；均因收件列表为空而失败，没有编译或环境错误。失败日志、XML 和可重新应用的测试补丁保存在证据快照中。生产代码没有为通过验收而改变。

后续应由原应用服务在保存业务状态后发布事件，同事务保存最小站内消息和外发意向；原领域聚合继续决定业务事实，通知层负责原参与人、去重及只读定位，外发仍在事务外执行。新来源实现后再补权限、迟到和回滚回归，不以已有组合门禁代替。
