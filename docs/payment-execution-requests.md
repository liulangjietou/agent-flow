# 出纳选择的持久复查

更新：2026-09-28。在接入财务／出纳 API 前，先完成可恢复的执行请求，避免在 HTTP 幂等事务中调用账户服务。此阶段为领域、V46、仓储和后台链路；认证办理 API 与页面继续开发。

## 处理顺序

后续出纳入口在验证当前角色、法人范围、原授权版本和确认内容后，只登记一份 `PaymentExecutionRequest`。输入固定原授权、认证出纳、所选出款引用和所见账户版本，不接收金额、收款账户或资金系统地址。同一授权在数据库中只能有一个请求；重试不能更换出纳或账户。

幂等请求提交后，独立后台按原财务目标读取出款目录和本人当前账户。检查时不持有申请锁或幂等事务。服务再次加锁，重读真实批准、原挂账、授权与当前组织条件，校验所选账户版本，然后在一个事务中完成：授权登记执行、创建原授权号的付款队列、把请求标为 READY。任一版本或历史写入失败，三项一起回滚。

READY 只表示原付款命令已登记，实际资金结果由独立 `PaymentOperation` 跟踪。付款后台发送前仍会再次检查实际来源及两端账户。领取检查不等于发送，账户检查成功也不等于到账。

## 失效与恢复

| 条件 | 行为 |
| --- | --- |
| 网络、协议或目标配置暂时不可用 | 保存分类并退避，继续读取原选择 |
| 只读检查租约丢失 | 同请求恢复，迟到执行者无法覆盖新版本 |
| 账户引用、版本、法人或出纳目录不符 | BLOCKED，不创建付款命令 |
| 财务在检查期间作废授权或原批准变化 | VOIDED，不创建付款命令 |
| 原授权到期 | 未执行授权与请求一起到期，不自动延期 |
| 结果历史写入失败 | 原授权仍未执行，付款队列不存在，可由原请求恢复 |

V46 新增请求及请求版本表，外键绑定原授权，READY 还须指向相同授权号的实际付款操作。仓储比较原始输入和版本，读取时核验租户、出纳、授权、状态及时间关系列。有效授权的业务占用仍由 V45 的授权表维护，不能通过新轮次换号。

配置 `agentflow.payments.request-worker-enabled=false` 可停止检查，已有付款查询继续独立运行。检查租约默认 90 秒，范围 15–300 秒，轮询间隔默认 1000 毫秒，每批最多十个标识。未配置财务系统不返回假账户或假成功。

## 验证

新增请求领域测试 6 项，实际聚合／数据库／回环 HTTP 链路增加 7 项，V45→V46 迁移 1 项。此次 H2 范围回归共 87 项通过（34 项领域、53 项服务端）；PostgreSQL 的后台、持久化及迁移范围 25 项通过。不同阶段范围有重叠，不能把同名总数视作同一集合或相加。618 个 Java 文件、1096 个类型作者和语法检查通过。

新增时间负例先失败：请求不能在真实执行登记时刻之前标记 READY。正常创建测试没有覆盖错序恢复，补充登记时刻与请求创建／完成时刻的交叉检查后通过。详细日志见 [验收证据](evidence/payment-execution-requests-20260928.json)。合成回环资金事实不代表实际企业或银行到账；财务与出纳认证入口、状态页面、借款生成及费用结算继续实施。
