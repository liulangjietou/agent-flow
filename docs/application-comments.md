# 申请协作评论

待办详情和申请详情提供“协作评论”。当前开放审批中申请的追加评论；已批准、驳回、退回、撤回等状态暂时只读，结束后能否追加仍待业务确认。评论是沟通记录，不替代批准、退回、驳回等审批意见，不改变申请版本、轮次、审批结论或引擎任务。

## 使用方式

1. 打开有查看权限的申请，在“协作评论”输入补充说明，点击“追加评论”。正文为 1 至 4000 个字符的非空白纯文本，服务端去掉首尾空白。
2. 记录显示真实作者、时间，以及记录时的申请轮次和状态。默认从最新评论开始，每页 30 条，支持按轮次筛选及加载更早评论。
3. 评论草稿仅保留在当前浏览器页面的内存中，按租户、账号和申请隔离。切换视图后可继续填写；刷新或关闭页面会丢失未发送内容，浏览器离开提示会涵盖这些草稿。
4. 申请在填写时被修改或审批后，旧评论草稿不会自动绑定到新版本。重新加载申请、核对内容，并明确选择使用最新版本后才能继续。只读状态仍保留未发送正文。
5. 发送结果未知时，通过现有请求恢复入口核实原操作；原正文、路径和幂等键保持不变，不能借重试悄悄改写正文。恢复成功后只清除与原请求一致的草稿。

不支持编辑或删除历史评论、附件、@ 提醒和站外推送。评论作者身份本身不会增加申请访问权限。

## DDD 职责与数据

- `Application.requireCommentContext`：聚合负责核对版本和当前可评论状态。
- `ApplicationComment`：不可变记录，保留服务端时间、认证作者和当时的上下文。
- `ApplicationCommentService`：在已授权的申请上编排查询或追加，不改写申请聚合。
- `ApplicationCommentController`：复用申请详情的实时可见性；幂等回放也先授权，不能用旧请求重新取得已失去权限的正文。
- `JdbcApplicationCommentRepository`：始终限制租户和申请，使用时间及 UUID 的稳定倒序分页；条件插入再次匹配已核对的申请版本、状态和轮次，避免保存已经过时的上下文。

V13 只新增 `application_comment` 及查询索引，不搬运审批意见，不补造旧评论，不改写申请和迁移历史。评论与幂等成功响应共用事务，失败不留半条记录。H2 和 PostgreSQL 共用相同迁移。

## API

`GET /api/v1/applications/{id}/comments`：支持 `roundNo`、`limit`（1—100，默认 30）、`cursor`；未知参数或不合法游标返回 400。游标绑定租户、账号、角色、申请和轮次，不能跨上下文复用。每页重新授权，不可见返回 404。

`POST /api/v1/applications/{id}/comments`：必须带 `Idempotency-Key`，正文为 `content` 和 `expectedVersion`，成功 201。版本不符为 409，当前状态不可追加为 422。重复原请求可回放原成功记录，即使后来申请结束，也不会再次写入；失去申请查看权后回放仍被拒绝。

末页明确返回 `nextCursor: null`。页面按纯文本渲染评论，任何 HTML 内容均以文字展示。完整契约见 [openapi.json](../agentflow-server/src/main/resources/api/openapi.json)。
