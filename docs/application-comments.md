# 申请协作评论

待办详情和申请详情提供“协作评论”。当前开放审批中申请的追加评论；已批准、驳回、退回、撤回等状态只读。评论是沟通记录，不替代批准、退回、驳回等审批意见，不改变申请版本、轮次、审批结论或引擎任务。

## 使用方式

1. 打开有查看权限的申请，在“协作评论”输入补充说明，点击“追加评论”。正文为 1 至 4000 个字符的非空白纯文本，服务端去掉首尾空白。
2. 记录显示真实作者、时间，以及记录时的申请轮次和状态。默认从最新评论开始，每页 30 条，支持按轮次筛选及加载更早评论。
3. 评论草稿仅保留在当前浏览器页面的内存中，按租户、账号和申请隔离。切换视图后可继续填写；刷新或关闭页面会丢失未发送内容，浏览器离开提示会涵盖这些草稿。
4. 申请在填写时被修改或审批后，旧评论草稿不会自动绑定到新版本。重新加载申请、核对内容，并明确选择使用最新版本后才能继续。只读状态仍保留未发送正文。
5. 发送结果未知时，通过现有请求恢复入口核实原操作；原正文、提醒名单、路径和幂等键保持不变，不能借重试悄悄改写正文。恢复成功后只清除与原请求一致的草稿。

支持明确选择本轮已有读取权限人员发送站内 @ 提醒，详见下方规则。历史评论保持只追加；评论附件和站外推送尚未开放。评论作者身份本身不会增加申请访问权限。

## DDD 职责与数据

- `Application.requireCommentContext`：聚合负责核对版本和当前可评论状态。
- `ApplicationComment`：不可变记录，保留服务端时间、认证作者和当时的上下文。
- `ApplicationCommentService`：在已授权的申请上编排查询或追加，不改写申请聚合。
- `ApplicationCommentController`：复用申请详情的实时可见性；幂等回放也先授权，不能用旧请求重新取得已失去权限的正文。
- `JdbcApplicationCommentRepository`：始终限制租户和申请，使用时间及 UUID 的稳定倒序分页；条件插入再次匹配已核对的申请版本、状态和轮次，避免保存已经过时的上下文。

V13 只新增 `application_comment` 及查询索引，不搬运审批意见，不补造旧评论，不改写申请和迁移历史。评论与幂等成功响应共用事务，失败不留半条记录。H2 和 PostgreSQL 共用相同迁移。

## API

`GET /api/v1/applications/{id}/comments`：支持 `roundNo`、`limit`（1—100，默认 30）、`cursor`；未知参数或不合法游标返回 400。游标绑定租户、账号、角色、申请和轮次，不能跨上下文复用。每页重新授权，不可见返回 404。

`POST /api/v1/applications/{id}/comments`：必须带 `Idempotency-Key`，正文为 `content`、`expectedVersion` 和可选的 `mentions` 账号数组，成功 201。版本不符为 409，当前状态不可追加为 422。重复原请求可回放原成功记录，即使后来申请结束，也不会再次写入；失去申请查看权后回放仍被拒绝。

末页明确返回 `nextCursor: null`。页面按纯文本渲染评论，任何 HTML 内容均以文字展示。完整契约见 [openapi.json](../agentflow-server/src/main/resources/api/openapi.json)。

## 本轮 @ 提醒

- 输入正文后点击“@ 选择或核对提醒对象”，可按账号搜索和翻页，明确勾选最多 20 个不同账号。仅在正文写 `@manager` 不触发提醒。
- 可选范围来自本轮申请人、当前未完成任务的有效接收人、本轮真实办理者；排除发送者自己。管理员身份不自动加入目录，只有抄送快照权限的人员不具备评论读取权限。
- 当前账号、申请或版本改变时清除旧核对结果。明确将草稿更新到新版本时保留正文、清空旧提醒选择。旧轮次办理者不会自动进入新轮次目录。
- 发送时锁定申请并重新检查发送者可见性、版本、状态和接收人资格。已停用或离开本轮范围的账号返回 `409 / COMMENT_MENTION_UNAVAILABLE`，整条评论不保存，刷新名单后重新选择。
- 评论、提醒和幂等记录共用事务。提醒落库失败全部回滚；原键回放成功记录不会再次提醒。回执正文、申请、版本和名单无法核实时，前端保留原请求恢复入口，不能报告成功。
- 消息中心显示“有人在评论中提及你”，只保存通用提醒、原申请标题、单号、轮次和操作者，不复制评论正文。打开原申请仍按当前权限检查，提醒本身不授予权限。

`GET /api/v1/applications/{id}/comments/mention-options` 支持 `q`（账号子串，不区分大小写）、`afterUser`（原页末尾账号）和 `limit`（默认 30，最大 50）。响应含 `applicationId`、`roundNo`、`applicationVersion`、有序账号 `items` 和可选 `nextAfter`；禁用缓存。查询只读取当前可提醒范围，不发送通知。

调用链为 `ApplicationComments → ApplicationCommentController → ApplicationCommentService → CommentMentionDirectory / ApplicationCommentRepository / InboxRepository`。Controller 限定请求格式并检查申请权限；聚合保留可评论状态和版本规则；目录服务组合当前任务、真实办理事实和人员启停信息；应用服务在根申请到子申请的既定锁顺序下编排同一事务。提醒不会更新审批聚合、任务或审计结论。

V91 仅向原评论表增加 `mentions_json`，历史评论默认空名单，不补发旧正文中的 @。旧客户端可省略名单，升级前已保存的幂等回执继续原样回放。旧迁移保持不变。
