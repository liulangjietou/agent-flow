# 付款结果与财务异常通知

这是 F17 的员工付款阶段记录。员工借款和费用报销的付款操作，以及付款操作创建前的出纳请求检查异常，现在可以产生最小站内消息及外发意向，并从消息读取对应的原授权。F17 仍为 OPEN；供应商付款及其他财务异常的通知尚待接通，固定安装包与环境验收也未完成。

## 调用链与职责

1. `PaymentOperationService` 和已存在的付款争议处置服务保存原付款状态后，在原事务中发布 `PaymentOperationChanged`；`PaymentExecutionRequestService` 保存原出纳请求状态后，在原事务中发布 `PaymentExecutionRequestChanged`。
2. `PaymentNotice` 根据已经保存的领域状态选择事实类型。它只决定通知语义，不修改银行结果、审批结论、资金金额或结算状态。
3. `PaymentNotificationService` 投影最小消息，交给 `JdbcInboxRepository`。原付款、消息和外发意向在同一事务提交；外部发送仍由通知工作进程执行。
4. 读取走 `PaymentNotificationController → PaymentNotificationAccess → VoucherAccess / PaymentAccess`。通知服务负责消息归属和原付款定位，财务服务负责既有角色、法人和敏感字段权限。
5. 消息页面先读取原付款详情，再由用户明确进入原申请轮次或原出纳付款。读取、刷新和页面导航均不发起付款，也不自动标记已读。

受影响场景包括员工借款放款、报销付款、登记前账户或来源检查、超时和租约恢复、银行查无或冲突、资金退回，以及原授权结束后的历史消息读取。既有审批、代理、核减和个人投递功能继续走原入口。

## 事实和去重

| 原付款事实 | 消息类别 | 对用户的表达 |
| --- | --- | --- |
| 已确认成功、失败、资金退回 | `PAYMENT_RESULT` | 分别说明收到成功、未成功或退回回执；三者不能混用。 |
| 网络结果未知、查无、回执冲突 | `PAYMENT_ATTENTION` | 要求核对原交易，不提示自动重新付款。 |
| 新发送前授权过期、来源或账户变化 | `PAYMENT_ATTENTION` | 说明尚未开始的新发送已经停止，不声称银行付款失败。 |
| 发送前检查暂时不可用 | `PAYMENT_ATTENTION` | 说明需要检查原记录，保留原检查失败分类。 |
| 正常排队、检查、发送、查询、银行处理中、主动复查 | 无新消息 | 不把正常进行中的操作误报成异常。 |

事件键为 `employee-payment:<原付款授权 UUID>:<事实类型>`，并沿用消息表的租户、接收人和事件键唯一约束。同一原授权的同类事实只通知一次；登记前检查与其后的付款检查共用同一身份。更高查询版本、重复事件和已经失效的迟到执行者不增加重复消息。不同事实各自保留，例如成功后发生资金退回。

登记请求的 `BLOCKED`、`VOIDED`、`EXPIRED` 和带失败分类的 `QUEUED` 分别投影账户复核未通过、来源变化、授权过期和检查暂不可用。正常排队、检查及 `READY` 不产生异常消息。此时可能尚无付款操作，详情仍明确显示“尚未发送付款”，不会构造银行回执或资金结果。

本阶段不向历史付款批量补发消息。新状态事件按上述规则投影。没有新增表或迁移，原付款定位保存在既有事件键中，读取时严格验证规范 UUID、事实类别、申请和轮次绑定。

## 接收人和当前权限

- 接收人仅为原收款员工、原财务授权人和原执行出纳。人员须仍在可信组织目录中有效；财务和出纳还须保留原法人的有效任职。不会广播给管理员或同角色所有人。
- 付款命令尚未登记时，原出纳从该授权的持久请求读取；没有原请求就不能推定出纳身份或授予详情权限。
- 站内消息采用固定标题和最小正文，不复制申请标题、金额、账户、指令摘要或银行回执内容。
- 外发意向沿用本人通知偏好、收件绑定和原同意版本。领取或重试外发前，重新检查原参与关系和当前人员、法人任职；失效意向抑制发送。
- 读取 `GET /api/v1/notifications/{id}/payment-target` 必须是原消息接收人，且通过当前原业务权限。接口不接受查询参数，成功响应为 `Cache-Control: no-store`。
- 申请人和财务必须通过原轮次财务字段读取权限；财务还需显式 `FINANCE` 角色及当前法人任职。出纳必须通过显式 `CASHIER` 角色及法人范围，只取得既有最小付款视图。
- 后台投递没有当前登录会话，不推断外部 IdP 的实时角色；最小通知不授予财务数据读取权。打开详情时，原业务入口重新执行当前认证角色与字段检查。
- 接口以事件键中的原付款号读取，不采用“该轮最新授权”。原授权结束、同轮重新授权后，旧通知仍展示旧付款及其当前记录。

## 页面和验证边界

消息中心新增“付款结果更新”和“付款执行需核对”，点击“查看原付款”后才读取详情。身份或消息切换会清空数据并取消旧请求，迟到响应不能回填；失权、损坏响应和超时不能保留可导航的旧详情。出纳入口可定位目录第一页以外的原付款。

范围验证记录见 [员工付款阶段证据](evidence/payment-notifications-employee-20261003.json)与[登记前检查阶段证据](evidence/payment-request-notifications-20261003.json)。后者包含 132 项不同的 Java 用例和 50 项前端用例，覆盖实际领域事件和数据库回滚、原角色与法人权限、未发送请求及跨阶段去重、同轮重新授权后的原记录绑定、实际 Vue 组件的加载/切换/导航，以及已有消息和批量付款的关联回归。

本阶段先以一个失败用例复现“请求已阻断但没有通知”，再接入原事务事件。最终 Java 范围测试 126 项与单独执行的 6 项嵌套批量测试没有重复计数。Web 生产代码与 OpenAPI 文件未改变，复用前阶段已通过的构建、类型检查和契约清单证据，并核对相应源文件保持；本阶段重新执行了接口契约测试。

这里的 HTTP 权限测试通过 Spring MockMvc 执行，页面验证使用编译后的实际 Vue 组件与模板。它们不替代独立安装包运行、真实浏览器或 PostgreSQL 验收，也不证明真实企业资金系统或通知平台已联调。
