# 批量付款

出纳可将同法人、同币种、同资金目标的 1–25 笔借款或报销授权登记为一个批次，并明确选择所有成员共同可用的出款账户及其版本。批次保存原授权与执行请求的关联；资金结果仍逐笔展示。

## 调用链与职责

- 调用方：“出纳付款 → 批量付款”页面和 `POST /api/v1/payment-batches`。
- 下游：当前出纳任职和职责分离 → 按原申请编号排序加锁 → 原 `CashierPaymentActions.EXECUTE` → 批次及成员原子保存 → 原账户复核工作器 → 原付款工作器 → 借款到账或报销结算。
- 影响场景：混合借款与报销、版本过期、重复或重叠批次、登记后单笔授权作废、账户变更、银行结果未知和原请求恢复。
- 批次实体负责不可变成员、共同范围及精确合计；应用服务负责跨原申请的锁顺序和事务；既有单笔领域继续负责付款状态。批次没有单独的资金状态机或工作器。

## 登记与执行

每个成员只提交原授权编号和已展示版本。服务端从授权读取金额、收款人、法人和资金目标，不接受客户端金额、账号、租户或自报回执。未知字段与重复成员在入口拒绝。

登记在一个本地事务内逐笔调用原出纳用例，保存原执行请求、逐笔审计、批次和幂等回执。任一版本、权限、业务来源、账户选择或数据库成员约束失败，整批回滚；排序锁定避免两个重叠批次按不同勾选顺序死锁。事务中不调用外部资金系统。

成功返回 `202` 仅表示意图已登记。提交后，每笔独立复核当前账户、授权和业务依据；某笔失效不会把其他有效付款一起作废。查询和明确查无后的原号重发继续使用原单笔入口。批次不会新增银行交易编号，也不能把多笔状态合成为“全部到账”。

同幂等键和正文回放原批次；同键修改正文返回冲突。新键不能重复登记已选择的原授权。回放前仍检查当前出纳角色、法人任职及职责分离。

## 持久依据与权限

V75 新增 `payment_batch` 和 `payment_batch_item`，并为原执行请求添加组合唯一键。成员同时引用第一版原授权、第一版请求修订及请求与授权的实际绑定；同授权和同请求分别只能归入一个批次。详情重读初始修订并核对批次，不要求当前单笔停留在初始状态。

列表在 SQL 分页前按当前有效法人任职过滤；详情仍使用原出纳最小付款投影。`ADMIN` 和 `FINANCE` 不自动获得出纳权限。摘要和详情不暴露目标摘要、完整账户或完整业务申请。合计采用十进制字符串，可超过单笔金额上限而不损失分位精度。

| 接口 | 用途 |
| --- | --- |
| `POST /api/v1/payment-batches` | 明确登记批次；正文为 `items`、`debitAccountReference`、`debitAccountVersion`、`comment` |
| `GET /api/v1/payment-batches?limit=25&beforeId=...` | 当前出纳法人范围内的历史批次，默认 25、最多 100 条 |
| `GET /api/v1/payment-batches/{id}` | 原成员与当前独立付款状态 |

页面逐笔读取当前账户目录，只展示引用、版本、币种及脱敏展示一致的交集，必须人工选择。账户读取、最终确认和实际登记分开；取消不写入，双击不重复提交。失联时通过现有“未确认操作”恢复原正文和幂等键。成员、身份或视图切换会废弃旧响应。

## 当前验证与未完成部分

领域相关 11 项、H2 服务端付款与契约 55 项、PostgreSQL 流程及 V74 → V75 迁移 50 项通过；测试范围重叠。前端 36 项、构建、后端打包、作者检查与 OpenAPI 静态检查通过。视图切换后迟到刷新打开旧批次的问题先由失败测试复现，再通过请求序列约束修复。

隔离验收库从 V74 升至 V75，保留 133 张旧业务表的 1,538 行、5 份附件及 15 份原财务文件；910,799 字节备份通过读取校验。实际 HTTP 完成 100.00 元报销与 200.02 元借款组批，总额 300.02 元。每笔仅有一个执行请求和一次银行发送；原键回放没有新付款，报销达到结算完成，借款可用余额为 200.02 元。98 份业务响应通过 OpenAPI 校验，其中 10 份批次响应也通过实际前端校验函数。

执行后，1,537 行旧业务数据原文保持，票夹用量一行仅增加新发票原件的字节数和上传次数；原附件、原付款及会计命令保持，新记录独立追加。资金服务为本地合成服务，这些结果不代表企业银行联调。
