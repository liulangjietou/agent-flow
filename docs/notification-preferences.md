# 个人通知偏好

个人设置在消息中心中维护，只影响当前登录人的邮件和企业 IM 偏好。站内业务提醒始终开启，两个外部开关默认关闭。V92 偏好增量包含设置、变更历史和同事务外发意向；后续 V93 的 SMTP、受控绑定及本人查询／恢复接口和页面已完成本地验收，见[外部通知投递](notification-delivery.md)；[企业微信参考发送器](wecom-notifications.md)已完成后台和接口范围验证，运行及真实渠道验收继续。`PENDING` 不能解释为发送成功。

## 规则与职责

- `NotificationPreferences` 拥有本人开关、乐观版本和每个渠道的同意代次。修改一个渠道不撤销另一个渠道的同意；关闭后再开启产生新代次，旧消息不能复活。
- `NotificationPreferencesService` 编排设置保存、历史追加和旧意向抑制。并发初次保存只有一个版本获胜；设置和抑制失败都整体回滚。
- 现有审批、评论、抄送、任务与超时提醒继续从 `InboxRepository.append` 写入。`JdbcInboxRepository` 仅在本次首次插入站内消息时追加外发意向，并加入原审批事务。开启偏好或重复写入旧事件不会补发历史消息。
- 外发意向只保存站内消息标识、租户、接收人、渠道和原同意代次，没有复制标题、评论、表单、地址或凭据。站内已读不产生新的外发意向。

偏好属于接收人，管理员也不能通过该接口查询或替其他人修改。接口不接收地址、身份覆盖或站内关闭开关。邮件与企业微信账号绑定均来自受控部署配置，个人接口不能更换收件目标。

## 接口与页面

`GET /api/v1/notifications/preferences` 返回 `inAppEnabled`、`emailEnabled`、`enterpriseImEnabled`、`version`、`updatedAt`。首次读取返回版本 0、空更新时间，且不创建数据库记录。读取和保存均禁止缓存、拒绝查询参数。

`PUT /api/v1/notifications/preferences` 必须提供两个布尔开关、`expectedVersion` 和原有幂等请求头。未知字段被拒绝；版本冲突返回 409。无变化保存不产生新历史，但也必须匹配版本。

同键恢复回放原成功回执，不重新执行设置。假设开启 v1 的响应丢失、另一会话后来关闭为 v2，恢复 v1 仍返回历史 v1 回执，当前设置继续保持 v2。页面随后独立读取当前设置，不把历史成功解释为当前开启。

消息中心明确展示外部接通条件与送达边界。读取失败、超时和版本冲突不开放旧版本保存；响应缺字段或回执与原选择不符时保留原请求。切换账号取消旧查询并隔离迟到结果。未确认写入通过现有恢复入口处理，不自动生成新请求。默认值提示标记为“上次读取时”，避免未知写入之后误述当前状态。

## 数据升级与发送边界

V92 新增 `notification_preferences`、`notification_preference_change` 和 `notification_dispatch`，不回填老消息或改写历史评论。

审批事务内不锁定多个接收人的偏好行，避免不同通知顺序造成锁竞争。V93 关闭设置会抑制可见的旧 `PENDING`、`RETRY_WAIT` 意向；并发入队仍可能落入旧代次。SMTP 后台在开始发送前锁定并复核当前代次、账号启用状态、本人消息归属和固定绑定，不只凭队列状态发送；实际网络操作放在事务外。已经开始的发送无法通过关闭开关召回，真实回执仍会保留。重试、未知结果、公开恢复入口和完整本地运行验收见[投递实施](notification-delivery.md)。
