# 流程版本通知文案

流程管理员可在设计器中配置申请提交、退回和最终批准时发给申请人的站内通知文案。配置参与保存、撤销/重做、版本比较、发布和模板文件导入导出；已发布版本只读，已有申请继续使用创建时绑定的版本。

## 使用与约束

设计器的“站内通知文案”提供三个输入框和纯文本预览。每项最多 500 个 UTF-16 字符单元，保留换行、回车和制表符，去掉首尾空白，拒绝其他控制字符。留空时仍显示平台事件、申请标题、单号和轮次。

文案是管理员配置的固定文本。HTML 标签与 `${amount}` 等内容按原文展示，不执行脚本、表达式或表单字段替换。该配置只作用于申请人的提交、退回和批准消息；消息接收规则与申请访问授权继续由原有服务决定。

请假、用印、合同审批三个内置模板更新到模板版本 2，复制时带入原有说明中的三类文案。已有版本 1 副本不自动升级；请求旧目录版本时返回版本冲突，用户查看最新模板后重新复制。

## 调用链与 DDD 职责

配置链路为 `DefinitionNotificationTexts` → `DefinitionController` → `DefinitionApplicationService` → `DefinitionDraft` → `JdbcDefinitionDraftRepository`。`NotificationTexts` 值对象约束文案内容；定义聚合负责同一 revision 下的更新及发布后不可变性。模板复制应用服务将目录文案转换为同一值对象，不另建模板执行链路。

申请创建时，`ApprovalApplicationFacade` 从已选定的准确发布定义取得文案，交给 `ApprovalApplicationService` 创建申请。`Application` 保存不可变文案快照；仓储后续更新申请状态时不改写它。退回或撤回后重提仍使用该申请原快照，不查询后来发布的新版本。

审批事件由 `ApprovalNotificationService` 读取申请快照，生成带 `content` 的 `InboxMessage`，与原审批事务一起落库。消息阅读状态由消息对象管理；标为已读不改变文案。`NotificationInbox` 使用 Vue 文本插值展示内容，不解析 HTML。领域层不引入 Flowable 类型。

## API 与文件兼容

定义创建、更新、查询和比较接口新增 `notificationTexts`：

```json
{
  "submitted": "已收到申请，请等待审批。",
  "returned": "申请已退回，请查看意见后补正。",
  "approved": "申请已完成审批。"
}
```

- 创建时省略配置，使用空文案。更新时省略或传 `null` 保留当前配置；传 `{}` 明确清空全部文案。只传某一项时，其他项设为空；不做单项补丁合并。
- 配置对象拒绝未知字段、非字符串值和超限内容；仍需要流程管理权限及原有幂等键。已发布定义不能直接修改。
- 版本比较接收完整配置快照；省略或传 `null` 表示空文案，可能产生与已配置发布版本的差异。它不采用更新接口的“省略即保留”语义。
- 消息响应新增可空 `content`。历史消息可缺省该字段，客户端保留统一事件显示。
- 当前设计器导出格式版本 2，包含 `process.notificationTexts`。读取格式版本 1 时保持原契约；不把 v2 属性塞入 v1 或静默丢弃不认识的配置。

## 数据迁移

V24 只增加三列：`approval_definition.notification_texts_json`、`approval_application.notification_texts_json`、`notification_inbox.content`。三列允许 NULL，不从当前模板回填旧流程、旧申请或历史消息；旧记录读取时使用空配置。

H2 迁移测试验证 V23 → V24 保留历史行和旧迁移记录，重复迁移不执行新操作。独立 PostgreSQL 验收先用上一版本程序创建真实待办，再停机升级；逐表比较 66 张业务及引擎表的原字段摘要，原字段和旧 Flyway 历史均保持一致。对比只排除上述三列，包含评论的既有 `content` 字段。

其他未发布开发分支有同号迁移时，应在后续实际整合时调整未发布迁移编号，不能修改已进入主线的 V24。
