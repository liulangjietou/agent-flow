# 批准意见填写与确认

在待我审批打开任务，点击“批准申请”后先进入意见表单。意见选填，确认后提交当前节点的批准；取消只关闭并清空表单。全部同意会签仍需所有人完成批准，当前节点批准不等于整张申请已批准。

意见输入框在表单打开后获得焦点，取消后回到原动作按钮。任务、版本或账号切换时清空旧表单；发送过程中以及原请求结果待确认时，沿用现有全局操作锁。连接中断后可恢复原请求，保留同一任务、版本、意见和幂等键。意见会显示在已办记录和申请操作审计中。

## 原因与职责

原界面把 `APPROVE` 与领取、释放一并直接执行，后端虽已接受 `comment`，审批人却无法从 UI 输入批准意见。原前端测试验证请求构造和回交，没有执行实际组件的批准按钮逻辑。

调用方 `TaskActions.vue` 通过 `App.performAction` 和 `api.taskAction` 提交已有任务动作契约。下游仍由 `TaskController` 执行幂等入口、`FlowableTaskFacade` 编排授权/版本/领域状态/引擎完成，`JdbcTaskAuditAdapter` 保存实际意见。新增内容属于表示层交互，没有新增领域规则、接口、数据库迁移或依赖。

批准意见依照现有契约保持选填。退回、驳回和回交仍须填写意见；待回交的受托人不能批准，原责任人接回后可填写自己的批准意见。领取和释放保持原直接操作。

## 验证

先增加最小回归，直接编译并运行真实 Vue 组件的 setup：首次点击批准预期不产生事件，修改前实际发出 `APPROVE`、`comment=undefined`，测试失败。修复后补充取消、空意见、任务/版本/账号切换、操作锁、会签/回交快照检查；请求恢复检查同时覆盖 APPROVE 与 RESOLVE。

Node 测试运行 Vue 组件逻辑，不渲染浏览器 DOM；焦点、标签、窄屏和真实审批提交分别通过内置 Chromium 验证。测试不替换实际生产组件的 setup，不复制它的动作判断。

- 前端：247 项通过，64 个 OpenAPI 操作校验通过；`vue-tsc` 与生产构建通过。
- 工具检查：19 项通过。259 个 Java 文件、426 个命名类型作者标签完整。
