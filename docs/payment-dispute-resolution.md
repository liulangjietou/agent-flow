# 原付款争议裁决

更新：2026-09-29。本阶段实现原银行付款的人工裁决，使用已持久化的原交易对账回执；本地合成银行验收不代表企业银行联调。

## 调用链与职责

财务从原业务详情读取付款、最新对账候选和最后一次裁决，在填写对账凭据编号及原因后明确确认。`PaymentDisputeController` 在幂等回放前验证当前财务及原轮次完整字段权限；`PaymentDisputeService` 取得原申请/财务聚合锁，再核对实际操作者、授权版本和付款版本。

`PaymentOperation` 决定当前争议是否允许采用候选终态；历史修订查询提供最早确认到账及曾出现资金事实的依据。`PaymentDisputeResolution` 保留人工决定和裁决前后版本。付款、裁决凭据、审计、借款解冻和适用的报销恢复在同一个短事务内完成，没有外部 HTTP 调用或新的付款命令。

调用方是财务页面；下游是原支付修订仓储、借款余额、报销结算、原预算消费记录及付款凭证准备；影响场景包括迟到回执、银行更正、普通重复查询、已消费资源、预算迟到确认、归档后争议和财务权限撤销。原出纳与申请人不能裁决自己的付款，管理员仍受原字段权限约束。

## 采用的业务规则

- 仅 `RECONCILING` 允许裁决；`UNKNOWN`、查询中、查无和处理中都不能被人工宣布为成功或失败。
- 候选只能来自最新持久对账回执，观测时间五分钟内、外部版本达到已见最高版本，且没有倒退观测时间。过期时先查询原交易，再重新核对。
- 支持确认 `SUCCEEDED`、`FAILED` 或 `REVERSED`。客户端只携带展示版本、结果枚举、对账凭据编号和原因，不提交银行回单、金额或账户。
- 原交易编号保持一致；历史已有无争议到账时，成功候选必须保留原金额、账户、到账时间及回单编号。另一张回单不能覆盖原到账依据。
- 任何历史修订出现过到账或退回，包括后来被覆盖的冲突候选，都不能确认“失败”并释放占用。需要资金系统给出可核验的原交易事实。
- 确认失败也不自动结束原授权，财务仍需单独执行安全结束，重新付款仍需新授权和独立出纳确认。
- 确认退回不恢复旧发票、额度或借款余额，也不释放原付款占用。实际退款调整、凭证冲回和借款结清继续由各自业务处理。
- 新争议不会继承上一次裁决。历史决定只作为历史显示，普通成功查询不会解除资金冻结。

## 下游恢复

借款仅在明确成功裁决后解除 `PAYMENT_REVIEW`，并核对与原放款身份、金额、到账日和约定还款日一致。限额、预留和已核销账本原样保留；重复查询不重置余额。

报销恢复重新验证原批准、纸件、挂账和付款。未消费资源回到待核销；已消费资源按原预算消费操作恢复为等待确认、已拒绝或已结算，均不重复扣减。预算已经实际消费时不会再要求其处于“冻结待消费”阶段；当前预算状态由原操作证据判断。独立凭证或批准争议继续冻结。

付款凭证继续使用首次确认成功的修订和原回单。原准备仍可继续执行，已经阻塞的准备沿用现有财务重试入口；裁决不替换已登记的会计命令。已封存报销档案保持原 JSON、摘要和原件，当前依据提示可以恢复，原包不会重新生成。

## 数据与接口

V53 增加仅追加的 `payment_dispute_resolution`，按同租户原付款关联裁决前后连续修订，每个争议版本只允许一份决定。外键阻止删除关联证据。原付款输入、原冲突修订和旧授权均不改写。JSON 保留外部回执完整时间精度，关系时间列按数据库微秒精度存储及比较。

| 接口 | 行为 |
| --- | --- |
| `GET /api/v1/applications/{id}/payments?roundNo=1` | 财务可见最小对账候选、拒绝原因和最后裁决；申请人没有裁决材料投影 |
| `POST /api/v1/payments/{id}/dispute-resolutions` | 严格版本、明确终态及人工凭据；幂等、当前权限复核，响应 `no-store` |

审计动作 `PAYMENT_DISPUTE_RESOLVE` 记录操作者、理由和前后状态；裁决表保存对账凭据编号。页面不展示完整账号、命令摘要、网关配置或原因自由文本。读取及刷新不触发决定，切换身份会清空未提交凭据并丢弃迟到响应。
