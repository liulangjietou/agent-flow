# 结构化财务实施

2026-09-28 开始实施。依据项目原 `doc/05-费用报销领域设计.md` 及当前 `docs/remaining-implementation-plan.md`；D1–D6 和保守默认已经用户授权。此文是实际开发记录，不把未配置外部接口或未验收环境标记为完成。

## 事实源与调用链

费用报销页 → 费用核算应用服务 → `ExpenseReport`、发票、事前申请/借款余额 → 审批申请用例。`Application` 只拥有审批状态、轮次与任务，报销明细、含税金额、核定额和应付金额以 `ExpenseReport` 为准。结构化业务只通过自己的写入入口操作，通用表单入口须拒绝绕过财务校验。

外部预检、账户、汇率和发票查验在事务外获取；本地事务复核申请与财务版本、占用发票和余额、冻结快照、启动审批并写预算消息。预算冻结、凭证和支付由持久任务在事务外调用。外部状态未知时保留原幂等号并对账，不能盲目再次付款。

核减调用方是当前财务待办处理人。应用服务负责当前任务、申请状态、组织权限和职责分离；报销聚合保证只减不增、分摊平衡、税额不超含税额、冲销额不超过核定额，并追加差额记录。结算拥有独立状态和付款授权，采纳 Agent 摘要不参与这些状态转换。

受影响场景：草稿/补正、提交与重提、跨币种明细、重复发票、并发占用、预算冻结失败、签收、核减、零应付结算、外部账户变化、凭证失败、支付回调乱序、撤销与归档；通用表单及旧申请保持原事实。

## 金额与核减规则

金额采用非负定点十进制；按当前费用设计支持两位金额精度，入参超出精度直接失败，不静默四舍五入用户填写的金额。汇率仅在提交时应用，按行四舍五入至两位后汇总。币种必须显式匹配；汇率来源、日期和币种对随轮次冻结。

成本分摊先校验原币合计等于行申报金额。本币折算或核减后的金额按原始分摊权重使用最大余数法分配整分，并按原输入顺序打破余数相同的平局，保证分摊与核定行金额严格相等。

税额不内置推断税率或抵扣政策。原币税额必须不超过含税金额；可抵扣资格由版本化政策/查验事实提供。核减时财务明确核对核定税额，服务端要求金额和税额均不增加、税额不超过核定含税金额；不根据模型结果或通用比例宣称完成税务校验。

制度核算额与可抵扣额使用法人本位币。冻结时将原币含税额和申报税额逐行折算，与制度结果核对；已核定的本币可抵扣额直接保存，不再次汇兑。外币回归通过真实 HTTP 制度适配器将 USD 100 / 税 USD 6、汇率 7.1 得到的 CNY 710 / 税 CNY 42.60 送入冻结聚合，防止领域测试夹具与真实端口口径分离。原始明细和已有历史快照保持原样。

草稿明细允许多币种；冲销使用法人本位币。核减后冲销超过核定总额时，从已冻结的选择顺序末尾依次下调，保留每笔变化；对应余额预留和预算释放由应用服务同步编排。任何错误必须发生在聚合状态整体替换之前，不能出现前几行已经核减而后续一行失败的半更新。

## 已完成的财务基础与草稿 API

`Money`、`ExpenseLine`、`ExpenseReport` 现已实现两位金额、行汇兑、分摊守恒、费用/税额独立核减、借款冲销收敛及不可变轮次。核减不会改变提交时的费用、汇率、制度与账户证据。`EmployeeAccountSnapshot` 只保存外部引用、掩码和绑定摘要，不保存完整卡号。

V33 给审批申请增加不可变 `BusinessReference(EXPENSE, id)`，旧表单的绑定保持空，不根据历史流程名称猜测财务业务。数据库外键同时核对租户、申请、业务类型和报销标识；财务版本与审批版本分开更新，每次财务写入追加 `expense_report_revision`。申请与财务写入共用短事务，追加证据失败时整体回滚。

草稿入口为 `POST /expense-reports`、`POST /expense-reports/{id}/revise`，读取使用 `GET /expense-reports/{id}?roundNo=`。金额 JSON 为 `{"value":"10.00","currency":"CNY"}`，拒绝 JSON 浮点数、科学计数法和未知金额属性。普通申请的创建、编辑、提交、撤回及作废不能处理结构化费用，返回 `USE_BUSINESS_ENDPOINT`。

结构化费用定义必须包含 `expenseDetails`、`amount`、`currency`、`overPolicy` 四个必填字段。完整费用是一个敏感字段组 `expenseDetails`，必须声明敏感标记并由节点显式授权；隐藏或脱敏均不能通过费用 API 取回原文。管理员无明细豁免。`amount`、`currency`、`overPolicy` 只由已核定财务轮次派生，草稿不填猜测值。旧审批人只能按原轮次权限读取原财务快照，不能读取后续补正草稿。支付账户的内部引用和摘要不返回页面。

本节是草稿基础阶段的记录。读取权限测试中的冻结事实只用于投影验证；后来完成的正式提交与实际审批链路使用独立消费者验收，见 [正式报销提交](expense-submission.md)。业务页面及结算仍按上表继续实施。

验证记录（2026-09-28）：领域 15 项；草稿 API、既有审批安全、重提与字段权限 39 项；H2 升级与 OpenAPI 契约 6 项；PostgreSQL 草稿与升级 11 项；OpenAPI 101 个操作、166 个结构、36 个请求示例。范围交叉的 H2/PostgreSQL 测试不重复累加为功能数量。证据位于 `docs/evidence/expense-foundation-20260928.json`。

## 已完成的资源模型与数据库互斥

`Invoice` 分别维护查验和占用状态。有效查验绑定原件摘要、规范票号、所属法人、金额税额及有效期；查验失败保留已有占用，既不能视作成功，也不能释放其他单据的权利。核销后不可释放。重提迁移使用完整的报销单、轮次及行归属；原轮次释放不能影响新轮次。

`EmployeeAdvance` 以实际放款引用形成余额；`ExpenseRequest` 以当前租户、同一申请人的已批准申请形成分行额度。数据库锁定批准申请直到首次额度落库，草稿不能形成可用额度。二者组合使用 `ReservedAmount`，分别保留有效预留和逐笔核销归属，核销后同一归属不能重新预留。事前申请关闭后不能增加用量，但可以核减、释放、迁移不增额的原占用及完成原核销。已配置的容差仅计算一次，向下取整到分。

V34 使用 `finance_resource` 和 `finance_resource_revision` 保存不可变来源、乐观版本及追加证据。`finance_amount_use` 规范化保存预留/核销，外键阻止跨租户报销归属。发票使用 `invoice_active_claim` 的 `(tenant_id, invoice_key)` 主键约束有效占用，而非在 H2 无法直接共用的 PostgreSQL 部分索引；占用与已核销的互斥效果相同，释放时移除现行键，历史版本记录仍保留。两个不同上传文件的相同规范票号也会争抢同一数据库键。

验证增加资源领域 14 项、仓储并发 10 项、草稿回归 10 项、H2 升级 1 项；PostgreSQL 仓储并发 10 项及升级 1 项。先失败再修复的回归包括核销后重新预留的绕过、未批准申请形成额度。发票重复文件的竞争使用两个不同聚合和真实并发事务，不依赖同一对象的乐观锁来冒充号码去重。

资源基础阶段的仓储集成测试使用合成批准申请和放款引用。后续原件上传、持久验票、制度端口与正式提交已分别接入；真实企业事前批准和放款源仍待接入验收。证据位于 `docs/evidence/expense-resources-20260928.json`。

## 已完成的财务只读端口

已实现按租户配置的真实 HTTP 财务目录、本人账户、法人汇率、制度判定与原件验票适配器。默认关闭，缺少配置明确不可用。目的地和凭据不能通过业务请求覆盖；响应须匹配租户、请求编号及业务事实，不能用重定向、过期数据或未知结果代替真实成功。网络调用禁止持有数据库事务，响应接收过程有体积与总耗时限制。

`GET /api/v1/finance/catalog` 返回当前员工的可用法人、类别、成本中心、项目和城市；拒绝任意员工或租户查询参数，设置 `Cache-Control: no-store`。账户值对象现在统一拒绝完整卡号冒充掩码。新增失败回归确认旧实现会接受完整号码；金额解析还修复了严格 JSON 模式下错误地重入根读取、误判正常后续字段的问题。

本次范围通过领域 19 项（包含既有核算 15 项）、服务端 42 项（网关 HTTP 11、配置 13、目录入口 3、草稿回归 10、OpenAPI 5）。公开契约为 102 个操作、172 个结构、36 个请求示例。无数据库迁移或页面变更；未声称企业服务或正式财务流程验收完成。协议和配置见 [财务网关说明](finance-gateway.md)，证据见 `evidence/finance-gateway-20260928.json`。下一步继续原件票夹、持久预检、提交及预算与结算编排。

## 已完成的持久验票

V36 保存本人发起的独立任务、固定原件与法人、输入发票版本和目标指纹；事务外调用实际 HTTP 网关。同一发票只有一个活动任务，结果必须通过租约和当前版本校验。真实业务拒绝与系统不可用分别记录，均不释放已有占用；超时任务不能被晚到结果覆盖。

排队后重启继续执行；已领取后崩溃则保留原租约，到期仅记录超时，新的明确请求才再次发送。打包服务在 PostgreSQL 与合成本机网关完成这两种恢复及显式重试，128 次 HTTP 请求包含状态轮询，最终 2 个成功、1 个超时任务及 9 条任务版本记录。相关测试、权限和迁移边界见 [持久验票说明](invoice-verification.md) 及 `evidence/invoice-verification-20260928.json`。

当前契约为 112 个操作、186 个结构、38 个请求示例。继续实施提交预检、预算、提交与结算和业务页面；本机合成查验不替代真实企业接口验收。

接入预检前修复外币口径衔接：领域负例及真实适配器消费者各 1 项先失败，修复后核算/端口契约 20 项、HTTP 网关/草稿 22 项通过。根因是旧领域测试用原币构造制度事实，既有网关测试仅使用人民币，未覆盖真实本位币结果进入冻结的路径。没有迁移或重新计算历史轮次，证据见 `evidence/expense-policy-currency-20260928.json`。

预算只读预检端口已补齐，按核定含税分摊发送精确本位币金额，不按借款冲销后的付款额占预算。结果绑定整个单据、轮次、财务版本、员工、法人、期间和分摊列表；预算不足、制度未配置、期间关闭与服务不可用分别处理。通过只表示检查时可用，完整预检任务及提交后预算冻结仍在后续编排，不能以该只读结果放行财务审批。


## 共享提交资源计划

`ExpenseSubmissionResources` 在不可变输入的副本上计算发票、事前批准额度和借款预留变化，供只读预检与最终提交复用。更换同票号原件先释放旧占用；同一批准行先执行减额再执行增额，允许 80/20 改为 90/10 的合法分配。关闭事前申请后只能迁移不增额的原归属；已核销的旧轮次不能利用尚余余额再预留。

计划返回每一步财务版本，由应用服务在单个事务内顺序保存，不能跳过中间审计版本。真实仓储测试验证最后一笔借款出现版本冲突时，发票占用、事前额度、报销冻结与追加证据全部回滚，其他单据已完成的预留保持原样。输入快照本身不会被失败的计划污染。

本阶段领域计划 8 项、既有核算/资源 30 项、仓储 10 项、H2 计划仓储 2 项及 PostgreSQL 同场景 2 项通过；数据库测试范围重叠，不相加为功能数。这是共享领域编排与仓储验证，尚未接入完整预检或提交 HTTP 入口。证据见 `evidence/expense-resource-plan-20260928.json`。
