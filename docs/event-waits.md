# 原生事件等待的后台接续

更新：2026-10-01。已实现精确契约版本的流程节点、原生消息订阅、内部事务消费及参与者只读接口。来源验签、持久收件、后台消费和管理员原号恢复随后已接通，见[签名收件](event-inbox.md)。**事件等待整体仍未完成**：管理、设计器与等待页面及完整浏览器验收继续实施；本地合成来源验证不代表实际企业来源已经接入。

## 调用链与职责

- 设计器或定义 API 保存 `EVENT_WAIT` 节点，必须同时提供 `eventContractKey`、规范正整数文本 `eventContractVersion`。纯领域校验拒绝缺省、最新版、表达式及配置在其他节点上的引用。
- 流程发布和每次申请提交／重提由应用服务锁定同租户的精确契约版本，并检查可用性。多个契约按业务键与版本的固定顺序加锁。契约不存在或停用时不能发布或发起新轮次。
- Flowable 适配器只生成原生中间消息捕获节点。消息名称由服务端生成，避开同一 BPMN 文档的流程、节点及连线标识；不会将来源名称或外部文本放进表达式。
- 内部 `EventWaitService.advance` 由可信持久收件编排调用。它先锁申请及其财务聚合，再锁引用的事件契约；申请、当前轮次、原生订阅、流程定义与执行、运行变量、来源、事件类型和信封版本全部一致才允许推进。
- 推进使用明确的执行标识，不广播消息，也不传入外部流程变量。已有人工审批意见必须保留；流程结束仍由原审批完成服务处理轮次、财务约束、审计及事务通知。

原生消息订阅的标识就是本次等待身份。不新增另一套等待状态表。成功后该订阅被消费；重复、并发请求和旧轮次消息都不能再次推进。依次到达两个引用同一契约的节点时，必须分别使用两个实际激活身份。

## 停用、暂停与失败

契约停用阻止新发布和新轮次发起。在审流程仍可保留真实人工决定并到达等待节点；停用期间不消费，恢复原契约版本后才可继续。流程暂停也不消费，原订阅身份保持。

引擎推进、申请版本、轮次完成、审计及通知共用事务。通知写入失败时原生订阅恢复，申请版本和通知均回滚；后续可以重试同一个内部命令。外部消息去重、可靠入库、消费标记及原失败恢复也已接入该边界，具体状态和管理接口见[签名收件](event-inbox.md)；失败展示页面继续开发。

## 已实现的读取接口

`GET /api/v1/applications/{id}/rounds/{roundNo}/event-waits` 使用原申请的参与者权限，要求明确正整数轮次且不接受查询参数，响应禁止缓存。每个条目只返回等待标识、节点名称及标识、契约键及版本、实际创建时间、暂停和契约启用状态，不返回表单或流程变量。

流程图读取识别 `EVENT_WAIT`。成功消费追加 `EVENT_RECEIVED` 审计，并进入原事务通知和 Webhook 机制；这条系统事实不能冒充人工批准。
