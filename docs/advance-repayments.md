# 借款还款与结清

本阶段把已到账借款、报销冲销和实际还款分开记载。原放款金额不变；未还款 = 原放款 − 已报销冲销 − 已还款。预留仍属于未还款，不能被另一笔还款占用。未还款归零才结清。

## 业务规则与调用链

借款详情的财务用户先输入原收款编号，由持久查询任务读取原法人、员工、借款和付款交易对应的资金及 ERP 事实。只有已经收款、且员工借款贷方分录已经入账的完整凭据才能确认。银行转账、现金收款和工资抵扣均由外部系统证明；平台不提供手工改金额、代扣工资或再次推送凭证的入口。

一次确认采用一笔完整外部收款，并归属一笔原借款；一笔借款允许多次部分还款。跨借款拆分收款需要外部提供各自明确的原借款收款与分录依据。

- 调用方：`AdvanceRepaymentStatus` → 查询、确认及历史 API；原本人资金列表展示独立还款与未还余额。
- 下游：原轮次字段权限、当前法人任职、原放款成功修订、财务网关只读端口，以及借款余额与还款仓储。
- 影响场景：已放款借款部分还款、全部结清、与报销预留并发、凭据重复、收款撤销、失权及请求恢复。

余额守恒、预留互斥和借款状态由 `EmployeeAdvance` 判断；查询租约和一次消费属于 `AdvanceRepaymentCheck`；跨原放款、人员、凭据和审计的编排由 `AdvanceRepaymentService` 承担。外部 HTTP 在事务外执行，财务确认在同一短事务保存余额修订、原凭据、查询消费与审计。

## 对外查询端口

沿用 [财务网关](finance-gateway.md) 的固定租户目标、认证、请求关联和严格结果信封，新增 `POST /advance-repayment`。这是只读请求，不发送 `Idempotency-Key`，不能产生扣款、记账或还款事实。

`data` 请求：

```json
{
  "advanceId": "11111111-1111-4111-8111-111111111111",
  "legalEntityId": "22222222-2222-4222-8222-222222222222",
  "employeeId": "alice",
  "paymentReference": "BANK-ORIGINAL-001",
  "currency": "CNY",
  "receiptReference": "RECEIPT-001"
}
```

所有身份字段都来自原放款，页面只提交 `receiptReference`。成功信封中的 `data` 回传完整相同 `request`，并包含：

| 字段 | 约束 |
| --- | --- |
| `status` | `NOT_FOUND`、`PENDING`、`CONFIRMED`、`REVERSED`；查无不表示还款成功 |
| `revision` | 查无必须为 0，其他状态必须为正整数；不能倒退到已观察的旧修订 |
| `observedAt` / `validUntil` | 查询时间已经发生，有效期大于观察时间且不超过五分钟 |
| `funding` | 确认或撤销时必填：`channel` 为 `BANK_TRANSFER/CASH/PAYROLL`，以及 `transactionReference`、精确 `amount`、`receivedAt` |
| `posting` | 确认或撤销时必填：`voucherReference`、`entryReference`、精确 `amount`、`accountingDate`、`postedAt` |

查无或待处理时 `funding`、`posting` 必须为 null。终态资金与分录金额必须相等、为正且使用原币种；收款时间不晚于过账，过账不晚于观察；确认时还需核对收款不早于原放款。外部适配器必须验证该分录实际冲减这位员工的这笔借款，不能用总额相同的其他会计分录替代。

已观察的资金及分录身份、金额和发生时间不可改写。合法的新查询可刷新观察时刻和有效期，但同一收款的原事实保持不变。允许的业务拒绝只有 `LEGAL_ENTITY_UNAVAILABLE`、`EMPLOYEE_UNAVAILABLE`；连接及协议失败保持不可用分类。

## 权限、接口与恢复

| API | 行为 |
| --- | --- |
| `GET /api/v1/advance-requests/{id}/repayments` | 原轮次完整借款字段可读后返回余额、当前财务自己的最新查询及最多 25 条已确认历史；支持 `roundNo`、`beforeId` |
| `POST /api/v1/advance-requests/{id}/repayment-checks` | `advanceVersion`、`receiptReference`、`comment`；202 只表示查询已登记，`repaymentId: null` |
| `POST /api/v1/advance-requests/{id}/repayments` | `advanceVersion`、`checkId`、`checkVersion`、`comment`；明确确认原查询，不传金额 |

写入要求 FINANCE 角色、原轮次完整字段可读、原法人当前有效任职且不是申请人。ADMIN、CASHIER 不自动取得财务能力。幂等回放前仍重查权限；请求结果不明时恢复原路径、正文及幂等键。所有响应 `Cache-Control: no-store`。

查询领取后租约为 90 秒；超时结束本次任务，不复用迟到结果。财务可以重新登记查询。确认要求最新查询、仍有效的原件和当前余额版本一致；同一借款下其他财务更新的收款观测也会使旧证据失效。多个并发确认只有一个能够消费原查询。

V54 新增查询、查询修订及不可变还款表。查询关联原放款成功修订，还款关联已消费查询修订和实际借款余额修订。同租户、同法人下收款编号、渠道资金流水、ERP 凭证与分录分别唯一。数据库失败时整个确认回滚。旧借款 JSON 缺少还款字段时按空还款及无还款争议恢复，升级不改写原余额或付款修订。

## 收款变化

已确认凭据在后续明确查询中变为查无、待处理、撤销或与原资金事实矛盾时，借款进入独立 `REPAYMENT_REVIEW`，可用余额归零；原还款及报销冲销保留。临时连接失败不直接创造撤销结论。后续查询恢复成功也不自动解冻，原付款争议裁决同样不能清除此冻结。

还款撤销的财务裁决及独立调账属于后续调整阶段。当前页面说明该状态并展示历史，不提供无依据清账或改写原凭据。没有接入真实资金系统、工资系统或 ERP 的环境不视为企业验收。

## 本地验证

领域范围 40 项、H2 服务端范围 33 项及补齐后的还款集成 13 项、PostgreSQL 范围 113 项、前端范围 62 项通过，范围有重叠。PostgreSQL 包含原付款 36 项、报销结算 63 项、还款 13 项和 V53→V54 升级 1 项。前端构建及 Java 作者检查通过；OpenAPI 为 167 个操作、294 个结构、56 个请求示例。

打包后 33 次实际 HTTP 验证及结清后 6 次读取/登录通过，28 份业务响应另经 JSON Schema 验证。原 300 元借款先通过接口确认 100 元现金还款，再经浏览器查询、核对并确认 200 元银行还款，最终已还 300、未还 0、状态 SETTLED。数据库保留两笔还款、两笔确认审计及 11 份查询修订，原付款 18 份修订和原付款/凭证命令摘要不变。

浏览器验证了查询不冲减、明确确认后结清、原凭据和分笔历史；窄屏实测为 500 CSS 像素、余额两列且无横向溢出。请求的设备宽度受浏览器缩放影响，不能把此结果写成 375 CSS 像素验证。

新增边界测试先复现并修复两处问题：翻页失权后上一页敏感资料未清空，以及查询回执的空 `repaymentId` 被全局 JSON 策略省略。证据、截图、测试范围及备份路径见 [阶段记录](evidence/advance-repayments-20260929.json)。
