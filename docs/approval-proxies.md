## 采用的业务规则

用户已授权按推荐方案开发，代理采用以下规则：

- 租户管理员具名指定原审批人、代理人、一个已发布流程版本、起止时刻和原因。新版本需要独立授权，发布或停用发起不会改写原代理范围。
- 双方必须是本租户仍在用、具有本地审批资格的人员。实际代理人办理时还必须拥有认证源授予的 `APPROVER` 角色；代理不会复制原审批人的角色。
- 有效期采用 UTC 时刻，包含开始、不包含结束，存储精度为微秒。允许开始时间早于创建，但创建前不产生追溯授权；结束时间必须晚于创建。到期直接失效，不等待调度任务。
- 同一原审批人、同一版本的未撤销授权区间不得重叠，前一条的结束时刻可以等于后一条的开始时刻。提前结束追加具名撤销和原因，原人员、版本、期限和创建原因不可覆盖；更换范围需另建记录。
- 只代理原审批人自己的原生任务权限，不递归继承他人授予他的代理。代理人同样受禁止自审批、前序批准人排除、会签独立人员和字段显隐／脱敏约束。
- 代理办理保留实际办理人与原审批人、原代理编号和授权范围。不能通过领取、转交或再次委派把有期限授权变成永久权限。预算、核减、付款等财务专用权限须在各自入口核对，不能由通用代理隐式授予。

## 职责和调用链

| 层次 | 调用方与下游 | 职责与受影响场景 |
| --- | --- | --- |
| 组织领域 | 管理服务 → `ApprovalProxy` | 自身期限、不可变范围、乐观修订及终态撤销 |
| 组织应用 | 管理入口 → `ApprovalProxyService` → 组织、定义和代理仓储 | 同租户人员资格、发布版本、重叠关系、目录审计与事务 |
| 任务授权 | 待办详情／办理／会签／财务 → `FlowableTaskAuthorization` | 决策及报销签收／核减使用锁内 `requireAction`；核减先锁资源再复核代理。增减签等原生职责入口保持原授权 |
| 待办与读取 | 分页 SQL、旧待办接口、参与者和字段投影 → `FlowableApprovalProxyAccess` | 后台已接通总数、分页、详情、字段和附件；到期／撤销无须任务或调度状态更新 |
| 办理与留痕 | 审批应用锁 → 代理行锁 → Flowable／审计 | 锁后重读期限；保存实际批准人、原责任与授权快照，不重置 SLA |
| 代理提醒 | 有界扫描／原 SLA 事件 → `FlowableApprovalProxyNotifications` → Inbox／外发意向 | 原任务与直接代理相交，最小内容与持久来源同事务保存；外发领取再次检查原授权 |

代理存储没有引擎任务副本，也不写认证角色和任职。V96 只新增 `organization_approval_proxy`；同租户的流程、原审批人及代理人由复合外键约束，不给旧数据自动生成授权。

管理创建在组织目录写锁内检查重叠，保存与 `organization_change` 审计同一事务。撤销同时取得目录锁和原代理行锁；后续任务办理应在申请锁之后取得代理行锁，并且不得在持有代理行锁后反向申请目录写锁。领域状态及当前有效名单只作为授权依据的一部分，不能直接代替任务授权。

## 管理接口

全部入口仅限当前租户 `ADMIN`，不接受客户端指定租户、创建者或认证角色。GET 返回 `Cache-Control: no-store`，一页在同一数据库快照和观察时刻计算期限状态；人员姓名及当前资格独立投影，不覆盖原授权。`ACTIVE` 只表示期限有效，仍须核对双方资格与具体任务权限。

| 方法与路径 | 作用 |
| --- | --- |
| `GET /api/v1/organization/approval-proxies` | 使用 `personId`、`afterId`、`limit` 分页；人员筛选覆盖原审批人或代理人 |
| `GET /api/v1/organization/approval-proxies/{id}` | 按原编号刷新最新期限、撤销事实和当前人员资格 |
| `POST /api/v1/organization/approval-proxies` | 指定 `definitionId`、`principalId`、`substituteId`、`startsAt`、`endsAt` 和 `reason` |
| `POST /api/v1/organization/approval-proxies/{id}/revoke` | 指定读取过的 `expectedRevision` 和撤销 `reason`，不能修改原范围 |

写入使用原有 `Idempotency-Key`、OIDC CSRF 和页面身份绑定。回执只返回 `proxyId` 和原写入的 `revision`；重放一条已撤销授权的创建请求仍返回原创建回执，不恢复授权，也不返回可能已经过期的“有效”结论。界面需要随后 GET 原编号。成功回放前仍要求管理员资格，角色变化不能借原键取得记录。

管理 API 的 9 项 Spring MVC 范围测试通过 H2 和独立 PostgreSQL（同组不相加），包括跨租户、参数、分页、角色撤销、创建／撤销原键恢复、回执保存失败后代理／审计／幂等记录一起回滚。7 项路由和 DTO 契约测试通过，静态 OpenAPI 为 296 个操作、588 个 schema 和 113 个请求示例。首次故障测试修正了 MockMvc 异常断言，生产异常处理未改。见[管理 API 证据](evidence/approval-proxy-api-20261001.json)。这些是 Spring MVC 集成验证，尚无新安装包真实网络、页面或实际代理办理验收。

## 代理任务读取后台

`FlowableApprovalProxyAccess` 在一次读取中固定观察时刻，同时核对双方当前本地资格、实际账号 `APPROVER`、精确发布版本和原生部署、申请状态、本轮实例与原生责任。原审批人必须是当前 assignee，或未领取任务中明确记录的候选账号；不根据本地审批资格推断外部 IdP 角色，也不递归继承代理。原生委派的协助阶段不开放最终审批代理。

禁止自审批及前序实际批准人排除同样约束代理人。会签中，本人已有当前责任（包括委派出去等待返回的责任）或已实际批准时，不能再取得另一人的代理待办。明确的费用财务节点还要求代理人自己的 `FINANCE` 角色；签收／核减的后续进度见下文；预算和付款等独立财务授权不会从代理关系取得。

新分页先求完整可读代理任务集合，再与原生待办合并、筛选、计数和应用游标；多个原审批人不会使同一任务重复，空后续页仍返回筛选总数。只有实际授予代理的人员和精确版本会查询原生候选任务，没有代理时不额外扫描引擎任务。旧列表、详情和申请参与者复用同一判定，字段显隐、脱敏和原附件下载继续使用原节点的表单规则。只读访问不领取任务、不改写负责人、不重置原到期时间，也不产生永久历史参与身份。

读取阶段最初对纯代理返回空操作列表。后续决策阶段已在完成锁内写授权和审计后开放批准、退回、驳回，详见下节；领取、释放、转交、委派、协助完成及接收人选择仍不允许通过代理取得。

先用真实提交后的有效代理复现详情 403，再接通读取。新增 11 项 Spring MVC／引擎集成测试、相关 59 项既有回归通过 H2，共 70 项去重用例；PostgreSQL 重跑新增 11 项和分页 15 项，共 26 项重叠范围通过，不与 H2 相加。财务节点角色用例使用冻结申请／轮次夹具和真实原生任务，仅验证读取边界；首次缺少费用表单的夹具已修正，不代表完整报销提交或财务代理办理验收。静态 OpenAPI 仍为 296 个操作、588 个 schema、113 个请求示例。见[读取阶段证据](evidence/approval-proxy-task-read-20261001.json)。

上述读取阶段没有新安装包运行验收；以下决策增量也未替换既有 V95 服务。

## 代理决策与办理表单

`Task` 返回 `canActDirectly` 和本任务的 `proxyOptions`。原生权利默认优先；只有单一代理时，旧客户端省略 `proxyId` 可由后台唯一确定，多条代理必须明确选择。显式编号一旦无效即拒绝，不能静默换用另一条代理或本人的原生权利。新表单在确认时固定 `proxyId`，响应丢失后的原请求恢复保留同一身份、意见、版本与幂等键。

决策先取得申请及关联业务锁，再重新读取任务并锁定所选代理；行锁等待后使用新的观察时刻复核双方资格、有效期、撤销、精确版本、当前轮次和职责规则。撤销与决策使用同一行锁，已提交撤销能阻止等待中的决定。同一申请版本竞争只能成功一次。代理仍不能领取、释放、转交、委派、回交或增减会签成员。

批准、退回和驳回前，将原生最终 assignee 记录为实际办理人；另用原生 `approvalProxyPrincipal` 历史链接保留被代理的原责任。没有复用原生委派 owner，也没有新增任务副本表。任务审计的 `proxyUse` 固定原代理编号、修订、发布版本、双方人员、期限及授权观察时刻，不复制管理员创建原因。原生历史、业务状态、审计和幂等回执同事务提交；其中任一步失败全部回滚。

后续职责分离排除实际批准人。会签分别保留实际投票人和已完成的原责任，既不能由同一实际人再投另一票，也不能把已被代理完成的原责任人再次加签。原到期时间保持。已经发生的代理决定不会因授权到期或撤销而从历史消失；实际办理人和被代理人仅保留原节点的字段规则，敏感字段继续脱敏，隐藏字段继续隐藏。普通未选中的候选人不会因此取得历史访问权。

办理表单可选择本次身份、显示原审批人与期限；纯代理不显示增减签入口。任务、账号、版本或代理权限快照变化时清空待确认表单。审批轨迹与操作审计展示实际人、原审批人和授权核对时刻；记录详情保留代理编号及修订。

验证及日志见[决策阶段证据](evidence/approval-proxy-decisions-20261001.json)。H2 范围去重 140 项（领域 8、服务端 132）、前端相关 51 项、类型检查、构建及静态契约通过。新增代理决策 11 项覆盖三种决定、明确选择、真实并发撤销与同版本竞争、到期复核、回执失败回滚、原键恢复、职责分离、会签和历史字段权限；到期用例通过延迟行锁返回后的观察时刻稳定触发，未声称为真实并发阻塞到期。旧会签并发测试原同步点处于申请锁内，会由测试自己制造等待环路；同步点移到锁前，原成功／冲突、审计、重试及通知断言保持。生产锁策略未改。

独立 PostgreSQL 的 11 项决策和 11 项读取测试也通过，共 22 项与 H2 重叠的范围；保留库为 `approval_proxy_decision_b33f16429b`，不重复计入 140 项去重总数。静态 OpenAPI 为 296 个操作、590 个 schema、113 个请求示例。

决策阶段仅验证后台和组件，不把它算作完整代理运行验收。财务专用入口的后续进度见下节；代理通知对象、管理员配置页面、实际 HTTP／浏览器、非空升级及在审重启继续实施。

## 报销专用入口与财务原依据

报销页面经 `ExpenseWorkflowQuery` 读取当前任务的原生权利和直接代理选项，沿用原轮次敏感明细权限。`ExpenseApprovalService` 统一协调当前申请／报销锁、财务版本和任务授权；只有本轮签收节点能确认纸件，财务核减还需要本人 `FINANCE` 角色、纸件已签收和当前金额的预算已确认。这些是跨聚合与任务的编排，因此位于应用服务；签收的一次性状态仍由 `ExpenseSubmissionControl` 判断，金额与资源差额继续使用已有报销领域逻辑。

签收与核减允许可选 `proxyId`，与通用决定使用相同的单一代理自动选择、多项明确选择及显式失效拒绝规则。核减先取得冻结引用的财务资源行锁，再调用锁内任务授权，等待之前的读取结果不能作为金额变更的授权。没有新增财务或认证角色来源。

签收事实新增可选 `proxyUse`，保存实际签收人及当时原审批人、代理编号、修订和范围；旧 JSON 缺少该字段时按无代理读取。签收与核减均不通过代理领取或完成任务，原生负责人保持，原节点审批仍需单独执行。核减在原有任务审计保存实际办理人与代理证明，金额调整、资源、路由、预算意向、通知和审计同事务提交。授权撤销后，签收或核减不会赋予继续批准的权限。

前端复用通用身份选择逻辑，确认时明确本次原审批人；任务、账号、版本或代理选项变化清空旧表单，到期时阻止新提交，未知结果恢复保留原请求及双版本。签收信息同时展示实际签收人和原代理依据。

先复现真实报销代理读取返回 403，再补齐入口。8 项新增专项包含真实资源锁等待中的撤销／到期、角色隔离、签收和核减的末端事务回滚与原键恢复、旧 JSON 兼容。H2 去重 77 项（领域 9、服务端 68）、其中同组报销 PostgreSQL 27 项、前端 37 项、类型检查、构建及 OpenAPI 通过，数据库范围不相加。既有财务子流程、签收／核减、通用代理决策、归档原件及历史敏感字段范围回归通过。见[财务代理证据](evidence/approval-proxy-expense-20261001.json)。本次没有迁移或替换运行服务，实际网络、页面、升级及重启验收仍待完成。

## 代理待办与超时提醒后台

`ApprovalProxyNotificationScheduler` 每轮最多扫描 100 个原任务／代理组合，按租户、代理编号和任务编号推进游标。新任务、在审新增授权及未来授权生效都走同一链路；单项失败继续处理后续项，遍历尾部回到开头，重启后由持久来源去重。既有原 SLA 事件同时通知当时有效的代理，原到期时间和原生责任不变。超过期限后新建立的代理由待办扫描提醒，不重建已发生的 SLA 事件。

通知编排跨越组织授权、当前流程和消息队列，放在应用服务；原授权状态继续由领域与仓储判断。处理先锁申请及祖先，再锁原代理，并在锁后重新检查双方本地资格、精确发布版本、当前轮次与任务、原生直接责任、职责分离及会签独立性。目录无法证明身份源角色，后台不构造带审批角色的账号，也不复制申请标题、单号、节点名称或表单正文。用户登录后仍需自己的实际角色和当前任务权限。

V97 新增 `approval_proxy_notification`，同租户代理和站内消息以复合外键关联；旧消息不补造授权来源。消息、来源和个人偏好决定的外发意向同事务保存；多个 worker 只能建立一份同任务／原代理／事件的来源。外发首次领取和人工恢复只复核原代理，新建授权不复活旧通知。撤销或到期后历史站内提醒保留，点击原入口重新鉴权。

默认 `agentflow.notifications.proxy-reminders-enabled=true`，间隔 `agentflow.notifications.proxy-reminder-delay-ms=30000`。容器示例通过 `AGENTFLOW_PROXY_REMINDERS_ENABLED` 控制扫描；其他启动方式可直接配置上述属性。该开关不启用外部发送，邮件和 IM 仍需各自配置、个人偏好与投递 worker。应用升级到 V97 前按现有停写迁移步骤操作，不支持旧二进制跨版本运行。

## 管理页面与基础运行验收

## 代理生命周期通知

暂停、恢复、撤回、管理员终止、退回、驳回、会签减签和提前达标现在向原任务范围内有效的直接代理发送最小状态提醒。任务被暂停或删除前，在申请锁内捕获原生责任和代理来源；业务变更后、消息入库前再次核对原授权与双方资格。暂停中的本人会签责任仍占用独立席位，不能借暂停再接收另一人的代理责任。父流程控制传递至子流程时，每条提醒仍绑定自己的申请和轮次。

这些消息不复制申请标题、单号、节点名称、操作原因或表单正文，不增加历史参与者和读取权限。外发领取和人工恢复继续在目录锁内核对原代理；原授权撤销或到期后，新授权不能复活旧消息。已经入库的历史事实保留，点击入口仍实时鉴权。

调用链为实例控制／撤回／任务决定／会签成员变更 → `ApprovalNotificationService` → `FlowableApprovalProxyNotifications` → 站内消息、原来源和外发意向。接收范围跨组织与流程，因此由通知应用服务编排；没有把快照当作领域授权。上述写入和原业务、审计、幂等回执一起提交，任一步失败全部回滚。按原键恢复不会重复产生事件。

生命周期消息不追加其他代理的写锁。复核中先用两张独立申请的并发代批复现 H2 代理行死锁；移除额外写锁后，又在 PostgreSQL 复现来源外键的 `KEY SHARE` 与原 `FOR UPDATE` 形成等待环路。代理主键不可变，PostgreSQL 改用 `FOR NO KEY UPDATE`，保持同一代理的办理与撤销互斥，同时允许其他申请建立原授权的通知引用；H2 继续使用其支持的 `FOR UPDATE`。没有通过重试或吞掉冲突掩盖问题。

V98 为 `approval_proxy_notification` 增加 `event_version`：旧待办／超时来源保留版本零，生命周期来源使用本次申请版本。原消息唯一约束和两个同租户外键保持，重复暂停／恢复可以分别留痕，同一版本同一事件仍只能保存一次。生命周期记录不阻止后续首次待办扫描。升级只延续旧来源，不补造历史消息；按既有停写迁移步骤部署，旧二进制不能跨版本运行。

| --- | --- |
| 待办、原 SLA 超时 | 保留既有当前任务扫描和锁内授权检查；不重置期限 |
| 暂停／恢复、撤回／终止、退回／驳回、会签移除／提前结束 | 使用原任务范围和原代理，发送不含业务正文的状态事实 |

| 提交／最终批准、费用调整、评论 @、抄送、超时升级 | 保持申请人、被点名人员或原规则的接收范围，不从审批代理自动继承 |
