# 参与者检索性能验证

2026-09-24，修复 `/api/v1/applications/search` 在大量不可见申请下重复扫描流程变量和历史任务的问题。改动位于基础设施层 `FlowableApplicationParticipationSql`，不改变领域模型、审批状态、流程引擎写入或数据库结构。

## 根因与调用链

`ApplicationSearchController` 从认证上下文取得租户、用户和角色，经 `ApplicationSearchPort` 调用 `JdbcApplicationSearchAdapter`。非管理员的筛选条件包含本人申请、当前或历史参与关系，以及真实办理审计；筛选完成后才执行稳定排序和游标分页。管理员仍使用原租户内摘要查询。

旧实现把申请 ID 和租户列同时关联到两条引擎子查询。在 PostgreSQL 17.11、5,000 份申请中，无可见申请的账号需要完整检查候选申请，执行计划显示流程变量和历史任务各扫描 5,000 次，单次查询约 10 秒。原有小规模集成测试验证结果、权限与分页，未覆盖这一随候选申请数增长的扫描量。

修复先按认证租户、用户和角色查询实时参与关系，再以申请 ID 的集合成员关系过滤外层申请。集合在每次查询中重新计算，不缓存授权，也不将候选身份保存成永久权限。`IN` 保留存在性语义，重复变量、多个任务或多个身份关系不会重复返回申请。认证租户仍同时约束外层申请和内部流程变量。

此逻辑属于 Flowable 只读适配层：它依赖引擎表结构和查询计划，不是新的领域规则。历史指派人、委托所有者、非根执行上的流程变量等既有可见语义保持；不能将其替换成待办查询的当前轮次、候选人和激活状态约束。

## 授权与数据库回归

现有集成用例保留申请人、租户管理员、流程管理员、候选角色、认领释放、转交、委托、历史指派、真实办理审计、多轮重提及游标身份绑定。新增两个用例覆盖：

- 租户和申请变量必须绑定同一流程；任务局部租户变量、其他流程的正确租户以及错误变量类型不能授权。
- 多份绑定变量及用户/角色身份不重复分页；流程变量不强制要求根执行；空角色集合仍能读取实际指派申请。

8 项参与者查询集成用例分别在 H2 与 PostgreSQL 17.11 通过。默认 CI 使用独立 H2；需要 PostgreSQL 验证时，提供自行准备的隔离测试库，再运行：

```bash
AGENTFLOW_SEARCH_TEST_URL=jdbc:postgresql://localhost:5553/agentflow \
AGENTFLOW_SEARCH_TEST_USER=agentflow \
AGENTFLOW_SEARCH_TEST_PASSWORD=demo \
AGENTFLOW_SEARCH_TEST_DRIVER=org.postgresql.Driver \
mvn -B -ntp -pl agentflow-server -am \
  -Dtest=ParticipantApplicationSearchIntegrationTest \
  -Dsurefire.failIfNoSpecifiedTests=false test
```

该测试会写入合成流程和审批数据，必须使用专用测试库。完整 `mvn verify` 共 612 项通过，其中领域 178、服务端 434；前端 238、工具 19、构建与作者检查通过。

## 范围

当前有效任务查询的执行计划也已检查，几个候选改写没有得到稳定收益，未纳入生产改动。待办与运营统计仍有容量优化空间。此阶段不修改统计口径，不添加引擎表索引，也不调整资源限额。平台的生产规模、峰值流量和服务目标尚未冻结，本次结果用于定位与对比。
