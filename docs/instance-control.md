# 实例暂停、恢复与具名终止

当前阶段：**单实例与父子流程的暂停／恢复和具名终止均已完成本地验收**，分别见[终止运行证据](evidence/instance-termination-runtime-20261001.json)与[公开子流程证据](evidence/subprocess-public-20261001.json)。超时升级也已接入独立剩余工时与暂停抑制，见[升级规则及验收](task-escalation.md)。其余通知渠道、真实企业财务和企业环境交付仍在进行。

## 规则和职责

同租户管理员对当前在审轮次明确填写原因，并提交当前申请版本。暂停／恢复不改变申请的在审结论，不产生人工审批意见，不释放财务占用。当前轮次、实际实例、定义来源及受控租户变量必须一致；其他轮次、已结束实例、缺少平台暂停依据的原生暂停均不提供恢复操作。

入口负责请求格式、原因、版本和角色校验；应用服务先锁申请，再协调原生实例、任务期限、审计、通知与 Webhook outbox。任何一步失败回滚全部变更。成功响应按原请求幂等回放，回放仍检查当前管理员身份。暂停和恢复各增加一次申请版本。

存在固定父子调用时，只允许从根申请控制。根锁下核对整棵原调用树，统一暂停／恢复所有活动原生实例，每个活动申请各自增加版本；已批准分支不变。子申请读取自己的真实暂停状态，但不提供独立控制。子审计使用系统身份与根申请编号，不复制管理员在根申请填写的自由文本原因；后代通知失败会回滚整棵树。所有活动实例必须保留相同原暂停时间，恢复时各任务仍使用自己的原日历与剩余时限。

人工任务在暂停时保留原到期时刻，恢复时使用任务创建时绑定的日历修订，计算原到期之前剩余的真实工作时长。午休、周末、假日和夏令时均按原开放区间处理，保留小于一分钟的精度；多次暂停只接续当时余额。暂停前已到期的任务保留原到期事实及已发送的提醒，不重新获得办理时间。日历修订或原期限依据不可用时，恢复整体失败。未发送的升级提醒另行接续原升级期限；审批已超时但升级等待尚未结束时，也保留剩余升级工时。已经升级的事实不重置。

定时等待保留实际激活时生成的原到期时间，暂停期间不推进；恢复后，已经到期的等待可由原调度继续。此规则与人工审批的工作日历 SLA 分开。

暂停后任务不进入可办理待办与超时任务统计，也不能审批、转交、加减签或发送超时提醒。超时提醒与暂停操作统一采用申请优先的锁顺序，并在锁后重读任务状态和期限。申请仍计为在审；暂停前的节点读取权限继续有效，管理员也不能突破敏感字段约束。申请人需要管理员恢复后再按原业务规则撤回。

## 接口

| 方法 | 路径 | 行为 |
| --- | --- | --- |
| GET | `/api/v1/applications/{id}/rounds/{roundNo}/runtime` | 读取当前绑定实例的运行、暂停、结束或不可用状态及当前操作能力 |
| POST | 同一路径加 `/pause` | 明确暂停原轮次 |
| POST | 同一路径加 `/resume` | 明确恢复原轮次并接续人工任务剩余期限 |
| POST | 同一路径加 `/terminate` | 管理员具名终止当前运行或暂停的根轮次及未完成后代 |

写入正文只允许 `expectedVersion` 和 `reason`，要求原请求幂等键；禁止查询参数和客户端提供新到期时间。响应不返回引擎变量或表单原文。`pausedAt` 在没有暂停依据时可以省略，所有响应禁止缓存。

`canTerminate` 仅对同租户管理员、当前在审根轮次和实际绑定实例开放。终止后返回 `ENDED`，三项操作能力均为 `false`；申请及当前轮次为 `CANCELLED`，不能恢复或重新提交。已批准、已驳回等既有结论不能被终止覆盖。

## 终止的业务收尾

终止先取得原根申请及关联财务资源锁，再保存所有未完成任务的接收人，包括暂停任务。停止原生根实例后，必须核对真实结束历史，才能保存根轮次取消结论、`INSTANCE_TERMINATE` 审计和后代停止联动。已完成的子分支、原轮次内容、已完成意见和实际办理身份保持。

管理员原因只写根轮次和根审计。引擎删除原因会传到子实例，因此仅包含根申请编号；子轮次以 `system:subprocess` 记录实际取消来源，不复制根原因。消息使用既有 `APPLICATION_CANCELLED`，Webhook 使用 `ApplicationCancelled`，均不附带敏感正文。原幂等回放仍检查当前管理员身份。

费用发票、事前申请和借款预留按既有终止规则释放。外部预算冻结结果未知时仍查询原命令，确认冻结后另行登记释放，不把入队当成释放成功。采购只释放原应付占用，财务原轮次和历史事实保持。引擎、申请、轮次、资源、审计、通知与 outbox 同事务；末尾通知或占用释放失败时整体恢复原状态，包括原暂停和任务。

测试首先复现终止接口缺失，又复现暂停实例终止漏通知原审批人的问题：旧接收人查询只包含活动任务。新增 `unfinished` 查询仅供停止前保留通知对象，普通待办和可办理人员查询仍只读取活动任务。页面显式显示终止后不能恢复／重提，要求原因和确认；取消不发送，回执损坏或丢失继续保留原键恢复。

`INSTANCE_PAUSE`／`INSTANCE_RESUME` 保存具名审计和原因；`APPLICATION_PAUSED`／`APPLICATION_RESUMED` 通知原申请人和实际有效办理人员，接收人去重，入口指向申请。Webhook 仅投递精简事件，不复制原因或表单内容。相关状态与原到期依据保存在已有 Flowable 表中；原单实例阶段未新增迁移，当时为 V86。后续父子控制同样没有新迁移，当前源码测试库为 V90。

## 页面与原请求恢复

普通申请及五类财务申请的详情顶部统一显示本轮运行状态。管理员先选择暂停或恢复，填写原因，再明确确认；取消不发送请求。状态未读、读取失败、详情版本不一致或操作进行中时，不能沿用旧操作能力。暂停期间申请人不能撤回，财务详情的办理入口也被锁定；页面说明先由管理员恢复。

终止同样要求明确原因和确认。取消后，焦点返回原操作按钮。实际浏览器曾复现焦点落到页面主体：确认表单通过 `v-if` 卸载了按钮，旧逻辑在重新渲染前保存了空引用。修复位于确认面板，等待按钮重新挂载后读取引用；调用方申请详情、下游接口和业务规则均不变。原测试仅运行 setup，没有完整渲染，新增实际模板用例覆盖暂停、恢复和终止的按钮卸载与重建，先失败再通过。

入口状态由原申请、原轮次和当前身份读取，切换时取消旧查询。成功后重读申请和队列，清除同一申请的旧任务面板。响应丢失或成功回执损坏时，保留原幂等键和原正文；恢复回执必须匹配申请、轮次、目标状态与恰好一次版本增加，禁止修改原因后重新发送。

父页面原先将申请路径下的子操作回执当作完整申请，之前定时重试已出现同类问题。新失败用例复现了暂停恢复后详情不刷新；现在只有明确的完整申请操作进入原分支，其余申请子操作按原请求目标重读。范围测试同时保护提交、撤回、作废和保存的既有恢复行为。

## 验证证据

本阶段范围验证见[后端证据](evidence/instance-control-backend-20261001.json)。领域覆盖秒以下精度、跨工作区间、日历修订、多次暂停和已超时；接口覆盖角色、租户、原轮次、旧版本、并发与幂等、双向通知故障回滚、原定时器、暂停期间字段权限、并行会签与无期限任务。提醒并发测试在暂停事务未提交时读取旧快照并等待同一申请锁，确认锁后不投递。

原测试只覆盖可办理或已结束的节点，未覆盖暂停状态。新增失败用例复现了暂停后字段读取权限丢失，修正参与节点查询后通过；另用实际序列化响应复现契约误要求空 `pausedAt` 的问题，契约改为可省略，与全局空值省略配置一致。

页面和运行验收见[完整本地证据](evidence/instance-control-workflow-20261001.json)。新增 13 项前端测试，相关范围共 179 项通过，包含实际组件确认／取消、版本和身份切换、财务锁定、未知结果恢复以及完整申请恢复回归；类型检查、构建与 OpenAPI 检查通过。后端沿用前一阶段已通过的领域、H2 和 PostgreSQL 范围证据，本阶段没有重跑全部后端测试。

实际 V86 非空验收副本升级保留 168 张业务表的 3,604 行、8 条待办、69 条运行变量和 10 份文件。普通申请、并行任务、报销和定时等待分别暂停，跨重启后原状态、原任务、原暂停时刻及原到期时间保持。暂停期间原定时器经过实际到期时间仍未推进；恢复后正常产生待办。

人工任务恢复后保留原编号和创建时间，逐笔验证到期时间等于原到期时间加本次暂停消耗的开放时间；实际验收时段使用全天开放日历，跨午休、周末、假日和夏令时等边界由领域测试覆盖。恢复后再次重启，更新后的到期时间没有重算。3 个普通流程最终由原审批人作出 4 次批准；报销保持在审，120 张财务相关表与 10 份文件在暂停／恢复前后完全一致。

198 份实际 HTTP 响应通过契约校验，其中 29 份运行状态和 11 份操作回执同时通过前端校验；另有 2 份真实浏览器暂停／恢复回执通过两层校验。实际页面覆盖空原因、取消不发请求、敏感字段脱敏、申请人及财务暂停锁定、具名审计和实际 500 CSS 像素布局；浏览器重启后重新登录演示账号。未知结果恢复由范围自动化验证。真实企业系统、生产环境和远程 CI 仍独立验收。

## 具名终止的独立运行验收

[终止运行证据](evidence/instance-termination-runtime-20261001.json)使用独立 PostgreSQL 副本。先在 V88 创建普通、暂停、并行、定时、事件、采购及报销在审申请，再升级到 V90；218 张原表的 6,284 行和 11 份原件保持。12 次终止分别只有一条审计，原任务、作业和事件订阅均被清理，已有人工批准意见及原轮次快照保持。并发人工批准与终止只形成一个合法结论；已批准申请不能被覆盖。

真实 HTTP 注入采购释放失败、实际浏览器注入通知保存失败，均验证原暂停、任务、期限、版本、轮次和资源整体回滚。解除故障后使用原键、原正文恢复。报销在预算冻结未知时终止，跨重启继续查询原冻结号，确认后仅发送一次释放；原发票预留释放。采购付款释放当前应付占用，但保留已经确认的采购票据归属，不能据此将已入账发票再次用于报销。已接收但未消费的事件在终止后重启，被判定为 `TARGET_STALE`，没有重复推进。

374 份符合文档的实际响应通过契约，其中包含 3 份真实浏览器成功回执；另有 2 次故障注入的 HTTP 500，单独验证回滚和原请求恢复。运行响应含多次幂等重放，不计作不同业务操作。两次新版重启后，全部原终止请求仍可重放。相关前端 28 项、类型检查、构建及 OpenAPI 通过，实际 500 CSS 像素页面无横向溢出；本阶段仅修复前端焦点，后台沿用前一阶段通过的范围测试。

原 V88 服务的 219 张表、5,580 行和 10 份文件始终未改动。副本中 172 张原业务表的 3,878 行保持；唯一另核对的汇总变化是新上传一份 93 字节发票，使本人票夹配额增加一次上传及 93 字节。指定 5 个保留文件哈希一致。企业财务响应使用本地合成服务，真实企业接口、生产 TLS 和远端交付仍单独验收。
