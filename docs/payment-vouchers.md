# 付款凭证：原银行事实与独立会计入账

更新：2026-09-28。本阶段完成隔离工作树的本地开发与验收，不代表真实银行、ERP 或企业归档系统已经接入。

## 当前行为与调用链

员工借款和正额费用付款确认成功后，同事务登记 `PAYMENT` 凭证准备。准备执行器在事务外读取会计期间及科目映射，再登记原凭证命令；过账复用既有持久执行器。ERP 不可用不会把已确认到账改为未付款。

全额借款冲销及零金额费用没有实际银行付款，不生成付款凭证。费用资源和预算是否核销继续由报销结算账本判断；付款凭证已过账不表示已归档。

调用链：`PaymentOperationService` 保存成功修订 → `PaymentVoucherRegistration` → `VoucherPreparationService.paid` → 原准备队列 → `VoucherOperationService` → 原 ERP 端口。申请锁、业务聚合锁和事务顺序沿用现有财务链路。

## 原始依据与职责

- `VoucherPreparation.Source` 对付款增加原支付编号和本地成功修订号。会计重试、银行重复查询均不改写这个来源。
- `PaymentVoucherSources` 核验真实支付修订、当前支付、原授权、原挂账及冻结业务轮次。金额、两端账户和成功回单不能由 HTTP 调用方填写。
- 借款时区来自原借款轮次；费用时区来自正式提交采用的成功预检。不能查询今天的法人目录或用服务器时区重新解释到账日。
- 当前付款仍须无争议成功，原挂账仍须可用。退票、冲突和未确认状态阻止新会计发送；原凭证的未知结果或已过账事实仍可查询。
- 付款后审批撤销不抹去银行事实，付款凭证保留原批准版本。原挂账仍使用最终批准、纸件与预算冻结守卫。
- `VoucherSources` 组合两种实际来源，执行器复用租约、未知结果查询和原号重发。实体负责自身状态，跨仓储核验位于应用服务。

原测试只验证付款凭证工厂对当前批准状态的处理，运行时没有消费银行成功的凭证链路。失败复现分别证实真实成功付款没有准备任务，以及撤销当前审批后原成功付款被拒绝。修复没有创建模拟批准申请，也没有延长原资金授权。

## V49 升级与恢复

V44 类型列带数据库自动命名检查约束。V49 复制并替换这一列，重建同轮同类型唯一约束和凭证外键，保留原输入、状态 JSON 及修订。新增付款外键绑定同租户、同业务、同申请轮次的授权及实际支付修订。

旧挂账来源不序列化新增空属性，原 JSON 比较更新保持兼容。仓储核对新增关系列与领域输入，不能拼接其他业务或修订的回单。

原准备执行器每批先补登缺失准备的历史成功付款，再处理队列。补登只读本地事实，不查询或重发银行交易。准备失败由财务显式重试，仍保留原成功修订；已有过账命令不能换编号绕过对账。

## 接口与页面

| 接口 | 行为 |
| --- | --- |
| `GET /api/v1/applications/{id}/vouchers/payment?roundNo=1` | 本轮独立付款凭证摘要 |
| `POST /api/v1/applications/{id}/vouchers/payment/actions` | `PREPARE`、`QUERY` 或 `RESEND_ORIGINAL`，不执行银行付款 |

读取沿用原轮次完整敏感字段权限。写入还要求当前 `FINANCE` 角色、非申请人、同法人有效任职，幂等回放前重新授权。响应 `no-store`，不公开原命令、账户摘要、原始回单或外部目标。

挂账和付款视图、受理回执均包含 `kind`。两类入口互相拒绝对方的操作号；客户端同时核对类型、业务、轮次和版本。独立审计动作 `PAYMENT_VOUCHER_*` 保存实际操作者及说明。

借款与费用详情分别显示挂账、银行付款和付款凭证。确认后才写入；未知结果沿用原幂等键恢复，恢复后重新读取。身份、类型、轮次或版本切换会清空旧视图。
