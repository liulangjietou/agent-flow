# 模型与通知配置自检

系统自检复用运行服务的真实配置，区分适配器未启用、后台未启用及配置有效。检查不调用模型、不获取企业微信令牌、不发送邮件或 IM，也不把配置校验解释为真实企业连接或递送验收。

## 调用链与职责

系统自检页和首次审批引导 → `GET /api/v1/system/checks` → `SystemCheckService` → `SystemDiagnostics`。入口继续要求 `ADMIN`，报告禁止缓存。基础设施诊断负责当前存储和配置事实，应用服务将安全状态映射为中文提示；不修改审批领域或外发队列。

通知诊断先查询当前租户站内消息存储，再从 `NotificationDestinations` 启动时已校验并冻结的绑定读取渠道。只返回当前租户同时启用绑定与发送器的渠道集合，不返回收件人、地址、应用、服务器、凭据、数量或其他租户信息。个人偏好和实际发送资格继续在原发送链路复核。

模型诊断复用 `AssistConfiguration.requireAvailable`，不另建一套参数校验。未启用时保留历史读取；已启用但参数无效时报告脱敏失败，后台停用不能掩盖配置错误。报告不包含目标地址、模型名称、密钥或异常原文。

## 状态

| 检查 | 稳定代码 | 含义 |
| --- | --- | --- |
| 通知 | `NOTIFICATION_WORKER_DISABLED` | 外部发送后台未启用；另外说明本租户是否已有启用绑定 |
| 通知 | `NOTIFICATION_BINDINGS_MISSING` | 后台已启用，本租户没有启用绑定 |
| 通知 | `NOTIFICATION_CHANNELS_CONFIGURED` | 后台已启用，本租户至少一个邮件或企业 IM 绑定启用 |
| 模型 | `AGENT_MODEL_DISABLED` | 模型适配器未启用 |
| 模型 | `AGENT_MODEL_WORKER_DISABLED` | 参数校验通过，模型执行后台未启用 |
| 模型 | `AGENT_MODEL_CONFIGURED` | 参数校验通过，模型执行后台已启用 |

以上配置状态均为 `WARNING`。依赖查询失败或模型参数无效沿用 `DOWN / CHECK_FAILED`，超时、繁忙及中断沿用 `UNKNOWN`。四项基础检查的通过计数保持原语义，不将外部配置计为完整上线验收。后台开关只表示本进程配置，不证明调度持续运行。

## 回归原因与范围

原自检固定返回模型 `NOT_IMPLEMENTED` 和通知 `IN_APP_ONLY`，模型与外部发送器实现后没有同步。原集成测试甚至要求保留模型占位，缺少启用配置和当前租户绑定的交叉验证；验收脚本还要求附件存储处于旧占位状态。

新增真实 Spring 配置下的 HTTP 用例先复现固定状态错误，再修复诊断；验证本租户企业 IM 不包含另一租户邮件配置、无效模型参数脱敏、查询前后业务表不变，以及模型／IM 回环服务收到零次请求。默认关闭、缺少绑定、停用绑定或服务、停用后台、超时和管理员授权继续由范围测试验证。

后端范围去重 60 项通过；分次执行的 42、24、8 项范围有重叠。前端自检、首次引导和模板范围 14 项、构建及 OpenAPI 通过。原验收脚本在旧服务上先失败，修正后在独立 H2 服务通过；初始及最终构建的 8 份自检响应符合契约，权限拒绝和业务查询前后不变也已核对。实际浏览器验证引导、自检、模板说明与 500 CSS 像素，控制台无警告或错误，模型／IM 协议服务请求数始终为零。见[验收证据](evidence/system-adapter-checks-20261001.json)。

本轮交付检查还发现 53 份 Java 文件的 92 处作者信息缺失或写在 Javadoc 正文中。已补为独立作者标签，并通过 Java 语法树对比确认修复前后全部 1,266 份 Java 文件的代码结构相同；作者门禁最终检查 2,432 个命名类型，缺失和语法错误均为零。该范围只改注释，不重构业务逻辑；最终构建和运行复核使用补正后的源码。

真实企业模型与通知渠道仍在[剩余工作](remaining-local-work.md)中；本项修复不会替代其验收。
