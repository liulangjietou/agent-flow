# 报销付款退回通知

F17 的员工报销付款退回查询、明确登记和原消息详情已接通。本阶段只完成本地实现与范围验证，F17 整体仍为 OPEN。验证记录见[阶段证据](evidence/expense-return-notifications-20261003.json)。

## 调用链和事实边界

财务从原报销的付款退回入口发起查询，后台工作器读取银行入款和员工应付贷方原件。`ExpensePaymentReturnService` 在查询状态持久化后发布 `ExpensePaymentReturnChanged`；登记时先完成查询消费、账本、决定及跨业务资金凭据保存，再发布同事务事件。通知服务只投影已保存事实，消息、外发意向与财务登记共同提交或回滚。

查询不可用、来源失效、原件未核清、发现退回以及明确登记分别形成通知。排队、查询中及正常未见退回的查询保持安静。发现候选退回不等于资金已经登记；明确登记也可能是“确认未见资金退回”，不能统一称为回款成功。预算与其他资源调整继续依据各自真实状态办理。

接收人是原申请人和本次查询的实际财务核对人。创建及外发领取都重新检查当前人员与原法人任职。去重键为 `expense-return:<原查询编号>:<事实种类>`；重复事件和 HTTP 原键回放不会重复发送。通知不包含金额、账户、入款流水、会计科目或证据正文。

## 原查询与原登记

`GET /api/v1/notifications/{id}/expense-return-target` 只读取本人消息，不接收额外查询参数。详情固定原报销轮次、首次成功付款修订和本次查询，不发起银行查询、资金登记、资源调整或标记已读。

登记仓储按原登记编号恢复事实，并重放登记前后的账本修订及查询消费，同时核对登记当时的结算修订。随后新增的资金登记和结算变化不能替换旧消息依据。旧待核对消息可以展示同一查询后来实际完成的登记；旧失败或未核清消息仍保留自身状态。

申请人读取沿用原轮次字段权限，财务还须当前 FINANCE 角色和原法人任职；管理员不能借通知绕过敏感字段。响应使用 `no-store`。页面分别展示消息发生时事实、当前原查询状态、原件有效窗口和明确登记，只提供重新读取与原申请轮次导航。身份切换、失权、超时、卸载及来源不一致会清除旧内容并阻断迟到响应。

前端保留已验证的微秒与毫秒精度边界：历史登记在到期前完成时，不因浏览器截断成同一毫秒而误拒绝展示；这不会提供新的登记许可。
