# 费用预检解释与补正建议

状态：A02 进行中。权威时效依据、本人来源选择、持久模型队列、严格来源校验、人工复核、公开接口及费用页面已实现。原请求恢复交互、页面范围验证、固定安装包非空升级及实际 HTTP／重启验收已通过；真实浏览器及 PostgreSQL 新范围补验仍待完成，A02 保持 OPEN。

## 调用链与职责

原费用页发起预检 → `ExpensePrecheckWorker` 领取 → `ExpensePrecheckEvaluator` 获取财务事实并执行原规则 → `ExpensePrecheckService` 保存终态。新增的 `ExpensePrecheckObservations` 在外部调用前，用短事务记录制度快照和本地依赖摘要；执行器根据真正读取的外部事实缩短有效期。

这些依据属于费用上下文。Agent 后续引用既有检查结果，不负责判定制度、预算、发票占用或提交资格。`ExpensePrecheckObservation` 只表达解释时效，不能构造可提交候选，不能把 `BLOCKED` 或 `UNAVAILABLE` 改成 `READY`。

## 已实现的版本与失效规则

此前只有 `READY` 保存完整候选证据；业务失败仅保留阶段、行号和受控错误码。现在实际执行得到的终态还可保留：

- 观察开始时间及不超过五分钟的截止时间；目录、账户、制度、验票、预算事实和法人次日零点只会进一步缩短期限。
- 执行时固定的已发布制度选择，未启用平台制度时保持原外部制度模式。
- 本人当前及上一轮引用资源的版本摘要、原件元数据、验票尝试和修订总数、规范票号的有效占用。资源不可供本人使用时只记录受控的不可用状态，不复制他人资源。

摘要材料在内存中计算，仅摘要保存在预检结果；资源标识、票号和其他单据归属不会因此成为页面或模型输入。财务 HTTP 与文件读取继续在事务外执行，没有新增外部调用。

解释可用性同时检查最新预检序号、原申请与财务版本、可编辑状态、任职、财务目标、制度、依赖和期限。再次验票即使失败且发票版本不变，也使旧解释失效；其他文件占用同一规范票号同样使其失效。`READY` 另复用正式提交的现有有效性检查。

预检期间制度发布或资源变化不会把当前事实补进旧观察；旧结果保留当时的结论，解释入口须要求重新检查。内部异常或领取后超时可能没有可信观察，不能据此补造有效性。

## 存量与公开契约

观察作为既有预检结果 JSON 的可选字段保存，无表结构迁移、历史回填或重新触发。旧结果缺少观察时仍能读取，解释可用性返回 `PRECHECK_EXPLANATION_REFRESH_REQUIRED`；只有明确发起新预检才能获得新依据。

公开预检 DTO 不增加内部摘要或观察内容；已有状态、金额预览、正式提交和幂等回执契约保持。现有正式提交继续检查完整候选证据，不依赖解释状态。

## 已实现的解释执行与复核

本人费用单 → 原预检时效判断 → 明确勾选来源 → 固定身份、双版本、预检序号及模型目标 → 持久队列 → 事务外模型 HTTP → 严格解释输出 → 本人采纳或放弃。`PrecheckExplanationService` 负责跨聚合授权和时效编排；`PrecheckExplanationRun` 负责执行及复核迁移；费用检查结论仍由原费用服务负责。

发送目录仅包括原检查状态、检查时间和记账日期，原问题的阶段、行号、性质和错误码，以及可选费用行的类别、日期、城市、数量、单位、申报金额、票据数量和是否选择事前申请。账户、票号、附件、自由文本、成本归属和人员身份不进入目录。每次必须明确选择 `precheck:result`；业务失败还须选择具体问题。最多选择 20 个问题、64 项来源，编码后的来源最多 64 KiB。

来源文本及 SHA-256 在排队时固定。模型只收到选定来源与待解释问题标识，不发送本地人员、租户、申请、单据或运行标识。模型目标、提供者、模型名和提示版本来自部署配置并纳入授权摘要；发送前由现有 `OpenAiTextClient` 再核对实际目标。解释共用其事务外传输、响应大小、超时、重定向和工具调用限制。

每个选定问题必须恰好返回一条解释，引用必须包含其自己的原问题，并逐项匹配本次实际发送的标识与摘要。业务失败还须有人工补正步骤。额外属性、遗漏问题、错误摘要、标量强制转换、工具调用和截断内容均不能成为待复核结果。解释和补正均为文本，不包含可执行的字段赋值、付款或审批动作。通过来源校验只代表引用匹配，不表示模型解释已经获得业务认定。

队列在 V107 的独立运行表及迁移轨迹表中持久化；复合外键绑定租户、本人、原费用单、原预检及已存在的财务版本。每单最多一个活动运行，首次领取固定租约，领取后中断只在到期时记录超时，不自动重发。单据到运行的锁顺序与现有费用服务一致；模型 HTTP 不持有数据库事务。排队、领取、发送前和采纳均检查原预检及依赖是否有效。

`ADOPT` 只记录本人选择的问题与复核说明，不生成财务版本、不改金额或检查结论、不推进审批。实际补正通过原费用编辑入口保存。`DISMISS` 可以处理过期解释，但不能带采纳选择；原解释与来源始终保留。模型等待期间业务变动后，生成结果可作为历史查看，不能采纳。

## 公开接口

路径前缀为 `/api/v1/expense-reports/{id}/precheck-explanations`：

| 方法与后缀 | 行为 |
| --- | --- |
| `GET /input?precheckId={uuid}` | 返回明确预检的可用性、真实模型目的地及发送目录；失效时目录为空。 |
| `POST` | 绑定双版本、原预检、目标摘要及来源选择，返回 202 安全排队回执。 |
| `GET` | 按 `page`、`pageSize` 读取本人历史索引，默认 20、最多 50 条。 |
| `GET /{runId}` | 读取原来源、解释、人工记录及当前可采纳性。 |
| `POST /{runId}/review` | 明确选择 `ADOPT` 或 `DISMISS`，与迁移轨迹同事务保存。 |

所有读取禁止缓存，管理员身份不能代替本人资格。查询拒绝未知、多值、非规范或越界参数；写入拒绝查询参数和未知正文属性。写请求共用现有幂等协议，回执不携带源内容或模型输出，原键回放不再执行模型或复核。

## 费用页面与请求恢复阶段

已保存的费用编辑页及本人当前详情页接入解释面板。审批任务和历史轮次详情不开放本人解释入口；最终读取和复核仍由后端校验本人资格。所有来源默认未勾选，发送前展示实际目的地、原检查结论、所选问题和可展开的原始文本。历史记录保留实际发送的来源及模型逐条引用，金额文本原样显示，不作浮点重算。

费用申请版本、财务版本、最新预检标识及有效截止时间共同控制采纳。新预检出现后，即使费用版本不变，也立即关闭旧解释采纳；过期记录仍能查看或放弃。采纳只记录所选原问题和复核说明，实际费用补正由原编辑入口保存并重新预检。

读取分别限制为十二秒，账号或单据切换中止旧读取，迟到结果不回填；失去读取权限清空整个解释区域。页面未提交选择和说明纳入费用编辑、提交及关闭按钮的锁定。成功回执须先核对运行编号、状态和版本，才能清除平台待恢复请求；网络和认证失败沿用原请求正文与幂等键。恢复后定位原运行并通知已挂载面板，不替换费用草稿。

## 响应状态与版本边界补验

2026-10-04，V02 核对复现了历史及详情响应在“未知状态 + 缺失版本”同时出现时被接受的问题。此前测试分别破坏状态或版本，遗漏了组合边界。根因在两类响应共用的 `summary`：未知状态查表和缺失版本均为 `undefined`，相等比较误判为合法。现先确认正整数版本，再核对明确状态对应的版本。入口仍统一在 API 响应解析层，失败沿用 `RESPONSE_UNREADABLE`，不向组件重复增加校验。

两个失败用例先于修复，覆盖一般未知状态和原型属性名称。修复后 69 项相关前端测试、类型检查和生产构建通过；从哈希核验的旧安装包证据复制 274 份实际响应，以新解析器重验通过。后者是历史响应兼容性检查，没有重新执行后端进程或浏览器。V02 整体仍待全部本地功能完成后验收，详见[边界修复证据](evidence/precheck-response-version-20261004.json)。
