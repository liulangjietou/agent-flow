# 会计期间、科目映射与凭证端口

更新：2026-09-28。本阶段完成三个领域端口及真实 HTTP 适配器，供后续结算应用服务使用。后续已实现 [凭证持久执行](voucher-operations.md)，以及 [批准后自动准备](voucher-preparation.md)，公开财务操作入口和付款授权仍在实施。

## 原事实与职责

财务应用服务负责锁定已批准业务、核对审批与财务双版本、登记同轮同类型的唯一有效凭证任务。事务外执行器向原财务目标查询期间、映射并推送原命令，响应由领域事实类型校验；ERP 维护总账、期间与科目。期间关闭采用阻断规则，不能自动把原记账日期移到下月。科目缺失返回不可用，平台不内置企业科目。

`VoucherCommand` 固定租户、业务/申请/轮次/双版本、员工和法人、原记账日期、核定含税/可抵扣税/冲销额、期间与映射快照、明细及发送时效。凭证区分员工借款挂账、费用挂账和实际付款三类：

| 用途 | 借方 | 贷方 |
| --- | --- | --- |
| 员工借款 | 员工应收款 | 员工应付款 |
| 费用挂账 | 费用净额及可抵扣税 | 借款冲销及员工净应付 |
| 实际付款 | 员工应付款 | 本次授权出款账户对应银行科目 |

各用途必须精确等于原核定总额，禁止把方向错误但总数相等的明细视为正确。费用行保留原行号和成本中心/项目；冲销保留每笔借款引用，不允许重复；零应付报销仍可生成非零含税费用凭证。全部核减为零时不生成零金额凭证，后续结算须独立处理无金额影响的关闭。

付款凭证必须携带原 `PaymentCommand` 与 `SUCCEEDED` 回单，核对租户、业务和申请标识、轮次、双版本、法人、员工、精确金额与出款账户。付款待处理、失败、退回或另一租户的回单不能作为已付款依据。构造命令本身不证明调用者有结算权限，也不证明其行明细来自实际已批准聚合，这两点由后续结算应用服务从持久业务中派生并校验。

## 固定 HTTP 协议

沿用 [财务网关](finance-gateway.md) 的租户隔离、HTTPS/Bearer、严格 JSON、2 MiB 响应上限、无重定向、无自动重试与事务外调用。四个操作均绑定持久财务目标；目标变化即返回 `TARGET_CHANGED`，凭据轮换允许继续查询原系统。

| 相对路径 | 请求 | 成功数据 |
| --- | --- | --- |
| `accounting-period` | `AccountingPeriodPort.Request`：法人、本位币、记账日期 | `OpenPeriod`：完整请求、期间编号/版本、起止日期、观察时刻及有效期 |
| `account-mapping` | `AccountMappingPort.Request`：法人、本位币和必要科目键 | `Mapping`：完整请求、来源版本、时效及完整科目集合 |
| `voucher-command` | `{command,commandDigest}`；请求号与 `Idempotency-Key` 都为持久命令 UUID | `VoucherObservation` |
| `voucher-query` | `{operationId,commandDigest}`；新的传输号，无幂等头 | 原命令的 `VoucherObservation` |

期间成功只允许包含原日期的开放期间，未来、过期或换日期的结果无效。关闭返回 `ACCOUNTING_PERIOD_CLOSED`，不适用法人返回 `LEGAL_ENTITY_UNAVAILABLE`。

映射键为 `role` 和 `selector`。`EXPENSE` 的选择器为费用类别，`BANK` 为原出款账户引用，`DEDUCTIBLE_TAX`、`EMPLOYEE_RECEIVABLE`、`EMPLOYEE_PAYABLE` 使用空串。映射必须完整且恰好覆盖所需集合，每项为 `{key,accountCode}`，无重复、缺失或额外项。缺少配置返回 `ACCOUNT_MAPPING_UNAVAILABLE`；平台不能用默认科目补齐。

过账响应的外层 `SUCCESS` 表示得到有效事实。`PENDING` 仅表示已受理；`POSTED` 必须有实际凭证号、原期间和日期、相等且精确匹配原命令的借贷金额、过账时刻。`FAILED` 必须带原操作绑定及封闭失败原因。`REVERSED` 保留原凭证与冲销事实，后续须进入对账。`NOT_FOUND` 只允许查询返回，版本为 0，不能当作自动重新过账的指令。

其他状态的版本从 1 开始递增且必填。不能用无原命令绑定的外层 `REJECTED` 作为过账失败；超时、网络故障、非法响应都表示结果未知。ERP 应在过账事务内核对原期间/映射版本，按同一编号与摘要幂等，并长期提供权威查询；缓存未命中不属于权威不存在。

发送区间为 `[createdAt, expiresAt)`，并受期间与映射有效期约束。过期阻止新推送，仍可查询已经受理的原操作。凭证成功、重复和乱序的持久状态推进由 [持久执行器](voucher-operations.md) 负责，适配器不承担该职责。

## 摘要与验证

摘要使用 SHA-256；字符串 UTF-8 编码，每项前附四字节大端字节长度。以 `agentflow-voucher-command-1` 开头，按 `VoucherCommand.digest()` 中顺序编码全部标识、版本、日期、金额、期间、规范排序映射、按行号排序明细、付款依据及有效期。可空辅助核算使用空串，其余字段禁止空值，数目显式编码；金额为两位小数。不依赖 JSON 属性顺序。

独立 Python 向量包含中文科目，结果为 `99de112e40fd24e5c91b5aaac01d92e0b306b1e874f97db515bb5828dbac8b80`。精确字段序列保存在本地 `voucher-digest-vector.json`。对接方须复算相同摘要，不能只按操作号返回无关内容。

新增领域 11 项、真实回环 HTTP 9 项通过；连同既有支付、预算、网关与配置回归共 66 项通过，范围有重叠。负例曾发现付款依据复用时遗漏租户一致性：原测试只改变同租户的版本和账户，未覆盖同标识跨租户。新增最小测试先失败 1 项，领域约束修复后全部通过。Java 作者与解析检查通过，共 569 文件、1000 命名类型。

本阶段没有数据库迁移或页面变更。回环 ERP 为合成契约测试；持久结算、授权、自动对账、回调及企业 ERP 联调继续实施。证据见 [会计端口记录](evidence/accounting-ports-20260928.json)。
