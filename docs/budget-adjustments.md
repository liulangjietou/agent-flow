# 独立预算调整

本项按用户已授权的剩余工作方案实施，支持预算追加、调减和同法人同期间调拨。现有 `BudgetCommand.ADJUST` 只改变报销的冻结占用，不能用于调整预算总额。

## 当前边界

已实现调整内容、原台账只读端口、不可变审批轮次、批准依据、敏感表单契约，以及 V76 独立申请和预检任务持久化。公开预算申请 API、预检后台编排、正式提交与实际最终批准已接通并通过 H2/PostgreSQL 联动验证。目录模板与申请、审批、历史轮次页面已接入；V76 原库升级、实际 HTTP 和页面组件验证通过。独立财务执行及实际额度变动继续实施，实际浏览器与窄屏验收仍待补齐。

本任务的隔离验收服务已从 V75 升级至 V76；135 张旧业务表的 1,694 行、6 份附件和 15 份原财务指令文件保持。main 和生产环境未升级。

## 调用链与职责

- 调用方：预算申请页面提出调整方向、日期、预算引用和正额金额；申请人明确选择本次任职。
- 下游：按申请员工授权的财务目录和 `budget-ledger` 只读端口提供真实法人、本位币、期间、额度、已占用和已使用金额。正式提交冻结这些依据，再接入原审批引擎。
- 影响场景：追加和调减、双边调拨、退回补正、撤回重提、期间关闭、预算并发变化、组织或财务目标变化、审批字段权限及未知执行结果恢复。
- 金额、期间和轮次不变量属于预算领域；申请、审批与队列事务属于应用服务；外部调用由基础设施适配器在事务外执行。历史读取由原字段权限约束。

## 已实现的业务约束

`INCREASE` 只允许调入预算；`DECREASE` 只允许调出预算；`TRANSFER` 必须有两个不同的预算引用。金额为正额、精确两位且使用法人本位币，未知草稿字段拒绝，不允许自报余额、原版本或执行成功。

台账返回请求中恰好一个或两个预算，每个预算带法人、独立版本、期间范围和状态。调拨的法人、币种、期间标识和日期边界必须一致；两端增减同额，合计额度不变。调减上限为 `max(额度 - 已占用 - 已使用, 0)`，不改写原占用或消费记录。真实超预算事实可以读取，允许申请追加，不伪造余额来通过预检。

外部观察必须不晚于使用时间、不超过五分钟并且尚未到期；历史轮次按当时提交时间恢复。后续补正追加新轮次，批准封存原内容。批准不会修改台账，也不会生成预算已生效事实。

每次草稿修改、提交冻结或最终批准追加原始修订；仓储拒绝替换原轮次、错误操作标签和错误具名人员。数据库绑定审批业务类型、申请人及原版本；并发修改只有一方保存，修订追加失败回滚主记录。

预检队列固定双版本、任职、财务目的地、原内容及递增尝试号。每张申请只有一个活动预检；排队、领取和完成分别保存历史。租约到期后的成功只记录超时，不能延长租约或重开已完成任务。读取申请事实统一经过申请仓储，校验数据库列与 JSON 身份一致，避免直接反序列化绕过来源绑定。

预算敏感明细使用保留字段 `budgetAdjustmentDetails`，普通申请入口拒绝创建这种表单。人工审核契约要求每条结束路径经过能完整读取明细的人工节点。管理员身份不构成绕过字段权限的依据。

## 外部只读协议

`POST {finance-base}/budget-ledger` 沿用版本 1 信封，返回原租户和传输请求号；请求固定 `legalEntityId`、`employeeId`、`accountingDate` 和 `budgetReferences`。响应包含原请求、观察版本与有效期，以及每个预算的稳定引用、名称、版本、期间和三项精确金额。

读取不携带写入幂等号，也不自动预留或调整预算。缺配置、财务目标变化、网络或协议失败均不能返回空额度假成功。允许的业务拒绝为法人不可用、员工不可用、预算不可用、预算制度不可用及期间关闭。响应中未知字段、数字型金额、过期事实、错误归属和缺失期间状态均拒绝。

预算执行领域和 HTTP 协议已实现；持久授权、执行队列、公开财务办理与页面继续接入。只有外部确认实际生效，才能展示执行完成。

## 原子执行协议与恢复

`ApprovedBudgetAdjustment` 固定实际批准后的申请版本、原审批轮次及目的地。独立财务授权必须使用批准后重新读取的台账，操作者不能是申请人；额度、占用和已用可以反映最新事实，但预算引用、调整方向、日期、期间和批准金额不能替换。授权最长五分钟，且不超过台账有效期或观察时间加五分钟。

`POST {finance-base}/budget-adjustment-command` 使用持久操作编号作为传输请求号和 `Idempotency-Key`，内容为 `command` 与 `commandDigest`。摘要以长度前缀覆盖原批准、新台账、全部额度变动、具名财务决定及期限；重复发送保持原编号、原文及摘要。每个变动提供预算引用、预期版本、原额度和新额度。外部必须一次核对全部预算版本、期间、授权期限及余额，原子应用所有变动，保持已占用和已使用金额；同编号不同摘要应拒绝，不能重新执行。

`POST {finance-base}/budget-adjustment-query` 只携带原 `operationId` 和 `commandDigest`，每次使用新的传输请求号，不携带写入幂等头。原授权过期不阻断已发送指令的查询，配置目标变化不能改查新系统。两个接口都不能在数据库事务内调用，也不能通过普通通用读取入口绕开目的地绑定。

回执固定操作编号、摘要、状态、递增修订及观察时间。`APPLIED` 必须包含一个原子生效引用、实际时间及恰好全部预算的前后版本、前后额度、期间、日期、占用和已用；调拨只返回一端、错额、修改占用或沿用旧版本均属于无效响应。`PENDING` 只表示受理，`NOT_FOUND` 只能来自原号查询且修订为零；`REJECTED` 必须是绑定原指令、保证整条指令没有生效的拒绝，普通 HTTP 或信封拒绝不能证明无副作用。

`BudgetAdjustmentOperation` 将超时、失联和过期租约保存为未知，后台只能退避查询原号；查无后必须明确重发仍在有效期内的原指令。已受理后查无、修订倒退、同修订事实变化或终态改写进入核对，后续普通查询不自动解除争议。只有从未发送或原系统明确无副作用拒绝才可安全结束本次执行占用。迟到结果不能覆盖新领取状态。

领域相关 32 项、回环 HTTP 与网关相关 51 项通过，含新增领域 15 项和调整适配器 6 项；范围与以前阶段有重叠。实际 0.01 元双端指令序列化、固定幂等字节、响应丢失后原号查询、严格回执及目的地限制通过验证，见[执行领域与协议证据](evidence/budget-adjustment-execution-protocol-20260930.json)。本阶段没有迁移或替换现有 V76 验收服务，也没有执行任何现有申请的预算写入。

## 申请与审批 API

所有路径位于 `/api/v1/budget-adjustments`，写入共用平台幂等请求边界；创建和补正回执只包含标识、双版本、轮次及申请状态。

| 路径 | 行为 |
| --- | --- |
| `GET /`、`POST /` | 本人有界目录、创建独立草稿；客户端不能指定申请人或预算余额 |
| `GET /{id}`、`POST /{id}/revise` | 按原轮次和敏感字段权限读取；补正同时核对申请和预算业务版本 |
| `GET /{id}/prechecks/options` | 本人预检可用性、当前目标摘要及最新检查标识 |
| `GET/POST /{id}/prechecks`、`GET /{id}/prechecks/{jobId}` | 本人检查历史、固定任职后排队、读取候选及当前是否仍可使用 |
| `POST /{id}/submit` | 使用最新有效预检，冻结轮次与任职并启动人工审批 |
| `POST /{id}/withdraw`、`POST /{id}/cancel` | 只改变尚未批准申请的生命周期，保留原台账快照 |

领取和结果落库分别用短事务，中间 HTTP 不持有数据库锁。结果落库重新检查双版本、原内容、任职和目的地。新检查登记后旧 READY 不可用于提交；进程崩溃后只对已领取任务记录到期超时，不自动重发旧读取。

正式提交将业务修订、审批轮次和 Flowable 启动放在同一事务。每条结束路径必须经过可完整读取明细的人工节点；真实最终批准才保存预算批准事实。任一修订或轮次写入失败回滚原任务，幂等重放不产生第二个轮次或批准。申请人补正后的草稿对旧审批人不可见，旧审批人仍只能读取获准的历史轮次；管理员也不绕过敏感字段约束。

后台预检由 `agentflow.budget-adjustments.precheck-worker-enabled` 控制，默认随已启用的财务网关启动；轮询间隔配置为 `precheck-poll-delay-ms`，读取租约配置为 `precheck-timeout-seconds`。关闭领取保留原任务和租约。
