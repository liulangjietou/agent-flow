# 独立预算调整

本项按用户已授权的剩余工作方案实施，支持预算追加、调减和同法人同期间调拨。现有 `BudgetCommand.ADJUST` 只改变报销的冻结占用，不能用于调整预算总额。

## 当前边界

已实现调整内容、原台账只读端口、不可变审批轮次、批准依据、敏感表单契约，以及 V76 独立申请和预检任务持久化。公开预算申请 API、预检后台编排、正式提交与实际最终批准已接通并通过 H2/PostgreSQL 联动验证。目录模板与申请、审批、历史轮次页面已接入；V76 原库升级、实际 HTTP 和页面组件验证通过。V77 独立财务复核、明确授权、事务外执行和原号恢复已实现，公开接口与财务页面已接入；V77 实际服务升级和执行验收接续进行，实际浏览器与窄屏验收仍待补齐。

本任务的隔离验收服务已从 V75 升级至 V76；135 张旧业务表的 1,694 行、6 份附件和 15 份原财务指令文件保持。main 和生产环境未升级。

## 调用链与职责

- 调用方：预算申请页面提出调整方向、日期、预算引用和正额金额；申请人明确选择本次任职。
- 下游：按申请员工授权的财务目录和 `budget-ledger` 只读端口提供真实法人、本位币、期间、额度、已占用和已使用金额。正式提交冻结这些依据，再接入原审批引擎。
- 影响场景：追加和调减、双边调拨、退回补正、撤回重提、期间关闭、预算并发变化、组织或财务目标变化、审批字段权限及未知执行结果恢复。
- 金额、期间和轮次不变量属于预算领域；申请、审批与队列事务属于应用服务；外部调用由基础设施适配器在事务外执行。历史读取由原字段权限约束。

## 已实现的业务约束

`INCREASE` 只允许调入预算；`DECREASE` 只允许调出预算；`TRANSFER` 必须有两个不同的预算引用。金额为正额、精确两位且使用法人本位币，未知草稿字段拒绝，不允许自报余额、原版本或执行成功。

台账返回请求中恰好一个或两个预算，每个预算带法人、独立版本、期间范围和状态。调拨的法人、币种、期间标识和日期边界必须一致；两端增减同额，合计额度不变。调减上限为 `max(额度 - 已占用 - 已使用, 0)`，不改写原占用或消费记录。真实超预算事实可以读取，允许申请追加，不伪造余额来通过预检。

外部观察必须不晚于使用时间、不超过五分钟并且尚未到期；历史轮次按当时提交时间恢复。后续补正追加新轮次，批准封存原内容。批准不会修改台账，也不会生成预算已生效事实。

每次草稿修改、提交冻结或最终批准追加原始修订；仓储拒绝替换原轮次、错误操作标签和错误具名人员。数据库绑定审批业务类型、申请人及原版本；并发修改只有一方保存，修订追加失败回滚主记录。

预检队列固定双版本、任职、财务目的地、原内容及递增尝试号。每张申请只有一个活动预检；排队、领取和完成分别保存历史。租约到期后的成功只记录超时，不能延长租约或重开已完成任务。读取申请事实统一经过申请仓储，校验数据库列与 JSON 身份一致，避免直接反序列化绕过来源绑定。

预算敏感明细使用保留字段 `budgetAdjustmentDetails`，普通申请入口拒绝创建这种表单。人工审核契约要求每条结束路径经过能完整读取明细的人工节点。管理员身份不构成绕过字段权限的依据。

## 外部只读协议

`POST {finance-base}/budget-ledger` 沿用版本 1 信封，返回原租户和传输请求号；请求固定 `legalEntityId`、`employeeId`、`accountingDate` 和 `budgetReferences`。响应包含原请求、观察版本与有效期，以及每个预算的稳定引用、名称、版本、期间和三项精确金额。

读取不携带写入幂等号，也不自动预留或调整预算。缺配置、财务目标变化、网络或协议失败均不能返回空额度假成功。允许的业务拒绝为法人不可用、员工不可用、预算不可用、预算制度不可用及期间关闭。响应中未知字段、数字型金额、过期事实、错误归属和缺失期间状态均拒绝。

预算执行领域、HTTP 协议、持久授权、执行队列、公开财务办理与页面已接入。只有外部确认实际生效，才能展示执行完成。

## 原子执行协议与恢复

`ApprovedBudgetAdjustment` 固定实际批准后的申请版本、原审批轮次及目的地。独立财务授权必须使用批准后重新读取的台账，操作者不能是申请人；额度、占用和已用可以反映最新事实，但预算引用、调整方向、日期、期间和批准金额不能替换。授权最长五分钟，且不超过台账有效期或观察时间加五分钟。

`POST {finance-base}/budget-adjustment-command` 使用持久操作编号作为传输请求号和 `Idempotency-Key`，内容为 `command` 与 `commandDigest`。摘要以长度前缀覆盖原批准、新台账、全部额度变动、具名财务决定及期限；重复发送保持原编号、原文及摘要。每个变动提供预算引用、预期版本、原额度和新额度。外部必须一次核对全部预算版本、期间、授权期限及余额，原子应用所有变动，保持已占用和已使用金额；同编号不同摘要应拒绝，不能重新执行。

`POST {finance-base}/budget-adjustment-query` 只携带原 `operationId` 和 `commandDigest`，每次使用新的传输请求号，不携带写入幂等头。原授权过期不阻断已发送指令的查询，配置目标变化不能改查新系统。两个接口都不能在数据库事务内调用，也不能通过普通通用读取入口绕开目的地绑定。

回执固定操作编号、摘要、状态、递增修订及观察时间。`APPLIED` 必须包含一个原子生效引用、实际时间及恰好全部预算的前后版本、前后额度、期间、日期、占用和已用；调拨只返回一端、错额、修改占用或沿用旧版本均属于无效响应。`PENDING` 只表示受理，`NOT_FOUND` 只能来自原号查询且修订为零；`REJECTED` 必须是绑定原指令、保证整条指令没有生效的拒绝，普通 HTTP 或信封拒绝不能证明无副作用。

`BudgetAdjustmentOperation` 将超时、失联和过期租约保存为未知，后台只能退避查询原号；查无后必须明确重发仍在有效期内的原指令。已受理后查无、修订倒退、同修订事实变化或终态改写进入核对，后续普通查询不自动解除争议。只有从未发送或原系统明确无副作用拒绝才可安全结束本次执行占用。迟到结果不能覆盖新领取状态。

领域相关 32 项、回环 HTTP 与网关相关 51 项通过，含新增领域 15 项和调整适配器 6 项；范围与以前阶段有重叠。实际 0.01 元双端指令序列化、固定幂等字节、响应丢失后原号查询、严格回执及目的地限制通过验证，见[执行领域与协议证据](evidence/budget-adjustment-execution-protocol-20260930.json)。本阶段没有迁移或替换现有 V76 验收服务，也没有执行任何现有申请的预算写入。

## 持久财务复核与执行

V77 新增财务台账复核、复核修订、原子预算指令、指令修订和安全结束证明五张表。此迁移已在 H2、PostgreSQL 及原有隔离验收库验证；当前验收服务为 V77。后台调度及公开办理已接入；批准不会自动生成财务授权，现有申请仍需明确办理。

复核从真实审批与独立预算申请同时派生来源，核对最终批准版本、轮次、申请人和冻结表单。每名财务在同一申请上只允许一个活动读取，尝试号在申请锁内递增；新读取一旦登记，旧 READY 不能再用于授权。单次读取租约到期保留失败，迟到结果不能成为授权依据。

明确授权必须对应该财务的最新 READY 原台账。保存指令、首版执行队列及复核消费使用同一事务；任意修订追加失败全部回滚。数据库外键绑定原申请、版本、财务人员及 READY 修订，唯一约束保证同一批准申请只有一个活动执行。已成功或结果未知的操作仍保留独占，不因退出执行队列而允许第二条调整。

领取和结果变更必须能由持久前版推导，旧进程、越级成功或改变原命令都会失败。恢复读取同时核对原 READY 修订与当前单次消费记录，不能只有旧台账而缺少真实消费证明。这一边界已先用失败测试复现，再补充仓储校验。

安全结束必须先停止尚未发送的队列，或引用原系统明确无副作用拒绝的当前修订。结束证明和解除独占原子保存；未知、查无、成功或核对状态均不能以“结束”重新生成命令。结束与后台领取使用同一申请锁，竞争只允许一方成功；结束后的原命令及历史可读取，但不能再次领取或更新。

新增领域 5 项、实际数据库重点 10 项通过；相关领域范围 20 项，H2 服务端范围 40 项，PostgreSQL 数据库范围 18 项通过，范围重叠。原批准来源、两人并发授权、竞争领取、安全结束、消费回滚、租约过期恢复、迁移保留及修订一致性均已验证，见[持久执行证据](evidence/budget-adjustment-execution-persistence-20260930.json)。后续工作器、当前财务任职复核及公开入口的接入结果见下文。

## 后台读取与执行

已接通独立台账复核工作器与原子预算执行工作器。领取和结果保存分别使用短事务，HTTP 在事务外调用；读取成功只保留 READY，必须由原财务再次明确决定，才单次消费该证据并入队。首次发送重新检查真实批准、当前法人任职及原目标；过期授权不发送。查询已发送操作不再以当前批准或原授权人的任职作为前提，仍由适配器严格绑定原租户、目标、编号和摘要。

工作器异常将原领取保存为未知，后续只能原号查询；权威查无也不自动重发。明确重发要求原授权人、原期限和当前资格都有效。安全结束由当前独立财务办理，不要求已停用的外部目标仍可访问，但必须保留从未发送或无副作用拒绝的当前证明。网络调用或迟到进程不能解除独占。

任职失效在复核完成时转换为停止状态。跨服务的只读守卫不建立独立事务拦截边界，避免其拒绝标记整个事务回滚而丢失停止记录；此问题已用真实 Spring 事务代理先复现，再通过 H2/PostgreSQL 验证修复。

调度随 `agentflow.finance-gateway.enabled` 启用，`agentflow.budget-adjustments.review-worker-enabled` 与 `execution-worker-enabled` 分别控制读取和执行领取，默认开启；两者使用独立线程。`review-poll-delay-ms`、`execution-poll-delay-ms` 默认 1000 毫秒，`review-lease-seconds`、`execution-lease-seconds` 默认 90 秒且限制为 15–300 秒。关闭工作器保留数据库原任务，重启按原版本和租约恢复。

新增后台验证 7 项；相关领域 12 项、H2 服务端 39 项和 PostgreSQL 数据库 17 项通过，范围重叠。外部端口在这批事务验证中使用合成响应，真实 HTTP 协议由前一阶段回环测试验证；没有执行既有验收申请。该阶段的公开财务权限、接口及页面已在后续接入，见[后台执行证据](evidence/budget-adjustment-execution-worker-20260930.json)。

## 财务办理 API 与页面

财务页面从已批准申请的详情进入，按原申请、原轮次和两份当前版本读取。原参与人只有在完整预算组可读时才能看执行事实；具备 FINANCE、当前法人有效任职且不是申请人的人员才能办理。待授权台账只向发起读取的本人财务展示。字段权限或任职变化后，旧成功请求的幂等回放也须重新检查权限。

| 路径 | 行为 |
| --- | --- |
| `GET /api/v1/budget-adjustments/{id}/execution` | 读取本人最新复核和原执行事实；可按本申请本轮 `operationId` 选择旧指令 |
| `GET /api/v1/budget-adjustments/{id}/execution/history` | 按原编号倒序、有界读取历史；默认 20，最多 50 项 |
| `POST /api/v1/budget-adjustments/{id}/execution/reviews` | 以批准双版本登记读取，成功读取不等于授权 |
| `POST /api/v1/budget-adjustments/{id}/execution/authorizations` | 明确消费本人最新有效台账，与固定指令及审计一起保存 |
| `POST /api/v1/budget-adjustment-operations/{id}/actions` | 原号查询、原授权人明确重发查无指令、或者有证明的安全结束 |

写入返回 202，只表示人工决定已保存；完整台账和当前执行结果须从权限接口重读。响应禁止缓存，未知字段拒绝。复核、授权、消费、队列及审计任一保存失败，不能留下部分成功。已批准、已授权、原系统已生效分别展示；完整指令、目标摘要和内部消费记录不返回页面。

页面逐分展示调出、调入两端的原额度、已占用、已使用、可用额和目标额度。原台账已经超预算时，可用额为零，仍可按批准追加或调入；不能错误地禁止修复预算，也不能借此调减已占用额度。确认时再次检查证据和授权期限。未知结果只能恢复原请求，刷新不会自动重发；明确查无后重发仍沿用原编号和期限。查询结果存在矛盾时，保留双方结果并禁止释放独占。

执行历史可分页并按原号重新查询，安全结束后的原授权保留。身份、轮次或版本变化使旧响应失效；任一读取或写入返回当前范围无权访问时，同时清除已读台账、历史及确认输入。页面的额度表按文本转义预算名称，金额使用原精确字符串。

服务端 H2 范围为领域 5 项、服务端 43 项，PostgreSQL 为服务端 29 项，其中财务工作流 11 项；范围与前期重叠。5 个新增操作和 11 个 schema 已与实际 Spring 路由及响应记录类型核对，契约总计 235 个操作、458 个 schema、84 个请求样例，见[财务接口证据](evidence/budget-adjustment-finance-api-20260930.json)。

外部纳秒台账曾暴露旧预检的毫秒截断问题；固定时间测试先复现，再将预览和完成时间一致向上收敛到数据库支持的微秒，原外部时间保持。两个精度回归以及实际审批/持久化均通过，见[时间精度证据](evidence/budget-adjustment-precheck-precision-20260930.json)。

前端新增财务 20 项、含预算申请/供应商财务/认证/幂等回归的范围 101 项通过，生产构建和契约检查通过。实际 Vue 组件验证了权限撤销、身份竞争、授权期限、未知请求恢复和历史分页；金额表 SSR 验证了精确展示及文本转义。这些结果不计为浏览器或窄屏验收，见[财务页面证据](evidence/budget-adjustment-finance-ui-20260930.json)。

## 申请与审批 API

所有路径位于 `/api/v1/budget-adjustments`，写入共用平台幂等请求边界；创建和补正回执只包含标识、双版本、轮次及申请状态。

| 路径 | 行为 |
| --- | --- |
| `GET /`、`POST /` | 本人有界目录、创建独立草稿；客户端不能指定申请人或预算余额 |
| `GET /{id}`、`POST /{id}/revise` | 按原轮次和敏感字段权限读取；补正同时核对申请和预算业务版本 |
| `GET /{id}/prechecks/options` | 本人预检可用性、当前目标摘要及最新检查标识 |
| `GET/POST /{id}/prechecks`、`GET /{id}/prechecks/{jobId}` | 本人检查历史、固定任职后排队、读取候选及当前是否仍可使用 |
| `POST /{id}/submit` | 使用最新有效预检，冻结轮次与任职并启动人工审批 |
| `POST /{id}/withdraw`、`POST /{id}/cancel` | 只改变尚未批准申请的生命周期，保留原台账快照 |

领取和结果落库分别用短事务，中间 HTTP 不持有数据库锁。结果落库重新检查双版本、原内容、任职和目的地。新检查登记后旧 READY 不可用于提交；进程崩溃后只对已领取任务记录到期超时，不自动重发旧读取。

正式提交将业务修订、审批轮次和 Flowable 启动放在同一事务。每条结束路径必须经过可完整读取明细的人工节点；真实最终批准才保存预算批准事实。任一修订或轮次写入失败回滚原任务，幂等重放不产生第二个轮次或批准。申请人补正后的草稿对旧审批人不可见，旧审批人仍只能读取获准的历史轮次；管理员也不绕过敏感字段约束。

后台预检由 `agentflow.budget-adjustments.precheck-worker-enabled` 控制，默认随已启用的财务网关启动；轮询间隔配置为 `precheck-poll-delay-ms`，读取租约配置为 `precheck-timeout-seconds`。关闭领取保留原任务和租约。
