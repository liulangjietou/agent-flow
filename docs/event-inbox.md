# 签名事件收件与原号恢复

更新：2026-10-01。事件来源认证、持久收件、后台单次消费、管理员查询与原号恢复已实现。配合[事件契约](event-contracts.md)和[原生等待](event-waits.md)，外部事件只能推进明确绑定的原等待。管理、设计器和等待页面已完成本地完整链路验收，见[事件页面](event-workspace.md)；实际企业来源继续独立联调。

## 调用链与职责

- 调用方是部署配置中明确启用的事件来源，向 `POST /api/v1/integrations/events` 发送签名原始字节。仅该精确 POST 路径使用来源认证；管理员查询、历史和恢复仍使用既有用户认证与 ADMIN 权限，OIDC 会话的其他写入继续执行原 CSRF 校验。
- 验签器在读取大小受限的正文后完成签名、时间、来源和严格信封校验。凭据来自部署配置，不能通过契约、收件或重试 API 写入。
- 收件应用服务按租户、来源、事件号去重，锁定申请与财务聚合，再校验精确契约版本。首次接收保存不可变认证事实、正文摘要和初始修订，返回稳定 202 回执。
- 工作器按到期时间取有限批次，每条使用独立短事务。应用服务锁定原申请及财务聚合、收件，再复核当前来源信任、原生等待和契约；引擎推进、业务收尾、审计、事务通知与消费标记一起提交。
- `EventInboxItem` 判断状态迁移、退避和恢复条件；JDBC 仓储保存原件和连续追加历史。事务失败先回滚，再按失败前修订单独记录失败，迟到的失败不能覆盖成功或管理员恢复。

受影响场景包括重复投递、并发消费、旧轮次或旧激活、暂停、契约停用、配置轮换、进程重启、财务审批收尾和通知失败。事件不携带表单、流程变量、批准结果或任意动作；后续人工节点仍必须由实际审批人办理。

## 来源配置与签名

入口默认关闭。需要部署方配置可信来源及独立凭据，例如：

```yaml
agentflow:
  events:
    enabled: true
    worker-enabled: true
    sources:
      erp-demo:
        tenant-id: demo
        source-key: erp
        trust-revision: 1
        enabled: true
        signing-secrets:
          - ${AGENTFLOW_EVENT_ERP_SECRET}
```

每个配置项对应一个唯一的租户与来源组合，最多 100 项。密钥格式为 `whsec_` 加标准 Base64 编码的 32–64 字节随机密钥，每个来源最多同时保留两把密钥用于轮换；不同来源及同一列表内不能复用相同密钥。配置错误只输出固定错误信息。

签名采用 [Standard Webhooks 的 HMAC v1 方案](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md)。本接口的具体约束如下：

| 请求内容 | 要求 |
| --- | --- |
| `webhook-tenant`、`webhook-source` | 对应启用的部署配置；还必须与签名正文中的租户和来源一致 |
| `webhook-id` | 事件号，ASCII 字母或数字开头，后续仅字母、数字、下划线和连字符，最长 128 位，不含点 |
| `webhook-timestamp` | 规范正整数 Unix 秒，投递时间与服务端相差不超过 300 秒 |
| `webhook-signature` | `v1,` 加 HMAC-SHA256 的标准 Base64；签名输入依次为事件号、点、时间、点、原始正文。最多接受四个以单个空格分隔的签名，必须至少有一个有效 v1 |
| 正文 | UTF-8 `application/json`，最多 8,192 字节；不接受压缩、重复 JSON 字段、未知字段、标量隐式转换或尾随第二个 JSON 值 |

关键头部重复时拒绝请求，入口不接受查询参数。摘要与签名都基于实际接收到的字节。重投保持同一事件号和原始正文，可以更新投递时间并重新签名。只是重新排版 JSON，也属于不同字节；同事件号会返回冲突。

签名正文仅包含以下九项：

```json
{
  "envelopeVersion": 1,
  "tenantId": "demo",
  "sourceKey": "erp",
  "eventType": "GoodsAccepted",
  "applicationId": "00000000-0000-0000-0000-000000000001",
  "roundNo": 1,
  "waitId": "actual-native-subscription-id",
  "contractKey": "goods-accepted",
  "contractVersion": 1
}
```

示例标识不是可办理的真实申请。`waitId` 必须来自该申请、该轮次的实际等待读取接口；重复遇到同一节点也必须使用新的激活身份。凭据、完整原始正文和签名不入收件响应或日志，数据库只保留必要信号及摘要。

日常密钥轮换保持 `trust-revision`，已经验签入库的消息继续使用原信任事实。变更来源信任主体时增加修订；旧修订消息进入待检查，不会自动按新配置消费。管理员恢复无法更换原租户、来源、信任修订、事件号、契约或等待，消费时仍须匹配原可信来源配置。

## 收件状态与恢复

| 状态 | 含义及后续 |
| --- | --- |
| `RECEIVED` | 已可靠入库，等待后台处理；202 仅确认这一事实 |
| `WAITING` | 原实例暂停、原契约或来源暂时停用，每 30 秒复查；不计为处理故障。事务异常按 5 秒起步退避，最高 300 秒 |
| `CONSUMED` | 原生等待已在同一事务内推进；重投仅返回原回执 |
| `IGNORED` | 原轮次／激活已失效，或等待引用的契约不同；终态，不允许将事件改投别处 |
| `REVIEW_REQUIRED` | 来源信任变化，或连续处理故障达到 10 次；停止自动处理，管理员核对后明确重试原件 |

恢复要求当前收件 `expectedVersion`、最长 500 字符的非空原因和 `Idempotency-Key`。恢复追加操作者与原因，保留首次接收时间和不可变输入；不会直接声明消费成功。相同幂等键回放原回执后，应重新读取当前状态，原回执可能早于后台处理结果。

## 管理接口与权限

| 入口 | 作用 |
| --- | --- |
| `POST /api/v1/integrations/events` | 来源签名认证，稳定 202 `{id,eventId}` 回执 |
| `GET /api/v1/integrations/events` | ADMIN，当前租户按接收时间和 ID 倒序分页 |
| `GET /api/v1/integrations/events/{id}` | ADMIN，当前处理状态及必要关联标识 |
| `GET /api/v1/integrations/events/{id}/history` | ADMIN，原收件的连续处理及人工恢复历史 |
| `POST /api/v1/integrations/events/{id}/retry` | ADMIN，对待检查的原件明确恢复；权限在幂等回放之前复核 |

成功响应禁止缓存。列表使用 `beforeId`，历史使用 `beforeVersion`，默认每页 30 条、最多 100 条；没有下一页时游标可省略或为空。重复或未知查询参数、非规范游标均拒绝。管理员读取范围不包含表单、附件、正文摘要或来源密钥，不扩大原业务字段权限。

V88 新增 `event_inbox` 与 `event_inbox_revision`，不回填历史外部事件。迁移约束和实体状态共同防止空原因的消费／忽略／待检查记录，以及缺少固定错误码的处理失败记录。旧二进制须连接与自身版本匹配的数据库。

## 验收边界

领域 5 项、H2 服务端范围 77 项通过；PostgreSQL 领域 5 项、服务端范围 29 项通过，范围重叠。覆盖验签、独立来源密钥、严格信封、并发去重、原事务回滚、暂停／停用、信任变化、原号恢复、分页、OIDC 保护及 V87→V88 迁移。OpenAPI 为 279 个操作、550 个 schema、108 个请求示例。

具体运行证据见[收件后台与重启验收](evidence/event-inbox-backend-20261001.json)。173 份实际 HTTP 响应通过契约检查，三次重启分别验证待收件保留、原信任恢复及已消费回放。三个实际等待各只推进一次，后续人工任务和已完成的人工决定保留。

独立 V87→V88 升级保持 216 张旧表的 5,118 行。整个运行验收结束后，171 张旧业务表的 3,673 行与 10 份附件保持原内容；只新增本次合成验收事实。原验收服务与源数据库未替换。

该后台阶段使用合成事件来源；管理、设计器和等待页面随后已完成本地验收，见[事件页面](event-workspace.md)。实际企业来源仍须独立联调；四个剩余工作包保持进行。
