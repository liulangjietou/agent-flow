# 供应商原付款真实退回

当前已实现累计银行退回协议、独立登记领域账本、固定目标 HTTP 适配器、V80 持久化、独立财务后台、原应付冻结、公开接口与办理页面。协议、存储、后台和页面范围验证分别记录，范围有重叠。既有非空数据库升级、实际浏览器办理及 ERP 独立调整继续实施，当前运行服务保持 V79。

## 调用链与职责

调用方是采购明细中具备原轮次完整字段权限的独立财务人员。应用服务从原银行命令与首次成功修订派生查询，保存读取意图后由后台事务外调用 `supplier-payment-return`。原 ERP 核销及本地占用完成分别保留，银行回款不直接恢复任何原账务或预算资源。

领域负责回款归属、累计金额、证据期限、独立办理人和单次消费。应用层负责原申请锁、当前法人任职、权限、连续历史、原银行争议与审计；持久层负责跨业务入款防重和原子登记。受影响场景包括核销前银行退回、核销后退回、多次部分退回、全额退回、不同财务先后核对以及旧回执恢复。

## 资金规则

- 固定原付款命令和首次成功银行事实。授权或旧账户目录到期不妨碍查询，不改用当前新目标、新账户或新付款号。
- 入款必须具有独立银行流水、正金额、币种、原公司出款账户引用和实际到账时间；原付款或付款回单编号不能充当入款。
- 部分退回累计严格小于原付款，原交易仍成功，原完成时间及回单保持。全额退回必须累计等于原付款，同时有更高修订的原银行撤销事实。
- `UNRESOLVED` 不包含可登记资金；`CONFIRMED` 表示原付款仍成功且没有实际退回。银行状态不能代替独立入款。
- 一次最多一百笔，证据最多五分钟且排他到期；不能超过当前银行观察的有效窗口。回款不得早于原到账或晚于本次观察。
- 累计回执保留全部此前已见原件，即使尚未登记。修订与观察时间不能倒退；累计回款版本增加也不能改写同一银行修订的事实。
- 明确登记只追加新增入款，每笔保留首次决定编号；重复确认不会再次增加累计资金。已登记实际回款保持待调整，不能靠另一项“无退回”确认清除。
- 原申请人和原出纳不能登记。查询只产生待核对结果，不自动确认资金；由发起查询的独立财务在期限内单次消费。

银行回款与 ERP 调整分步确认。后续需依据实际原核销或尚未核销的原预留分别处理；没有核清对应账务时保持待处理，不把资金登记当作应付已恢复。

## 当前验证

新增十三项领域测试，原银行与争议相关领域共 36 项通过；新增三项回环协议测试，网关相关 23 项通过。覆盖原公司账户、金额边界、累计遗漏、重复流水、原件期限、独立人员、单次查询消费、固定目标、无外部写入幂等键、严格 JSON、配置变化、事务外调用及应用 JSON 恢复。

新增检查曾发现两个独立版本号的边界：原测试覆盖版本倒退，没有覆盖累计回款版本增加但同一银行修订换回单。新增最小测试先失败，再要求相同银行修订的实质事实一致，范围回归通过。详细结果见[协议阶段证据](evidence/supplier-payment-return-contract-20260930.json)。这批测试不代表持久化、页面或真实企业联调完成。

V80 保存原成功修订、每次查询、累计账本和独立决定。登记、单次查询消费、修订及资金防重同事务保存；第二笔入款失败会撤销第一笔入款及全部本地变化。供应商银行资金共用法人内流水唯一键，可以先保存无 ERP 分录的真实回款；员工还款、借款退回和报销退回仍要求完整会计分录。登记的实际回款保持待调整，原银行、核销及完成事实不变。

新增八项存储测试覆盖累计追加、首笔决定归属、并发单次消费、跨付款重复流水、未登记历史、过时银行查询、纳秒原件恢复及 V79→V80 迁移。H2 领域 13 项、供应商存储 61 项通过；PostgreSQL 供应商存储 61 项、报销流程 125 项及借款还款 38 项全部通过。迁移测试保持十七张原表，但该迁移夹具中的共享入款表为空，既有非空验收库升级仍待实际办理阶段验证，见[持久化证据](evidence/supplier-payment-return-persistence-20260930.json)。

## 回款后台与原应付冻结

后台已接入独立财务查询、九十秒只读租约、事务外读取、明确登记和审计。每笔任务只查询一次，过期或失败后由财务发起新查询；迟到结果不能覆盖新状态。权限、原银行版本和当前本人查询在登记时再次核对，审计失败会回滚资金、决定及查询消费。原授权已到期或原核销已完成仍可取证。

出现新回款、未核清或矛盾原件时，按租户、法人、供应商和原应付冻结后续办理。原申请锁后按固定顺序锁定既有银行行，使冻结与另一张申请的占用、授权和新发送在短事务中串行判断。网络读取不持有这些锁。原核销已完成后银行重新变为未知、争议或退回，也会阻止同一应付再次付款。

ERP 已发送后仍保存真实核销结果；退回疑点阻止本地占用完成，不抹去 ERP 原凭证。原已完成记录继续保留。后台完成队列同时排除当前回款疑点和同应付更早付款的银行疑点，避免持续领取当前不可完成的记录。清除无退回疑点必须由独立财务确认新鲜原件；已登记实际入款继续等待独立 ERP 调整。

H2 相关范围共 116 项通过，PostgreSQL 领域 13 项、服务端 151 项通过，包含 35 项真实认证、Flowable 与回环财务接口流程。三项新增冻结测试先失败后通过，另有一项同应付早期付款复查的队列测试先失败后通过。

公开入口前补查了重复入款的错误处理：原存储测试只验证唯一键失败，没有要求应用返回明确业务冲突。新增最小测试先复现数据库异常直达调用方，再将登记冲突转换为稳定错误码，且第二笔登记、查询消费和审计整体回滚；H2 及 PostgreSQL 单项回归均通过。加上这项独立测试，H2 共 117 项、PostgreSQL 服务端共 152 项，最终结果见[后台证据](evidence/supplier-payment-return-backend-20260930.json)。公开 HTTP、办理页面及独立 ERP 调整尚未完成。

开发期间 Docker Desktop 停止，恢复原容器和 V79 服务后重新核验了原 2,401 行历史数据、7 份附件、16 份财务文件以及两笔采购的原银行、ERP 和完成凭据。此恢复没有升级既有验收库；新后台回归使用独立 PostgreSQL 测试库。

## 公开接口与办理页面

`GET /api/v1/supplier-payments/{id}/returns` 展示首次成功原付款、累计已登记回款、净资金与当前办理能力；登记历史按账本版本倒序分页，默认 25 条、最多 50 条。没有首次成功付款时金额为 null，不能查询或登记。当前金额不随历史分页变化，银行账号引用和完整命令始终留在服务端。

独立财务通过 `/checks` 登记一次只读意图，再通过 `/registrations` 明确消费本人最新原件。两类写入的幂等回放都重新检查当前法人任职、职责分离和原轮次字段权限；申请人及具备完整原文权限的参与人仅查看已登记记录，管理员没有敏感字段旁路。接口禁止缓存，拒绝自填金额、未知正文和写入查询参数；累计资金、历史决定、单次消费、审计与幂等回执同事务保存。

页面分别显示原付款金额、累计回款、原付款扣除回款，不将资金净额用作再次付款授权。查询和登记都先显示确认表单，登记需要核验材料与明确勾选；过期后禁用登记并在提交时再次判断。身份切换清除原件，迟到响应不能恢复旧按钮；结果未知使用原正文与幂等键恢复。回款变化会重读主付款及核销，银行争议变化也会重读回款。

新增六项真实认证、Flowable、数据库及回环 HTTP 集成测试在 H2 通过；PostgreSQL 范围共 85 项通过，包含存储 38 项、完整采购财务链路 41 项及 OpenAPI 6 项。前端新增 14 项，连同付款、银行争议和核销组件共 65 项通过；到期边界补测先发现本地期限错误被通用提示覆盖，再修复错误展示，最终新增范围 14 项再次通过。构建和静态契约通过；新增三个操作、十个 schema，原 OpenAPI 字节以片段插入方式保留。见[接口与页面证据](evidence/supplier-payment-return-workspace-20260930.json)。这些结果尚不代表既有非空验收库升级、实际浏览器或真实企业联调完成。
