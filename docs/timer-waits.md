# 定时等待与原失败恢复

更新：2026-10-01。本功能已完成隔离工作树的本地开发、H2/PostgreSQL、实际 HTTP、浏览器及重启验收。当前范围是相对节点激活时间的单次等待。事件、子流程、实例运维、暂停与 SLA 联动及安全批量办理继续实施，不把本功能算作整个高级流程工作包完成。

## 业务行为

- `TIMER_WAIT` 必须明确填写 `timerDelaySeconds`，取值为 1–31,536,000 的规范整数秒。不补默认值，不接受表达式、小数、cron 或循环。
- 实际进入节点时创建 Flowable 持久定时任务；服务重启保留原到期时间、执行标识及审批轮次。发布新版本不会改写已提交轮次。
- 到期只推进该等待。含等待的每条结束路径必须存在人工审批；并行分支中的等待不能提前释放另一条人工分支。等待推进保留独立审计，不生成虚假的人工审批意见。
- 下游配置、通知或财务准备失败时，引擎、申请、轮次和关联业务一起回滚。原任务转入原生失败队列，只保存安全错误码，不向查询接口复制异常原文。
- 同租户管理员填写原因、确认当前申请版本后，才能重试当前未暂停轮次的原失败等待。不能改时长、提前到期、切换节点或绕过后续人工审批。成功回执支持原请求幂等恢复；权限改变后不能回放。
- 撤回取消本轮等待；重提使用新轮次。原生实例暂停时调度器不会强行执行。本阶段没有开放实例暂停/恢复接口，也没有完成 SLA 剩余时间冻结规则。

## 职责与事务

调用链为设计器 → 定义校验与受限 BPMN 部署 → 原生持久定时任务 → 平台调度器 → 申请事务 → 实际后续节点、通知和审计。

原生异步执行器保持关闭，配置为 `flowable.async-executor-activate=false`；启用它会在启动时拒绝配置。原生强制执行 API 本身不能替代平台的到期、租户、当前轮次和暂停检查。平台调度由 `agentflow.timers.enabled` 控制，默认启用；`agentflow.timers.delay-ms` 默认 5000 毫秒，每批最多扫描 100 条，按到期时间与任务标识续查。

`ApprovalCompletionService` 由真实人工任务与等待推进共用。它先锁申请，再锁相应业务；仅在引擎实际结束时形成申请和轮次批准，并继续原有事前额度、借款、采购、预算及凭证准备逻辑。等待只是第二个实际调用方，没有引入任意引擎操作或可执行表达式扩展点。

## 公开接口与页面

- `GET /api/v1/applications/{id}/rounds/{roundNo}/timers`：复用申请读取权限，只展示该轮次的未结束等待、原到期时间、状态、错误码及当前可重试能力。
- `POST /api/v1/applications/{id}/rounds/{roundNo}/timers/{jobId}/retry`：仅接受 `expectedVersion`、`reason`，要求原幂等键；不接受额外字段和查询参数。

响应使用 `Cache-Control: no-store`。重试回执必须匹配原申请、轮次、任务及状态对应的版本增量；网络未知或回执错配时保留原恢复槽。

快速步骤、高级画布和便携模板均保留等待配置。申请详情的流程图显示本轮等待；取消确认不会执行。成功后重新读取申请与轮次。操作审计可单独筛选等待到期、失败和管理员重试；Webhook outbox 记录对应事实，真正完成时追加申请批准事件。
