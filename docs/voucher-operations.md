# 凭证持久执行与业务依据

更新：2026-09-28。V43 保存原始凭证命令、执行租约、回执和每个本地修订。当前已提供内部登记服务与后台执行器；最终批准后的自动准备、财务操作 API 和页面仍在下一阶段实施，现有批准不会自行生成凭证。

## 调用链与归属

批准后的 `Application` 与借款／费用聚合 → `VoucherSource` 派生不可变业务依据 → 期间与科目端口补充真实外部快照 → `VoucherOperationService.register` 在短事务中重新核对并登记 → `VoucherOperationWorker` 在事务外过账或查询 → 短事务保存结果及发布 `VoucherOperationChanged`。

`VoucherSource` 负责跨聚合的纯业务派生，状态推进由 `VoucherOperation` 自身负责。应用服务处理申请优先的锁顺序、真实仓储来源和事件事务；仓储负责精确绑定、唯一约束、乐观版本及修订追加；HTTP 适配器仍只处理 [会计契约](accounting-ports.md)。这样网络等待不会持有申请锁，本地确认失败也不会把 ERP 已执行误认成未执行。

借款挂账使用本轮实际批准金额和法人当地批准日。费用挂账使用最终核定本位币整分，保留原行号、类别、成本中心、项目及每笔借款冲销；税额按已有分摊拆分，不重新换算原币。核减后只能使用当前核定版本。纸单签收控制必须属于本轮，预算必须已确认冻结当前完整分摊。全部核减为零不建立零金额凭证，后续结算关闭独立处理。

付款凭证的纯派生已要求原成功支付回单；登记服务当前明确拒绝付款凭证，直到后续能从持久支付记录核验来源，不能由客户端提交一份成功声明绕过实际付款。

## 执行与恢复

| 当前事实 | 下一步 |
| --- | --- |
| `QUEUED` | 再次检查实际批准依据及发送有效期；领取后发送原命令 |
| `POSTING`／`QUERYING` 租约过期 | 保存 `UNKNOWN`，下一次只查询原编号与摘要 |
| HTTP 超时、非法响应或本地确认失败 | 保存封闭错误码及退避时间，查询原操作 |
| ERP `PENDING` | 保存外部版本与受理事实，按持久退避继续查询 |
| ERP `NOT_FOUND` | 停止自动处理；只有从未见过外部版本且原发送依据有效，显式领域动作才可重发原编号原内容 |
| ERP `POSTED` | 保存完整过账事实，可作为后续付款授权的必要依据 |
| ERP `FAILED`／`REVERSED` | 保留失败或冲销事实，不生成付款成功状态 |
| 倒退、同版本矛盾或非法状态变化 | `RECONCILING` 保留原接受事实、矛盾回执和见过的最高版本，不用于新付款授权 |

即使当前矛盾回执版本低于历史最高版本，最高版本也不回退。已确认凭证号、期间、日期、金额与过账时刻不能被后续矛盾响应覆盖。显式复查不清除矛盾；本阶段未开放人工解除矛盾接口。

同租户、业务、轮次、凭证类型只保留一个原命令。重试不能另造编号；不可变输入包含财务目标摘要。配置切到另一系统时停止网络调用并记录 `TARGET_CHANGED`。凭据轮换保持原目标时可以恢复。尚未发送且批准依据已改变则 `VOIDED`，发送窗口过期则 `EXPIRED`；不自动延长快照，也不删除原命令再登记新编号。

## 持久性与配置

`voucher_operation` 使用完整申请业务外键和同轮唯一约束；关系字段与领域快照读取时互相核验。更新须匹配前一版本、原输入与命令摘要；每次修订与当前行同事务保存。登记要求已有事务，外部执行器拒绝在数据库事务内运行。

在财务网关启用时，`agentflow.vouchers.worker-enabled` 默认启用；关闭后保留所有任务。`agentflow.vouchers.lease-seconds` 默认 90，范围 15–300；`agentflow.vouchers.poll-delay-ms` 默认 1000。单独的调度线程每批最多处理十项，跨执行器由数据库锁和版本控制。未接通 ERP 的部署没有合成成功兜底。

## 验证

范围测试共 85 项通过，包含 25 项会计领域、9 项真实 HTTP 适配器、9 项数据库与后台恢复、1 项迁移，以及借款批准、报销提交与 OpenAPI 回归。PostgreSQL 同时验证恢复与 V42→V43 保留升级，结果记录于 [验收证据](evidence/voucher-operations-20260928.json)，与 H2 测试存在重叠。

新增数据库测试覆盖并发只发送一次、HTTP 等待不占业务锁、事务回滚不发送、超时查询、权威查无不自动重发、过期执行者回执隔离、本地事件消费者失败后恢复、最高外部版本保留、跨租户读取及快照篡改。

初始状态机测试曾发现：只验证动作方法不能防止持久快照把曾发送操作还原成首次排队。最小恢复测试先失败，再补充构造不变量；恢复时只有保留权威查无证据才允许曾执行的操作重新排队。

本阶段未新增公开 API 或页面。所有 ERP 响应均为回环合成夹具，企业总账、付款和生产验收继续保持待验收状态。
